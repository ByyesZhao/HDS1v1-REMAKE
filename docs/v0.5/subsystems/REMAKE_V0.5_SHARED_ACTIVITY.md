# HDSI V0.5：共同活动

核对日期：2026-10-10。返回[总架构](../architecture/REMAKE_V0.5.md)。共同活动是有独立身份、公开剧情和推进时钟的共享模拟经历。

## 1. 开始、模式与结束

线上共同活动仍是远程聊天／游戏；线下共同活动把双方文字视作当面说话。开始须是双方确实确认现在开始，不能仅因谈到未来、预约到期或单方面邀请就进入活动。

个人导演提出开始，程序输出`【共同活动开始】`并在确认后开启活动计时和消息归属。首个共同节点随即可运行，不再等60秒。开始前的普通协商仍属普通聊天；活动开始后，仅明确普通归属的未读待处理输入按§7转移；旧活动积压不改归属。

共同活动主叙事输出公共剧情，程序统一加`【】`；角色动作由表达阶段输出，显示为`【动作：…】`。普通文字在相应线上／线下模式下理解。

最后先有本轮公共收尾，再输出`【共同活动结束】`；公开标记确认与正式状态提交是不同阶段，恢复需要识别合法过渡。活动结束前仍可能收到新消息，这些内容保留原活动身份。

## 2. 动作与纠正

线下用户的`【动作：伸手拉住她】`表示行为／尝试，括号外是说话。动作由模型按既定格式解释；程序没有逐条动作语义解析器，也不会因此强制角色配合。

用户可以在后续文字或括号剧情里明确纠正，例如`【我没有进商场，而是在门口拍照】`。角色应自然澄清或按新的剧情修正继续；原已发送记录保留。这不是编辑历史消息、全局撤销旧轮或替换整个活动记录的命令。

动作、发言、纠正均属于本场活动。控制消息必须全文为`【推进】`，它不作为角色可见对白或新的用户行动来源；活动外收到则提示当前没有活动。

## 3. 推进时钟

活动内新消息立即保存，不套普通15秒合批。普通自动推进默认在最后一条用户输入或最后一条已确认活动输出后60秒开始选择。

- 首节点按公开开始时刻立即触发。
- 新用户活动消息刷新等待。
- 新公开剧情、角色文字、动作或其他活动输出确认刷新等待；分段发送以最后实际确认的输出为准。
- 本轮没有任何输出，使用该轮成功完成时刻作为静默锚点，避免无输出循环立即连跑。
- `【推进】`直接请求下一轮，多个未消费请求可在同一节点处理；前一个未完成轮仍需先完成。
- 活动内到期预约也能触发合法节点，不能靠模型自行修改计时。

60秒表示选择下一轮的等待，不保证60秒后回复已经送达。模型生成和逐段发送还有耗时；失败、暂停或正在处理的旧轮不跳过。

每场活动由程序维护一个场景推进任务，随已确认时钟更新，结束时退出；模型不能创建、修改或取消此类任务。它是调度投影，不是额外的剧情模型。

## 4. 静默代写权限

程序选择本轮实际未读用户输入集合并冻结权限，然后向共同主叙事发送对应分支：

| 本轮选择 | 提示与行为 |
| --- | --- |
| 无新用户输入 | 允许公开代写双方在已确认活动内的动作选择及结果 |
| 有新用户输入 | 禁止新增用户动作，只能依据真实输入重述已明说行为；角色自愿配合留给个人导演 |

“双方无新输入”是现有提示词名称，实际资格是本轮没有选中新的用户输入，不是对双方所有历史发言做字数检查。上轮角色已经发过话不会永久取消代写；它影响的是活动计时。角色本轮是否开口，在主叙事之后由共同个人导演决定。用户复议旧消息不是新参与，`【推进】`也不是对白。

修补、生成恢复沿用这次冻结选择，后到未选未读消息留下一合法轮。不能让模型自己猜有没有代写权限。

静默时允许活动内关键动作和合理提前完成，不设置动作数量配额；不得替双方编新台词、报数、答复、心理、活动外重大承诺或关系决定。新增用户动作必须逐项列出且原文出现在公开剧情里，不能只藏在内部经历。已公开角色动作也是本轮已实现经历，个人导演不回头重做选择。

有新输入时，不能把“等我”推成进店、离开或购物，也不能由旧计划补出新用户动作。模型应保留未知。

## 5. 公开代写与记忆

用户已授权：成功公开的代写作为双方共享模拟剧情，用户回来可基于`【】`记录继续；角色可以记住和提起，不另加“用户是否在场看到”状态。无需每轮都有人回复，允许持续自动推进至活动完整收尾。

它不能证明现实用户真的做过相同行为，更不能据此新增用户稳定性格、能力、偏好或关系设定。后来纠正以新合法输入／公开结果修订后续理解和记忆，保留历史发送记录。

未发送草稿、未公开代写和未来纲要不能充当已发生来源。活动原文辅助连续理解，不自动扩大本轮新记忆或长期唤醒来源。

## 6. 节奏与自然收尾

普通活动提示词以约10个成功共同轮为自然收尾软目标，约第7～8轮开始收束；一般可以用约5轮或更多展开，但没有最少5轮硬规则。已完成、用户要求结束或角色生活需要时可以更早结束。实际平均轮数尚未统计。

默认硬上限20个成功共同轮；生成／发送失败恢复不重复计轮。默认上限下，第17～19轮进入收束阶段，20轮为最终轮。首节点必须有公开开场，最后一轮必须有公开收尾并结束活动。

提前结束也须有本轮公共正文，且提示要求正文实际交代收尾；仅仅非空不证明内容真的结束了。没有正文时，个人导演把结束意图留下一轮，不在修补阶段偷偷改主叙事。

收束阶段未完线索只减不增，保留原线索表达；目标／结束条件的含义延续依赖提示，程序没有完整语义漂移判断。最后未完事项可以公开合理暂停、约下次，不用“删掉线索”冒充全做完。小上限1～3可以短场，首轮同时为最终轮时同一公开正文兼顾开场与收尾。

剧情只能补已经过去的时间，不能为赶10轮把一分钟写成三小时。共同活动不是必须事先预约，已确认立即开始也合法。

## 7. 上下文与生活调度

活动全部内容——发言、动作、题外话、公共旁白、开始／结束标记——不占普通四段，也不刷新或保持普通聊天段。

活动中，共同主叙事、共同个人导演、表达和记忆得到本场完整已授权原文，旧版30条限制不适用于本场原文，也不按字符数截断。收尾轮沿用本轮选择完成表达和记忆；结束后的普通轮不自动获得完整活动聊天，通过正常相关记忆召回。一次活动可多条短期。

结束时仍未看的活动输入可转入普通待处理批次直接提供，仍保留活动归属、不占普通窗口。下一活动开始只迁移明确普通的未读输入；同批残留旧活动输入保持原批次顺序和就绪时间，待下一活动结束后再由普通调度首次读取。旧活动消息不延长新活动时钟、不进入新活动全文。

活动期间不另开自主推进；每个实际生活轮完成统一重设自主等待，活动结束后自然从完成时刻重计。合法活动使角色清醒参与，睡眠安排可由个人导演协调，结束后重新检查。学校通知不会另插活动节点，只在合法节点合并。

活动等待期间仍可派发每日环境准备。新环境请求后台等待，到期活动节点可先处理；ready等待串行提交门禁。旧preparationVersion0冻结任务继续串行恢复，可能暂时阻挡活动节点。没有“整场活动冻结环境链”的规则。
