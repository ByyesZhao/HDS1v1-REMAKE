## 方案判断

这次问题的关键是把“实际不能查看”与“不想立即回复”分开。沿现有字段与个人导演处理，比新增专注状态或程序强制回复更符合当前职责划分。以下设计可以保留：

| 计划内容 | 核对结论 |
| --- | --- |
| 普通专注活动默认可读，个人导演选择 now／later／none | 符合现有 App 顺序；先采用主叙事场景再确定 visible，再调用个人导演。none 仍可提交已读且没有输出，later 使用已有复议任务 |
| false 必须有合法结束时间，缺失进入格式修补 | 可以直接加在 `narrativeTask()` 现有字段控制校验中；`ModelClient` 已接收 parse 错误并执行最多 2 次修补，不需新调用链或 schema 重构 |
| 结束时间到达后先补生活，延长则重排 | `canRead()` 已处理预计结束到期；App 会在新的主叙事结果下重新判断，延长后保持未读并更新待看任务 |
| 多条消息复用一个待看检查 | `Scheduler.stashPending()` 已按 pending／unread 查找旧任务复用；不需要新增队列或调度器 |
| 保留睡眠和共同活动边界 | 睡眠独立使用 wakeAt；合法共同活动已有手机／睡眠门禁例外。统一 Activity 输出校验不必新增共同活动拒收条件 |
| 部署时条件化修正已知旧状态，并补未读唤醒 | 必要且范围合理。只改提示词无法立即纠正已持久状态；停服、备份、确认无未完成轮、现场重新核对、同事务补任务等步骤已覆盖主要边界 |

核对位置：[contracts.ts](../../../../src/model/contracts.ts) 第 52～64 行、[client.ts](../../../../src/model/client.ts) 第 55～67 行、[state.ts](../../../../src/host/state.ts) 第 7～16 行、[scheduler.ts](../../../../src/host/scheduler.ts) 第 54～79、92～104 行、[app.ts](../../../../src/app.ts) 第 131～196 行。

这些是“现有机制足以承接新规则”的判断，**不是宣称新字段约束已经实现**。当前源码仍允许 false＋null；计划要求新增的拒绝／修补测试应在旧代码上失败。

## M1：收窄重启后“不重复发送”的验收措辞

**级别：Minor，文档澄清，不是本次新增产品 BUG。**  
**位置：**原计划任务 2，第 105 行：“重启恢复不丢消息或重复发送”。

当前恢复只保证跳过已经持久确认的分段。`sending` 在恢复时会转成 `retry`，结果未知的发送仍会重试。如果 QQ 实际收到、但确认尚未写入本地数据库，重启可能再次发送该段。因此不能把这一行理解成此次需要实现跨平台的绝对只发一次。

依据：[app.ts](../../../../src/app.ts) 第 61～64 行、[recovery.ts](../../../../src/recovery.ts) 第 28～38 行；[recovery.test.ts](../../../../tests/recovery.test.ts) 第 38 行起已有“跳过已确认分段、重试未知分段”回归。本次已复跑通过。

建议 SOL 将该句改成：

> 未读消息与检查任务在重启后仍可恢复，已确认分段不重发；确认结果未知的分段沿用现有重试语义，不因本次查看资格改动扩大或缩小重试范围。

验收分开断言：未到期的检查任务重开后仍能唤醒、不会重复创建同一待看任务；confirmed 分段跳过；sending／retry 分段保持原行为。原计划第 4 节“已尝试发送的旧冻结结果沿用现有恢复合同”已经正确，无需改动恢复实现。
