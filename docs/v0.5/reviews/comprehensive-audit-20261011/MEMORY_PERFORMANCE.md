# 记忆与数据访问审核

日期：2026-10-11。源码基线：`ce7e88e9c8e4940ec17ae4b5dae2392fd6ddb57c`。状态：审核完成，建议未实施。

本报告检查基础提取、短期／长期许可、唤醒、合并、容量、清理、后台维护和检索的关键路径。没有确认新的记忆生命周期正确性缺陷；这不表示逐个状态组合已经穷尽。主要发现是串行提交中的重复工作，以及当前检索质量的提升空间。未读取正式数据库、私有配置或人设，未发起远程 Embedding。

证据：[探针](evidence/memory-performance-probe.ts)、[JSON](evidence/memory-performance.json)、[执行日志](evidence/memory-performance.log)。探针只用内存 SQLite 和合成数据；容量／清理耗时各预热一次、采样七次。时间是当前机器的现状样本，不是优化后的收益承诺；同期存在其他审核进程，工作次数比毫秒值更适合复验。

## M1：优先消除串行容量归一中的全量正文载入和排序查询

`src/recovery.ts:98` 每个非环境故事轮在正式提交事务内调用 `normalize`，包括本轮没有新增记忆的情况。`src/memory/capacity.ts:47,63` 两次调用 `allOwners()`；`src/memory/store.ts:121` 每次读取三个池的完整 JSON 正文。之后 `protectedIds()` 和 `counts()` 又分别读取元数据。长期超量时，`activeOrder → meaningfulAt → listAwakenings` 在排序比较器内重复查询同一条记忆。

| 合成输入 | 无超量 normalize 中位数 | cleanup.nextDeadline 中位数 | 超量 1 条的 normalize |
| --- | ---: | ---: | ---: |
| 100 短期＋1000 长期＋500 归档，每条 content 128 字符 | 95.69 ms | 107.31 ms | 135.22 ms |
| 同样条数，每条 content 4096 字符 | 468.77 ms | 174.37 ms | 511.11 ms |

两档无超量均 **修改 0 条，却完整载入 3200 个 owner**。增加一条普通长期后，只退出一条，但执行 **3600 次唤醒查询／3617 次 prepare 调用**。这是排序内部数据库访问造成的工作量，并非真实模型慢或网络慢。

收益较高的改动顺序：

1. 用同一份元数据／计数快照判断是否超量，没有差额立即返回；只为实际退出对象读取完整正文。保留对本轮恢复记忆和短期关联长期的保护。
2. 超量时一次性读取候选的最近有效唤醒／计数，预计算排序键；比较器只比较值，不访问数据库。
3. `metadataCanonical()` 当前每调用一次都重建整个 `Map`（`src/memory/metadata.ts:17-21`）；将映射作为该次计算的共享局部索引，供保护、截止和清理复用。`MemoryCleanup.nextDeadline()` 也可复用同一快照，减少纯调度时的重复扫描。

这是 CPU、解析和同步数据库访问优化，不需要改变 7／90／3／30、容量大小、排序优先级或记忆正文。预计工作量中等，验收应比较不同文本体积下的串行阻塞时间、每次查询／物化行数，并回归保护、同日唤醒和容量退出行为。已有 `tests/review17-capacity-cost.test.ts` 仅保证“未超量时不读取唤醒历史”，没有覆盖完整正文重复载入或刚超量时的排序查询数量。

## M2：在读取向量前判断语义通道是否可用

`src/memory/retrieval.ts:28-30` 先调用 `selectCandidates()`；`src/memory/store.ts:129-145` 无条件 JOIN 向量并复制成 Float32Array；之后 `retrieval.ts:36-44` 才得出 `uncalibrated` 等跳过原因。现有文档已准确披露纯语义通道未标定，不属于文档夸大。

探针给 1000 条长期各配 1024 维向量，实际检索每次读取 **4,096,000 字节向量**，最终 `semanticSkipReason=uncalibrated`、远程请求数为 0。这些向量没有参与该次排序。环境冻结还会把它们转为普通数组保存（`src/environment/snapshot.ts:50-56`），使同一问题扩大到持久化载荷。

建议把“无索引／空查询／未标定／签名不匹配”等判定前置，为候选选择增加明确的是否需要向量参数；只有通道可用时才 JOIN／解码。冻结检索应保存当时的能力判断及配置签名，保持恢复合同。无需删除已有索引或关闭后台索引能力。改动规模小到中等，可独立于 M1 交付。

## M3：用真实自然语言扩展检索标定，比继续堆叠上下文更有价值

当前 `defaultCalibration.lexical` 两类阈值均为 1，`semantic=null`。词法算法按去通用词后的汉字双字片段覆盖率选取（`src/memory/lexical.ts:3-10`）。对同一条“生日礼物是自己做的卡片”：

| 查询 | 分数 | 默认词法能否选中 |
| --- | ---: | --- |
| 生日礼物 | 1 | 能 |
| 还记得那次生日礼物吗 | 1 | 能 |
| 你还记得我送你的生日礼物吗 | 0.6 | 不能 |
| 我送你的贺卡还留着吗 | 0 | 不能 |

这四例只证明具体漏召回，不代表真实聊天总体召回率，也不证明模型后续补查必然失败。它解释了为何“库中有相关记忆”仍可能在自然问句中拿不到。既有标定夹具只有 16 例，多为短关键词；`scripts/check-memory-retrieval.ts:18` 在名为 validation 的集合上选择阈值，并直接报告该集合结果，没有另外的盲测集。

建议先建立包含真实问句风格、同义改写、多话题、时间变化和相似干扰经历的标注集，明确分开标定与盲测；再比较查询规范化、词法阈值和有签名约束的语义通道。指标至少包含错误召回、遗漏、查询成本和个人导演实际获得的相关资料。不能仅为提高召回就把所有记忆注入，也不建议未经评估直接降低全部阈值。

这是产品效果优化，需要样本与模型验收，工作量中等；可与低风险的 M1／M2 工程优化分开推进。

## 本次没有认定为问题的行为

- 活跃短期、常驻依据或缺摘要使容量暂时超标，是当前明确规则。
- 普通长期在短期退出后才生效、事件更新不等于唤醒、同日只计一次，所查实现和测试与说明对应。
- 后台准备异步、应用串行并校验版本，仍存在同步冻结／提交成本；并行等待不等于所有本地工作恒定时间。
- 未给正式库体积、数月延迟或真实模型记忆质量作结论；原始消息／经历不受三个记忆池的数量统一封顶。
