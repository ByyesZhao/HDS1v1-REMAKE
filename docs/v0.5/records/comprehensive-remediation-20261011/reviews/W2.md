## P1: Startup budget ends before all startup work completes

Location: `src/deployment/sticker-web-runtime.ts:34-42` (especially line 40).

`ready.then(stopStartupWait, stopStartupWait)` clears the timeout and removes the internal/error listener immediately after Puppeteer injection, while `Promise.all([startup, ready])` still waits for `ctx.start()`. The installed Context.start flushes all plugin startup tasks. Puppeteer itself installs the canvas plugin, whose startup opens a page and navigates before becoming ready. If canvas startup hangs after Puppeteer is injected, the promised 60000ms startup budget no longer applies. Likewise a later internal startup failure can be missed.

Reproduction: replacement Puppeteer Service constructor calls `ctx.plugin(Canvas)`; Canvas is a Service with `static inject=['puppeteer']` and `async start(){ await new Promise(()=>{}); }`; Puppeteer starts normally. With `startupTimeoutMs:40`, an outer observation at 250ms printed:

```json
{"probe":"ready-browser-with-hanging-canvas","result":"STILL_PENDING_AFTER_250MS"}
```

Keep the startup deadline and internal/error observation alive until the complete startup transaction settles, including `Context.start()`. Add a real Context regression for hanging and failing subordinate startup after Puppeteer is ready.

## P1: Runtime disposal does not await actual service cleanup or propagate its errors

Location: `src/deployment/sticker-web-runtime.ts:25-26` and the resulting Storage close at `scripts/stickers.ts:37`.

Installed `@cordisjs/core/lib/index.cjs` Lifecycle.stop (line 573) calls `scope.reset()` and returns. Scope.reset (line 706) launches disposal hooks asynchronously and catches errors into internal/error. MainScope.dispose (line 856) similarly returns a boolean. Therefore awaiting `ctx.canvas.ctx.scope.dispose()` and `ctx.stop()` does not await the actual canvas/Puppeteer `stop()` promises. Storage closes while service cleanup is still running, and a rejected browser.close is merely logged after runtime.dispose already succeeded. Existing tests record a synchronous Context dispose hook or replace scope.dispose with a throwing async mock, so they miss the installed framework behavior.

Reproduction: replacement Puppeteer Service has `async stop(){ await delay(40); throw Error('SYNTHETIC_BROWSER_CLOSE_FAILURE'); }`. Runtime disposal resolves, Storage closes, and only afterward does stop fail:

```json
{"probe":"asynchronous-browser-stop-failure","result":"resolved","stopSettledAtReturn":false,"events":["browser.stop.started","runtime.dispose.resolved","storage.closed","browser.stop.failed"]}
```

Acquire explicit completion/error ownership of the actual service stop operations, ensure canvas/page/browser cleanup is awaited before Storage.close, avoid duplicate closes, and report cleanup failure through the returned rejection so the CLI exits nonzero. Add a real Service asynchronous-stop test plus CLI close ordering/error regression.

## P1: Startup timeout can leave a late-acquired browser alive

Location: `src/deployment/sticker-web-runtime.ts:41-47` and disposal at lines 21-28.

A timeout calls Context.stop while Puppeteer.start can still be awaiting browser launch. That early stop sees no browser and completes. When startup later obtains the browser, neither the memoized runtime disposal nor the already-reset scope closes it. The installed Puppeteer implementation assigns `this.browser = await launch(...)` and stop only closes the current `this.browser`, so this is a real resource-ownership gap. Awaiting the initial stop alone does not address it.

Reproduction: replacement Browser.start waits 120ms then marks a simulated resource open; Browser.stop records whether a resource exists and closes it. At startupTimeoutMs=40 the factory rejects promptly, then late startup leaves the resource open (and Koishi emits INACTIVE_EFFECT while setting the service):

```json
{"probe":"late-browser-acquisition-after-startup-timeout","result":"browser startup timeout after 40ms","open":true,"events":["stop.open=false","factory.returned","browser.acquired"]}
```

Make startup acquisition cancellation-safe: promptly reject on the startup budget, but retain ownership of the pending acquisition and close anything that appears after cancellation. Add a controlled delayed-start resource test; preserve the existing never-settling-start timeout behavior without waiting forever.

### P1: The apparent canvas scope is the root scope, so browser closes before canvas

Location: `src/deployment/sticker-web-runtime.ts:37` (`ctx.canvas.ctx.scope.dispose()`).

A narrow probe loaded the **actual installed Puppeteer and canvas plugins**, replacing only puppeteer-core.launch and puppeteer-finder with synthetic implementations. Cordis service tracing rebases `ctx.canvas.ctx` to the calling root Context: `ctx.canvas.ctx.scope === ctx.scope` is true. Therefore this line disposes the root, which starts browser stop and canvas stop concurrently, instead of draining the canvas before browser closure. The earlier replacement-Service tests did not assert this ordering.

First actual-plugin probe observed `[browser.acquired, browser.closed, canvas.closed, storage.closed]`. A follow-up synthetic browser marked its connection closed in browser.close; page.close waited one turn and rejected if disconnected. This mirrors installed Puppeteer CdpPage.close, which awaits screenshot operations before asserting a live connection and sending Target.closeTarget. Result:

```json
{"probe":"actual-plugin-close-order","scopeInfo":{"root":"root","canvas":"root","canvasIsRoot":true},"result":"sticker browser cleanup failed: SYNTHETIC_PROTOCOL_CONNECTION_CLOSED","events":["browser.close.started","canvas.close.started"]}
```

Resolve the actual owning canvas scope from captured registration/service ownership (rather than the caller-rebound service.ctx), await its real cleanup, then stop the root/browser. Add a regression using the actual plugin with synthetic browser transport that requires page closure before browser closure and asserts each occurs once. Findings sent to implementer and root. No source/Git mutation; probes used in-memory Storage and no real browser/network.

The same actual-plugin probe independently confirmed late launch now closes its browser after timeout, including the real plugin's post-launch registration failure on an already disposed Context. This unexpected late startup error is explicitly logged and the browser is closed.
