## Findings resolved in re-review

### R1 — P2: reject owner identities that collide in the real store

**Resolved.** The validator now rejects duplicate physical table/id identities before seeding, while retaining typed identities across distinct tables. Independent execution passes both the short/long collision rejection and the detail/long same-ID real-evaluation regression (both owners are true positives). The original finding follows for traceability.

Location: `scripts/lib/memory-retrieval-evaluation.ts:156`, `:175-192`, `:242`.

Validation rejects duplicate typed owner keys, but accepts both `short:same` and `long:same`. `MemoryStore.saveOwner` stores both kinds in the same `memories` table using only `ownerId` as the primary key (`src/memory/store.ts:124-128`). Seeding the second owner silently replaces the first. The evaluator then reports the missing owner as a retrieval false negative, although it was never available to retrieval. This violates the complete-declared-owner seeding contract and can corrupt comparisons on otherwise accepted datasets.

A standalone miniature synthetic dataset with these two owners, both currently eligible and both matching `collision topic`, passed structural validation and produced:

```json
{"validated":true,"declared":["short:same","long:same"],"seeded":["long:same"],"actual":["long:same"],"metrics":{"TP":1,"FP":0,"FN":1,"precision":1,"recall":0.5}}
```

Reject short/long IDs that share the real storage key before evaluation, and preferably assert that all computed closure keys were actually seeded. Add a miniature regression for this rejection and a separate positive regression proving that `detail:same` and `long:same` remain distinct, since those use separate tables and the benchmark explicitly requires typed identity. Do not change runtime storage or the frozen main labels. The accepted main fixture does not contain this collision.

### R2 — P2: make the CLI input-overwrite guard recognize Windows file aliases

**Resolved.** The CLI now compares normalized Windows path casing and checks existing-file bigint device/inode identity, before dataset loading/evaluation. Independent execution confirms that a case-only alias is rejected and disposable input bytes remain unchanged. The existing-file identity implementation also addresses links; actual hard-link setup is explicitly skipped because this host denies link creation with EPERM. This is a recorded test limitation, not an unresolved required Windows case-alias defect. The original finding follows for traceability.

Location: `scripts/evaluate-memory-retrieval.ts:11-12`, `:28`.

The overwrite guard compares `resolve(input) === resolve(report)` as case-sensitive strings. On the current Windows filesystem, `memory-retrieval-v2.json` and `MEMORY-RETRIEVAL-V2.JSON` identify the same file but bypass that comparison. A report path differing only in case therefore allows the final `writeFileSync` to overwrite the frozen dataset, calibration, or candidate input.

A read-only proof against the fixture returned `guardRejects:false` and `sameDeviceAndInode:true`; no evaluation or write was performed. Reject equivalent existing-file identities (and normalize platform path casing where appropriate). Add a CLI regression using a disposable miniature input and a case-only output alias: require the overwrite error before dataset validation and verify unchanged input bytes. Handle symbolic/hard-link aliases when checking existing file identity as well.
