> 实施时使用 `superpowers:executing-plans` 逐项执行，保留失败回归与交付证据。本文件保留实施合同；代码及停服部署已完成，实际状态与尚未验证范围以交付记录为准。

**日期／状态：** 2026-10-10／代码及正式库部署完成，等待用户手动启动及真实QQ复核。代码基线 `a66a89c`（最新产品修复 `47eb14d`）；本地OneBot连接已另行修正。已采纳[ASTRA计划审核](../../reviews/phone-access-20261010/PLAN_REVIEW.md)的恢复语义、协议2及部署查询澄清。

**目标：** 普通专注活动允许查看消息，角色自行决定是否回复；确实无法查看的非睡眠活动必须给出结束时间，避免未读消息无期限等待。

**架构：** 沿用 `phoneAccess`、`expectedEndAt`、独立睡眠区间及现有 `check_messages` 任务。主叙事判断现实场景，程序检查控制字段并执行读取资格；个人导演决定回复意愿，不新增专注状态机或强制回复策略。

**技术栈：** 现有 TypeScript、Zod、SQLite、Vitest；不增加依赖。

**设计依据：** 本文件第2～4节、用户2026-10-10确认的场景规则，以及[实际未回复排查](../../records/onebot-connection-20261010/README.md)。返回[计划入口](../README.md)。

## 1. 规模与现状

这是现有流程的局部修改，预计主要修改提示词、主叙事合同及相关回归；不需要新增系统或数据库字段。普通聊天和共同活动共用活动合同，睡眠另有门禁，部署时还需处理已有状态，因此不能只补一句提示词就结束。

本次实测：3条14:39输入合批后，主叙事把实验室文献整理设为 `phoneAccess=false, expectedEndAt=null`；整轮完成，但消息保持未读，聊天个人导演、表达均未调用。现有代码及调度文档允许这种状态等到其他合法唤醒，下一次自主推进约17:38。此次要消除这种正常专注活动被误当成不可查看状态的情况。

## 2. 场景与权限规则

| 情况 | 查看资格 | 后续处理 |
| --- | --- | --- |
| 上课、看文献、写作、整理数据、一般实验等普通专注活动 | 默认 `phoneAccess=true` | 消息可进入个人导演；按当前反应选择 `now`、`later` 或 `none` |
| 洗澡、游泳等明确无法查看手机的活动 | `phoneAccess=false`，必须有具体 `expectedEndAt` | 保留未读，安排到期检查；到时先补生活，再判断是否可读 |
| 有明确限制的特殊上课／实验环节，例如要求收起手机、双手持续操作或不能离开的环节 | 可以 `phoneAccess=false`，同样必须有结束时间 | 依据实际限制设定，不能仅因为“上课”“实验”“忙”就禁止查看 |
| 睡眠 | 使用现有 `sleep.sleepAt`／`sleep.wakeAt` | 保留睡眠门禁和起床后处理积压消息，不再额外生成一份睡眠活动计时 |

`phoneAccess`只代表实际查看／沟通资格，不代表是否想聊天、是否愿意马上回，也不代表回复必然立即发送。专注及回复意愿由已有场景、经历和个人导演判断表达，不新增 `focused` 枚举。

上述默认是提示词中的场景原则，不建立描述关键词黑名单。模型仍需要判断是否存在真实限制；程序负责布尔值和时间条件，不用“实验”两个字决定能否查看。

## 3. 程序合同与调度

### 3.1 新主叙事输出

普通与共同活动主叙事的新输出统一检查：

- `currentScene.activity=null` 合法。
- `phoneAccess=true` 时，`expectedEndAt`可为null，允许没有严格结束时间的专注活动。
- `phoneAccess=false` 时，`expectedEndAt`必须是合法具体时间，且严格晚于 `startsAt`；不允许null或零长度区间。
- 已有“当前活动不能从未来开始”的校验继续保留。若预计结束时间已经到达，`canRead`按现有逻辑返回可读；不能仅因旧 `phoneAccess=false`阻挡读取。
- 到期主叙事如判断活动确实延长，必须给出新的有效结束时间；不能用null退回无限等待。

在 `narrativeTask()`现有控制校验里用字段路径报错，例如 `currentScene.activity.expectedEndAt: required when phoneAccess=false`，进入现有格式修补，最多2次修补；仍失败则沿用报错暂停，不替模型猜一个结束时间，不自动改成true。

JSON字段及主叙事接口保持原样。跨字段要求写入提示词与程序解析校验，不能只靠提示词，也不要求为这次调整重构所有schema。

### 3.2 查看与回应分开

沿用 `src/app.ts`顺序：主叙事补完此前生活 → 采用新活动状态 → 程序确定可见输入 → 个人导演决定回应 → 有回应意图才调用表达。

`now`产生草稿并进入表达；`later`设定未来复议时间，届时重新决定；`none`视作已经看到但不回应，不给它自动补一个查看任务。普通合批15秒、活动推进60秒、空闲整理15分钟和自主生活150～210分钟均不变。

### 3.3 不可查看到期检查

沿用 `app.ts`与 `Scheduler.stashPending()`已有的 `check_messages/checkReason=unread`机制，复用同一个待看任务，不因多条消息重复建立任务。确实不可读期间，新消息仍先落库；正文及图片观察不能提前进入角色模型输入。

到期会先运行普通主叙事：若恢复可读，将积压消息交个人导演；若给出新的不可读区间，则更新检查时间。定时器和任务重启恢复由现有机制承担。

### 3.4 共同活动与睡眠

新的“false必须有结束时间”合同同样覆盖共同活动主叙事，避免两类主叙事给同一字段不同的数据约束。共同活动面对面输入及代写权限仍走原有规则，不使用 `phoneAccess`新增一层拒收门禁。该活动时间字段也不取代共同活动60秒推进、约10轮收尾及20轮硬上限。

睡眠在主叙事之前已有独立门禁，由 `wakeAt`指定退出时间。保留预约调整作息、环境导演不受睡眠限制等现有行为，不把睡眠硬塞进普通活动字段。

## 4. 已保存状态与部署

没有结构迁移或新版本号需求。但新合同只约束新生成输出，修改提示词不会自动修复正式库里已有的无结束时间不可读状态。

部署前先正常停止HDSI并备份数据库及必要附属文件；确认没有未完成轮。读取当时活动与未读计数，留下脱敏报告。如果现场仍为这次已查明的普通文献整理、`phoneAccess=false`且结束时间为null，可按已确认的场景规则仅将该活动的 `phoneAccess`改为true，保持描述、开始时间、经历、情绪、体力、睡眠与自主推进时间不变。

在同一事务内，使用 `Storage.unreadMessages()`查询普通未读消息，为它们复用或建立现有 `check_messages`任务，`checkReason=unread`，时间为修正时刻之后1秒，`messageIds`引用这些未读消息。该查询排除开放合批和活动专属输入，不另写全表seenTurnId筛选。不能只改查看资格却遗漏唤醒；不能直接把消息标已读，也不能自行生成回复。重启后仍由正常主叙事及个人导演处理。

上述是针对明确现场的停服修正，实施时将脚本及报告放入本批记录，不新增通用迁移命令或描述关键词修复器。若现场已经变化，重新核对其实际约束：合法状态无需修改；无法确认的旧状态不批量改为可读，保留并报告，等正常合法唤醒使用新合同更新。不得覆盖正在处理的轮。

已完成历史轮、经历和记忆不重写；已尝试发送的旧冻结结果沿用现有恢复合同，不为新规则撤回已发内容。测试中的故意旧状态用于兼容性测试可保留，作为新模型正常输出的fixture则必须符合新合同。
