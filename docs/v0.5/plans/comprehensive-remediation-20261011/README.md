**Goal:** 依次关闭综合审核的 5 项代码问题和文档差异，落实保持业务合同的高收益性能改进，并交付独立的检索质量评估与候选标定。

**Tech Stack:** 仓库现有 TypeScript、Node.js `>=22.13.0`、node:sqlite、Vitest、tsx、Koishi／Puppeteer；不新增运行依赖。

**Spec:** [综合审核入口](../../reviews/comprehensive-audit-20261011/README.md)、[当前版本文档](../../README.md)、[文档目录原则](../../../DIRECTORY_POLICY.md)。审核及方案源码基线为 `ce7e88e9c8e4940ec17ae4b5dae2392fd6ddb57c`。

## Global Constraints

- 开始前记录 `git rev-parse HEAD`、`git status --short` 和与上述基线的源码差异；本轮已有未提交审核／方案／导航文件，不能 reset、覆盖或混入无关代码提交。若使用新 worktree，先确保本实施包及原审核在该执行目录可读。
- 默认在 `codex/` 执行分支逐项提交；每次只暂存该任务明确的文件。分项共享 `app.ts`、`organize.ts`、环境文件、网页 store／client、根 README，遵守下表顺序，不让多个工作者同时改同一文件。
- 不更改网页 20／40 额度、正文完整性、记忆容量与保护、后台一个工作单元、前台优先级、四段上下文、图片版本与未完成任务恢复合同。
- 预约 create at=NOW 继续合法；暂停继续允许已开始整轮完成。R1 显式裁决已消费预约的再次执行条件，R2 仅补选择结束后的暂停检查。
- 保留默认 lexical.fact=1、lexical.experience=1、semantic=null。Q2/Q3 输出候选，不自动写正式配置；“未找到更好参数”可以是合格评估结论。
- 本计划覆盖正常业务、性能与处理流程，不扩展成安全加固、任意损坏输入处理、框架重写或新的线上产品功能。
- 所有实现证据统一保存到 `docs/v0.5/records/comprehensive-remediation-20261011/evidence/`；本目录的 `evidence/plan-verification.json` 仅证明方案文档校验，不证明产品通过。原审核证据和历史交付不改写。
- 类型／编译／测试加载路径以 DELIVERY 的 V0/V1 为准，构建输出隔离，不用 `npm run build` 覆盖当前部署 `lib/`。不为编写或执行离线测试读取私有正式配置／数据库。

## 默认执行顺序与交付批次

### 批次 A：先修确定错误，形成可独立交付的版本

1. V0：让 smoke 和只读运行检查明确使用隔离编译目录。
2. R1 → R2：预约投影与暂停窗口。
3. W1 → W2 → W3：文本、图库装配、DOM 子树。
4. DELIVERY D1 的现有能力部分：D2/D3、图库命令、提取器版本；新增迁移参数尚未实现时不先写成当前能力。
5. V1、相关 V2、V4：一次批次工程验收及独立复核，留下 batch-a 记录。

批次 A 不依赖存量迁移、检索标定或性能重构，可以先交付。R2 是 API 层确定性修复，不将它写成已证实线上 QQ 命令窗口。

### 批次 B：按收益减少重复工作，保留行为

默认采用以下串行顺序，SOL 无需临时重新分组：

| 顺序 | 任务 | 本段结束时必须满足 |
| --- | --- | --- |
| 1 | W4 | 控制查询不解析正文，旧存储格式保持；可独立交付 |
| 2 | W5.1 → W5.2 → W5.3 | v2 新写、v1 兼容读、显式迁移、回退说明与成本验收成套通过 |
| 3 | R3 | 任务调度 pending 工作集、写后失效及同 epoch 顺序通过 |
| 4 | M1-A → M1-B → M1-C | 元数据、容量、排序、清理分别通过；不改业务生命周期 |
| 5 | M2-A → M2-B → M-D | 向量门禁、冻结兼容、两条记忆优化线统一实测 |
| 6 | R4a → R4b → W7 | 环境摘要、旧载荷工具、异步网页收尾联合通过 |
| 7 | W6 | 图片读取／编码复用及取消／恢复通过 |
| 8 | D1 剩余文档 → V1/V2/V3/V4 | 完整批次 B 验收、恢复矩阵、前后实测与关闭记录 |

关键技术依赖为 R1→W4、V0→R4a、R4a→R4b、R4a→W7、M1-A→M1-B→M1-C、M2-A→M2-B；其余串行排序主要用于减少共享文件冲突。允许分派独立的只读复核和测试夹具设计；不要为并行度拆开必须原子验证的接口改动。

W5.1 单个 commit 可以离线审阅，但 W5.2 的迁移与回退资料未就绪前不作为可发布完成。R4a 与 W7 之间不建立循环依赖：先交付独立的同步正文压缩，再统一异步 owner 收尾。

### 批次 C：质量评估，先证据后参数

1. Q1：数据与评估器，分组防泄漏、来源和权限合法；独立检查并冻结数据，仅看 development/calibration 基线。
2. Q2：只用 calibration 选词法候选，再对同一 holdout 一次比较 baseline/candidate。交付候选或保持当前参数的原因。
3. Q3：完成离线向量采集／回放工具及测试。实际供应商采集和效果结论依赖后续明确在线执行；若在 Q2 之后新增实验，使用另一个未查看的 holdout。
4. 交付工具、数据、报告和当前启用状态；不让“已写标定文件”代替真实效果验收。

Q3 在线实验未执行不会阻塞 A/B 或 Q1/Q2 的离线交付。未经在线采集和盲测，不关闭“语义质量已验证”这一状态；没有达到质量门槛就保持默认。

## 核心裁决与格式兼容

| 边界 | 本批明确选择 |
| --- | --- |
| 已消费预约 update | 只有显式不同 epoch 且晚于冻结 turn.at 才重新 pending；说明文字／同刻／过去修改仍 completed，cancel 优先 |
| 图库 import／rebuild | import 保留文档约定的搜索能力，独立 browser runtime；rebuild 只需 Embedding |
| 网页正文 | browser 给纯文本；材料完整保存；操作和 checkpoint 新写 ID 引用，不切短模型上下文 |
| 环境新摘要 | 仅 preparationVersion1 的 committed/superseded，且同 step 无在途 execution；v0/缺字段与未完成载荷保留 |
| 历史压缩 | `memory:compact-payloads --include-environment` 明确选择环境；默认范围不扩大；网页 v1→v2 用单独工具 |
| 记忆向量 | current 按实际 query gate；冻结按与 query 无关的能力 gate；旧配置摘要算法保持 |
| 质量启用 | 候选、线上验证、正式配置启用分开；方案不预先认定任何较低阈值有效 |

新代码必须读旧 v1 网页格式及旧环境快照，不要求启动先迁移。新写 v2 或压缩终态载荷后，旧二进制可能无法继续工作；不能用“新增可选字段”推导无损代码回退。后续正式部署前保存代码／构建和完整 DB/WAL/SHM 备份；成套回退会舍弃备份后的新增业务，详见 DELIVERY V4。逻辑载荷减小也不承诺 SQLite 文件立即缩小，本批不跑 VACUUM。
