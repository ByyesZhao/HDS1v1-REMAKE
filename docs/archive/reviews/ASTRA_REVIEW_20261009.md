## 3. 业务逻辑缺陷

### F1：新活动开始时覆盖上一场活动的未读消息身份

**根因位置：** `src/host/shared.ts:91` 选择全部“未看且有普通批次”的输入；`:93` 无条件把它们的 `sharedActivityId` 改成新活动。旧活动结束时，`:105–110` 则会将未读输入放进普通批次，并正确保留旧活动ID。这两条正常流程组合后出现冲突。

**可正常发生的顺序：**

1. 活动A末轮正在发送，收到一条未被本轮选中的A动作消息。
2. 结束标记已确认，基础记忆提取尚未完成。用户发来“现在一起开始拼图吧”，进入普通批次B1。
3. 16秒后用户又发一条，B1已经就绪，创建B2。A后处理完成时，把A遗留输入并入B2，保留A身份。
4. 下一轮只处理较早的B1，并合法开始活动B。开始提交时，全部带批次的未读消息被一并转移，B2中的A遗留输入也被改成B身份。

**后果：** 历史活动归属被改写，旧活动的动作可能作为新场活动的当前输入参与推进。共同活动文档§1、§7及恢复文档§5明确要求结束前收到的内容保留原活动身份，故这是实现与现行规则的直接冲突。

**证据：** [shared.test.ts](evidence/shared.test.ts) 贯通输入、发送确认、后处理、调度和下一场开始。所有批次前置断言通过，最后期望 `activity-a`，实际为新活动UUID；root归档后独立复跑仍失败。

**改进方向：** 转移需区分普通未读输入与已有活动身份的遗留输入。还要根据转移后剩余消息维护普通批次；不能只收窄筛选，却仍按整批删除 `pendingBatchIds`，否则留下的旧场消息可能失去调度入口。

**修复验收：** 上述交错下A身份不变，普通批次中的剩余消息仍能首次可见；B仅获得符合其归属规则的输入，普通窗口继续排除A遗留内容。

### F2：当前V1通知流程使已知安排的个人提醒无法发布

**根因位置：** `src/school/notices.ts:11` 对 `personal_reminder` 要求通知中的每个快照均已有知识记录。`src/school/calendar.ts:171` 的V1提醒同时包含 `plan_item` 和 `instance`，而首次下发通常仅包含 `plan_item`。`src/school/progress.ts:24`、`:51` 只提交真正读到的快照，本身是合理的。

**触发：** 合法事项显式配置个人提醒，例如班会提前120分钟；角色已读载有明确日期和时间的首次通知。到提醒时间，角色清醒且可读，但还没有程序展开的实例ID对应知识。默认机构提醒不受此问题影响。

**后果：** 提醒一直为 `scheduled`，实际选择结果为空，`schoolNotificationEligible=false`、`schoolNoticeDeadline=null`。除非另一条机构通知提前提供该实例，否则这条个人提醒没有正常唤醒入口；通常到现场获知时已经错过提醒。问题不是要提醒未知事项，而是角色知道的安排被内部实例身份额外挡住。

**证据：** [school.test.ts](evidence/school.test.ts) 第一项使用生产 `runEnvironmentStep` 的V1输入和提交，再通过 `prepareSchoolCommits`／`applySchoolCommits` 实际登记读取，最后检查发布、选择及截止时间。现有学校夹具 `tests/world-school-fixture.ts:10` 使用旧V0展开，未覆盖这个正向组合。

**改进方向：** 明确已知计划版本能够覆盖哪些派生课次；时间和版本匹配时，可以基于已知安排提醒，或在实际读取含具体课次事实的通知时建立相应知识。保留“个人提醒不得绕过安排版本知情资格”的原规则；机构提醒仍可合法告知此前未知的安排。

**修复验收：** 已读V1明确安排的个人提醒正常到期；未读事项、未读更正及已经取消／过期实例仍不误触发。

### F3：观察旧课次会把已读的新课程安排回退

**根因位置：** `src/school/progress.ts:31` 在现场获知时，除课次事实外还无条件附上历史实例的 `sourceSnapshot`，作为持续计划知识。`src/school/calendar.ts:14` 按获知时间覆盖同实体快照；`src/school/context.ts:17` 合并本轮获知时也直接覆盖。

**触发：** 09:00–11:00的课次已开始；09:15课程计划更正未来课次的教室，当前课次合理地保留V1历史。角色09:20读到V2更正，09:30又现场获知正在进行的旧课次。

**后果：** 09:30的现场记录将计划知识从V2退回V1，复现中地点从“下次起用新教室”回到“学院”。本轮个人阶段和正式提交后的知识投影都受影响。更正通知已经读过，不会自动重发来恢复V2。

**证据：** [school.test.ts](evidence/school.test.ts) 第二项经V1展开、计划更正、通知发布／读取，再提交现场获知，确认知识版本由2变成1。没有直接写入矛盾的知识表。

**改进方向：** 分开处理“本次课的历史事实”和“持续计划的最新已知版本”。即时上下文合并与已提交知识投影应遵守同一版本选择规则。只能从角色确实获知的版本中选择，不能直接取客观库最新版。

**修复验收：** 能同时记住当前课次仍在旧教室、未来课次已更正到新教室；没有读过更正时仍保留旧认知。

### F4：晋升为稳定认识后，原事件的具体事实无法按原关键词回忆

**根因位置：** `src/memory/lifecycle.ts:149–150` 创建概括性 `stable_understanding` 后，把主长期改为 `durable`；`src/memory/store.ts:127` 从检索候选中排除该长期。初始新认识未带 `projectionBasis`，即使后续同步补上，`src/memory/retrieval.ts:44` 的词法打分也不搜索其中的事件依据。

**触发：** 主事件“考试后在北门捡到蓝色钢笔”已有30个不同日期的有效唤醒，和另一件考试经历形成按相关性提供的稳定认识（`alwaysInclude=false`）。“每次考试后都会仔细整理文具”的结论及主题没有保留“蓝色钢笔”等事件独有词，原短期已不在有效窗口。用户问“还记得蓝色钢笔”。

**后果：** 晋升前该查询命中主长期，晋升后原长期和稳定认识都不命中。依据仍在数据库，属于检索入口缺失，不是物理删除。换成结论本身的词可能查到认识，但不能替代按原事件事实回忆。这与已披露的语义召回关闭不同：同一查询原本能够通过词法命中，晋升后该路径消失。

**证据：** [memory.test.ts](evidence/memory.test.ts) 第一项实际累计30个日期，再晋升并对照同一查询；额外同步依据后仍无法词法召回。查询已申请归档范围，扩大为归档并不能解决候选排除。

**改进方向：** 为稳定结论保留独立可检索的规范事件，或在晋升时建立事件依据投影，并让词法及向量索引使用一致的依据文本。应同时考虑事件与结论的去重呈现；仅开启语义检索不能消除这个数据建模缺口。

**修复验收：** 晋升前后按事件独有事实都可回忆，按抽象认识也可查询；依据更新后两条路径保持一致，普通长期容量不把常驻依据误算回普通池。

## 4. 性能与处理流程

### F5：后台对已经过时的输入仍先计算，再丢弃

**深度整理：** `src/memory/maintenance.ts:85–89` 在检查空闲资格前调用 `ensureCycle`，`:78–79` 已冻结、预留完整快照。故事刚结束时虽不会调用深度模型，却已形成待处理任务；等待15分钟期间事件继续更新，真正开始准备时仍用旧快照。旧版本直到应用阶段才被判为过时。

合成时间线实测：第0分钟 `startOne=false` 但已有任务；第5分钟更新同一事件；第20分钟首次调用仍收到旧内容，应用结果为 `stale`；随后第二次调用才收到新内容并 `applied`。一次有效整理消耗两次模型调用。

**索引：** 同类问题也发生在多个revision排队时。`:89` 选择索引任务只核对配置签名，`:101` 直接编码旧版本。内存夹具中revision1和2已同时排队、当前已为2，仍先编码1并废弃，再编码2；一次有效索引消耗两次Embedding。

**判断：** 现有应用门禁阻止了错误覆盖，不应报告为数据污染或“15分钟之前调用了深度模型”。这是可以明确节省请求和后台槽占用的流程优化。

**改进方向：** 深度整理在满足空闲资格时再冻结快照，或在发起请求前刷新已过时的待处理任务；索引按同owner合并待处理revision。保留请求发出后更新所需的应用版本核对。证据为 [memory.test.ts](evidence/memory.test.ts) 后两项。

### F6：每条输入前重复同步读取全部历史，成本随运行积累增长

`src/host/runtime.ts:27` 每次接收输入前调用完整 `checkWindowConsistency`。`src/dialogue/window-consistency.ts:7` 先读取消息、轮次、对话段；`:15` 又为五个阶段分别调用 `chat.recent`。`src/dialogue/chat-episodes.ts:43–45` 每次重新读取、解析、排序完整消息及对话段，最后才选四段。这五次调用实际只有普通主叙事与其余阶段两类读取资格。

在同一台机器、Node v24.21.0、内存SQLite、合成消息和已完成轮次中，一次检查解码消息表和普通段表各 **6遍**：

| 历史消息／轮次数量 | 消息JSON解码行数／次 | 单次检查中位耗时，5次样本 |
| --- | --- | --- |
| 1,000／1,000 | 6,000 | 18.03 ms |
| 10,000／10,000 | 60,000 | 173.22 ms |
| 50,000／50,000 | 300,000 | 903.70 ms |

这些是合成夹具结果，不是正式数据库延迟。夹具的已完成轮没有完整冻结候选，且无大量学校／记忆记录；不能将数值当真实部署上限。确定的结论是：当前输入入口会同步处理与本条输入无关的完整历史，阻塞同进程事件循环；普通四段规则并没有限制这部分数据库读取成本。

**优先优化顺序：**

1. 同一次检查复用消息／段快照及两种资格视图，先去掉重复的读取和排序。
2. 完整历史检查保留给启动、显式检查或升级；日常输入采用与本次变更关联的检查，维持相同归属规则。
3. 将 `Storage.unfinishedTurn()`、`outbox(turnId)`、未读消息等热查询下推到SQLite条件查询；已有未完成轮／outbox索引目前被 `all().filter()` 绕过。
4. 再优化学校通知：`personalKnown` 对每个提醒快照重新解码整个知识表，可以在单次调度内复用Map。此子项有静态证据，未单独测量收益。

不建议通过删除故事历史、截断活动原文、缩小四段窗口来解决数据库查询问题。改为数据库时间排序时，也要保持当前对带不同时区偏移时间戳的时间先后语义。

### F7：状态命令输出完整历史网页会话，搜索关闭也持续膨胀

`src/web/store.ts:60–65` 返回所有历史会话和逐owner统计；`src/host/runtime.ts:106` 直接 `JSON.stringify` 拼入给用户的状态文本。`src/index.ts` 正式装配网页服务，`src/web/phases.ts` 即使关闭搜索也建立阶段会话；完成时压缩检查点并不删除会话统计，因此当前关闭搜索的配置也会遇到增长。

**改进方向：** 用户状态只显示搜索是否启用、当前在途阶段额度、累计汇总及少量近期失败。完整逐阶段记录保留给显式诊断，聚合尽量在SQL完成。修复后应验证1000轮后普通状态长度基本稳定，原始额度及恢复记录仍完整。

## 5. 文档与验收偏差

### F8：Koishi离线smoke的模拟协议和次数断言都已过时

README §2 推荐的 `npm run smoke --prefix runtime` 当前失败。不是简单地把预期次数从4改成3就能修好。

第一处：`runtime/plugin-smoke.cjs:20` 用 `input.stage` 分流模拟响应，而 `src/model/resource-pool.ts:39` 的实际传输结构是 `input.context`／`input.roles`，环境阶段在 `input.context.stage`。模拟器因此没有正确识别world，连续返回错误结构。当前观察到的3次HTTP是world的首次请求加两次格式修补，并非world／campus／group已经成功。

第二处：修正模拟器取值后，空计划没有必需通知，`src/environment/runtime.ts:33` 正确跳过周模型；此时四个步骤可以提交，但只有3次生成HTTP。`:30` 仍硬断言必须4次。周模型模拟返回也仍是旧V0字段，扩充到有通知场景时需同步为V1。

**验证：** 保留原文件不改，在内存编译的隔离副本中只修阶段路径，仍因次数断言失败；同时修阶段路径和次数预期后，原脚本后续的四个提交步骤、两套计划及插件初始化断言通过。见 [smoke-probe.cjs](evidence/smoke-probe.cjs)。

**改进方向：** 按实际环境批次终态等待，不将HTTP次数当作完成信号；分别检查“空周免模型”和“有通知调用V1周模型”。将smoke纳入日常协议变更后的离线验收，而不只依赖现有Vitest套件。

文档保留的旧批次通过记录是历史证据，且已经注明不代表本轮重跑，这一点没有问题。需要修的是当前可执行验收工具，不能为让报告变绿而删除检查。

### D1：错过提醒的说明缺少已保存提醒的例外

导演与环境§5写“错过的旧提醒不集中补发”。代码及 `tests/world-school-review14-calendar.test.ts` 的 `already_committed_reminders_keep_delayed_publication_and_replay_state` 区分了两种情况：

- 展开／恢复时尚未提交且已错过时点的提醒不补建。
- 已经保存的提醒可以延迟发布；只要课次尚未开始，11:00和12:00的两个提醒可以在12:30一起成为 `available`。

建议把这个例外补入当前文档。是否进一步合并积压提醒属于产品规则选择，本次没有把既有明确测试确认的行为直接判成代码错误。

## 6. 后续实施建议

先解决F1–F4的身份、知识版本和检索连续性，防止正常运行形成错误关联或认知；F7、F8可独立处理。随后优化F5、F6，优先减少已经知道无效的外部请求和重复历史读取，收益比增加另一层模型判断更直接。

测试改进应围绕模块交界建立端到端夹具：生产V1通知生成到知识资格、结束输出到慢后处理再到新活动、晋升前后同一查询、后台排队到实际开始之间的更新。尽量复用生产输入／提交路径，避免旧合同夹具或手工插表恰好绕开新行为。

本次发现不要求重写主调度、改人物设定、引入额外模型或缩减已确认的上下文规则。各条建议以保持现有业务语义为目标；尚未取得在线证据的模型叙事质量、真实QQ行为和数月运行稳定性，继续保留原验收边界。
