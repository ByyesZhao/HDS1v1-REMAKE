## 3. 四项业务问题的核验及边界

### F1：新活动改写旧活动未读消息归属——成立

`src/host/shared.ts:105–111` 在活动结束后为遗留未读输入建立普通批次，保留旧活动 ID；`:91–95` 在下一活动开始时却迁移全部带批次的未读输入，无条件写入新活动 ID。旧输入因此可能参与新活动。

这条时间线在生产路径可达：Host 等待发送／记忆请求时仍可接收输入；结束标记确认后进入普通批次；较早批次先启动新活动，旧活动遗留输入所在的较晚批次尚未处理。正式一致性门禁也未阻挡这种合法过渡。

[活动证据](evidence/shared.test.ts) 使用生产 InputBuffer、Scheduler 和 App。夹具仅建立合法活动起点及固定模型结果，不是通过直接伪造消息归属制造问题；但它没有运行完整 SerialHost 端到端，后续可补该覆盖。

修复必须同时保持：

- 只迁移真正普通的未读输入；已有活动 ID 的消息保持原身份。
- 根据迁移后的未读残留维护 pending/open 批次及其就绪时间，不能因迁移其中一条就删除整批。
- 新活动的时间锚点与原文只使用真正归属新活动的输入。
- 旧活动遗留输入后续仍有普通批次主动唤醒入口，但不计入普通四段容量，不进入新活动全文。
- 提交与恢复遵守同一事务及幂等规则。

“仅收窄筛选却删除整批”会丢掉残留消息的普通批次主动唤醒及既定顺序／就绪时间；它不必然造成永久不可见，因为其他前台触发或自主轮仍可能捎带读取。ASTRA 没有声称消息被物理删除，无需为此反驳其结论。

### F2：已读安排仍无法触发个人提醒——成立，范围有限

`src/school/calendar.ts:171` 的 V1 首次下发通常包含 `plan_item`，提醒则包含 `plan_item` 和 `instance`。实际读取只登记收到的快照，`src/school/notices.ts:11` 却要求个人提醒的每个实体快照都已经以相同公开版本获知。因此角色知道明确安排，仍可能被程序派生实例身份挡住。

[学校证据](evidence/school.test.ts) 第一项贯通 V1 环境输出／提交、读取登记、发布、选择及截止时间。问题限于显式 `personal_reminder` 且尚未从其他通知或现场取得对应实例知识的路径；默认机构提醒不受影响，不是所有个人提醒都失败。

修复应允许已知安排在身份、公开版本和具体时间／周时段匹配时覆盖可确定推导的课次。不能删除全部知情门禁，不能从客观最新版补出角色尚未读到的知识。仍要挡住未知安排、未读更正、取消和失效实例。

版本校验应区分整条记录 `revision` 与公开变化 `deliveryRevision`；只更新内部备注不能让原本已知的公开安排再次失去提醒资格。

### F3：旧课次现场记录覆盖已读新安排——成立

已开始课次保留历史快照本身合理。问题在 `src/school/progress.ts:31` 将旧课次的 `sourceSnapshot` 再次登记为持续计划知识，而 `src/school/calendar.ts:14` 按较晚获知时间覆盖；`src/school/context.ts:17` 的本轮合并也直接覆盖。

[学校证据](evidence/school.test.ts) 第二项先实际读到 V2 更正，再现场获知 V1 课次，确认已提交知识回退为 V1。即时个人上下文回退也有源码依据，现证据未单列该字段断言，修复时应补本轮与提交后两处检查。

修复应同时保留“当前课次的历史事实”和“持续计划中确实已知的较新版本”，两处知识合并共用选择规则。不能改写旧课次历史，不能直接取客观库最新版来代替知情资格。既有细化中仅按获知时间选版本的说明也应同步澄清。

### F4：稳定认识晋升后具体事件失去检索入口——成立，不是删除

`src/memory/lifecycle.ts:145–150` 晋升后把原主长期设为 `durable`，新稳定认识可以是抽象总结且 `alwaysInclude=false`；`src/memory/store.ts:127` 排除原长期候选。初始认识没有 `projectionBasis`，后续同步即使补上依据，`src/memory/retrieval.ts:44` 的词法文本仍不包含依据。

[记忆证据](evidence/memory.test.ts) 第一项用 30 个真实模拟日期的有效唤醒达到晋升条件，对照晋升前后同一具体事实查询，并额外同步依据，仍能复现入口消失。

这里的“具体细节”指原事件中的独有事实，不是整个 `details` 表被删除，也不是所有晋升都无法回忆。原事件仍在库中；抽象结论的词可能命中新认识，`alwaysInclude=true` 还可能直接进入上下文，但不能替代按事件事实检索的能力。语义召回尚未启用不能解释晋升前可词法命中、晋升后不能的变化。

修复需保证规范事件依据与抽象结论都可按相关性召回，词法及向量索引使用相符的依据内容，并按 canonical 身份避免重复呈现。不要只取消 `durable` 候选排除而造成长期／认识重复，不要将所有认识改为 alwaysInclude，也不要把常驻依据重新计入普通长期容量。召回修复不应额外增加有效唤醒或刷新保留时间。

## 5. 后续修复建议

可以在同一轮局部修复中处理，无需重写主架构或增加语义裁判模型。建议先恢复 F8 的离线验收能力，为后续提交提供可运行门禁；再修 F1～F4 并补模块交界的失败回归，同步 D1 及 F3 的版本口径；F7 可独立处理；最后优化 F5、F6 并重新采样。

验收重点应是旧活动遗留输入遇到新 start、生产 V1 下发到个人提醒、旧现场与已读更正并存、晋升前后同一事件查询、排队到发请求期间的更新，而不只是原有单模块测试继续通过。修复后再跑完整回归和当前 smoke，分别记录测试夹具、真实模型及正式运行的证据边界。

本文件仅确认问题与修复边界，**尚未实施上述修复**；当前子系统文档也未据此假定缺陷已修好。
