# 当前代码与 V0.5 文档独立审核（2026-10-09）

## 结论

当前 V0.5 的主体说明与实现基本对应。普通四段、活动独立原文、冻结发送、记忆生命周期、学校知情版本和后台 checkpoint 的主要实现都有相应代码与回归依据；未发现需要推翻总体设计的证据。但现有测试全通过并不等于没有遗漏：本次另行复现了 **2 个代码问题**，其中一个会改写旧事件的时间事实，另一个使显式配置的后台字符批量限制失效。

提升收益最大的方向是减少日常路径对历史数据的重复读取／重写。先优化这些确定的程序成本，再考虑把环境模型准备移出前台串行槽；无需增加模型、缩小四段窗口或裁剪活动全文。

本次仅新增本目录的审核文档、独立复现与日志，未修复产品代码，未改写原有文档或正式配置。

## 2. 需要修复的代码问题

优先级含义：P1 为应优先处理的广泛功能阻断，P2 为应修复的局部行为错误，P3 为文档澄清。本次未确认 P0/P1 问题。

### B1 · P2：重谈旧事件时，省略可选日期会扩展旧事件时间范围

位置：[src/memory/lifecycle.ts](../../../../src/memory/lifecycle.ts) 第 28、36 行；日期最终通过 [context-views.ts](../../../../src/model/context-views.ts) 第 12–13 行进入模型资料。

正常触发路径：基础记忆结果创建一个短期，引用已有 `existingLongId`，明确 `hasNewEventProgress=false`，并合法省略可选的 `happenedAt/happenedUntil`。创建短期时程序把日期默认成当前整理时间，随后无条件与旧长期执行 `eventRange([long, short])`。

复现：原事件为 **10 月 1 日参加考试**，10 月 9 日只是重新谈起。结果 `happenedUntil` 从 10 月 1 日变成 10 月 9 日；该长期被召回时，其个人导演输入投影包含这段错误日期范围。`lastEventUpdateAt`、原长期期限仍保持旧值，故这不是此前 REVIEW26 已修复的“重谈续期”问题，而是仍然存在的**事件日期事实污染**。独立交叉补验覆盖了检索→个人输入投影，未调用实际个人模型，见 [memory-crosscheck.json](dialogue/memory-crosscheck.json)。

建议：引用已有事件且没有提供新的、有来源的事件日期时，继承该事件日期；不要把整理时刻隐式并入它。新事件、真实新进展、明确补充／纠正日期应分别处理。补回归覆盖 create＋existingLongId＋false＋省略日期，并检查实际模型投影，而不只检查保留期限。

### B2 · P2：`memory.batchCharacters` 在实际增量维护路径中不生效

位置：[src/memory/maintenance.ts](../../../../src/memory/maintenance.ts) 第 59–90 行；[memory-runtime.ts](../../../../src/deployment/memory-runtime.ts) 为生产装配提供 `idle`。

旧扫描分支会累计 `batchCharacters`，但实际带 `idle` 的装配进入 `ensureIncremental`，主选集合仅按 `batchItems` 截取。复现设置字符限制 150，三个互不依赖、各 120 字的长期记录仍同时入选，共 360 字；不存在依赖闭包不得拆分的例外。

默认值为 `null`，因此不影响默认无限制配置；显式设置这个配置的人会得到与文档／配置含义不同的请求批量，增加准备时间、费用或撞到模型容量的可能。

建议：在实际增量路径选主项时应用条数和字符限制，再完整扩展依赖闭包；明确首个单项超限时的既有容许语义。不要用硬截正文解决。补充通过生产装配或带 `idle` 的维护入口验证该配置的测试。

两个问题的完整依据、复现与建议见 [记忆专项](MEMORY_REVIEW.md)；数据见 [memory/reproduction-results.json](memory/reproduction-results.json)。

### D1 · P3：根 README 的“最新验收”落后于 V0.5 索引

[根 README](../../../../README.md) 第 11 行仍将 REVIEW26 的 107 文件／620 项称为最新；第 143 行“最近实现证据”仍导向活动窗口早期交付。V0.5 索引已经说明后续 ASTRA 和 R1 的 122／693。旧数字作为批次历史本身正确，问题是“最新／最近”的标签。

建议只更新入口摘要和最近交付链接，保留各旧批次记录的原始含义，不把所有历史数字统一替换成本次数字。

### D2 · P3：“非主证据不因此永久保留”容易误读

[记忆文档](../../../v0.5/subsystems/REMAKE_V0.5_MEMORY.md) 第 65 行的说法，容易被理解为非主证据到期后照常物理删除。实际 `protectedCanonicalIds` 会保护有效 learned 的主事件及所有 `evidenceMemoryIds`；只要仍被有效常驻引用，它们不会被归档清理删除。非主证据不自动变成 `durable`，但“退出当前检索”和“物理删除”是两件事。

建议改为：“非主证据不自动晋升 durable，仍按普通期限退出当前检索；有效常驻引用期间保留必要身份与摘要。”这也与同篇关于有效常驻证据受保护的段落一致。没有建议为了配合一句文案而删除依据。

## 4. 高收益改进顺序

以下均为性能／处理流程建议，不是安全或防御性扩展。合成规模不代表正式数据库现状；各项耗时不能相加当作一次真实请求的总延迟。

| 顺序 | 改进 | 依据与预期收益 | 实施边界 |
| --- | --- | --- | --- |
| 1 | 普通原文先 SQL 选最近有效段；记忆提取不读取随后丢弃的 recent；不运行个人阶段时延迟构造其专用上下文 | 每个普通轮可消除多次历史消息／段全扫，收益随历史增加；影响每轮常用路径 | 保留完整四段、稳定时间排序、未读资格、旧版本恢复和活动全文 |
| 2 | 学校／环境调度用当前有效集合查询与同次快照 | 日常 deadline、就绪扫描仍反复解码已完成环境步骤和历史学校资料；只需安排下次运行时不应读取完整模型输入和结果 | 保留知情旧版本和历史证据；不能用只取最新安排替代角色实际已知信息 |
| 3 | 已完成维护 payload 只压缩一次，清理单元只处理相关任务 | 当前每删一条记忆会重复重写全部历史 done 维护任务，存在可消除的写放大 | 不删除恢复需要的 pending/computing/ready 数据，不回退 R1 修复 |
| 4 | 用 Set／Map 维护模型资料池去重索引 | `ResourcePool` 的逐次 `some` 在大资料池中二次增长；改动较小 | 保持首次加入顺序、原 ref／ID、跨角色只存一份正文的规则 |
| 5 | 环境模型异步准备、保存 ready 后择机提交 | 消除“新消息恰好到达环境 HTTP 请求中途”的剩余等待，改善交互尾延迟 | 中高工作量；必须维护四步依赖、冻结依据、跨日失效与前台提交一致性 |

前三项已有直接量化：

- **普通窗口**：固定只需当前普通窗口时，5 万历史段的合成普通轮仍三次扫描 messages 和 chat_episodes，测得约 484 ms；单独基础记忆上下文构建约 144 ms，读取的 recent 最终被丢弃。见 [上下文专项](DIALOGUE_REVIEW.md)。
- **环境调度**：合成 90 个历史日批次、360 个历史步骤，步骤 JSON 共约 30 MB。当前有一个 active 批次时，一次 `environmentDeadline` 仍四次读取全部步骤，解码 1456 行；5 个热样本中位约 430 ms。不是声称真实运行 90 天必然达到该体积，而是显示已保存大快照不应进入轻量计时查询。见 [调度专项](SCHEDULING_REVIEW.md)。
- **清理写放大**：5000 个历史 done 任务、清理 10 条记录，触发 50000 次 done job 重写，内存库测得约 1.12 秒；无历史任务约 7 ms。这里测的是同步本地程序成本，未加入正式文件库的磁盘同步成本。见 [记忆专项](MEMORY_REVIEW.md)。

环境异步准备应作为独立流程改造，不能简化为对整个 `runTurn` 加 `Promise.all`。当前“已有环境请求不被抢占”已写进文档，而且现有测试明确覆盖等待后再优先聊天；这是产品响应改善，不能反过来列成违约 BUG。
