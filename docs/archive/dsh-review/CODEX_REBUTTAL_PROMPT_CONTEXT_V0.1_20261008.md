## 2. 超限策略已由用户确定，不需要重新选择

用户此前明确选择：**“不自动移除，保留报错处理”**。因此 REVIEW20 §2.1 的 A/B 二选一已有答案：接受接口容量限制及报错，不引入自动减少旧段数的降级，更不截断当前段。默认4段和段内完整原文的方案保持。

### 2.1 采纳可观测性要求，但修正当前表现

当前故事执行链的行为可在 [`app.ts`](../../../src/app.ts)、[`client.ts`](../../../src/model/client.ts)、[`index.ts`](../../../src/index.ts)及 [`runtime.ts`](../../../src/host/runtime.ts)核对：

1. 接口错误保留任务名、HTTP状态和供应商返回的错误码／消息，抛出 `ModelRequestError`。
2. 故事执行失败后保存 `Runtime.lastError`，设置 `paused=true`，保留未完成轮。
3. 发送层尝试给用户发送字面量 `error`，日志记录异常；该错误通知发送失败也不会丢失原失败现场。
4. `hdsi.status`能显示暂停和当前阶段，目前没有直接展示故事的 `Runtime.lastError`；其中的“后台错误”属于记忆维护，不能混为同一错误。

所以“用户侧没有任何输出”需要限定为**生成失败时没有该轮的新剧情／角色回复**，而不是没有错误通知。若失败发生在已发送剧情之后的记忆提取阶段，之前确认的公开输出也不会消失。

建议实施细化增加一项小范围可观测性改进：让状态／错误提示区分上下文容量错误与普通请求失败，指出失败任务及阶段；未知供应商错误保持普通失败，不假定所有HTTP错误都意味着超限。不得在诊断里打印请求正文、角色背景、聊天、记忆或密钥。这里是待实施建议，不是已经具备的功能。

### 2.2 不采纳“等待15分钟后即可继续”作为恢复保证

当前暂停不会因时间经过而自动解除；新输入可以落库，但未完成轮必须先处理。`hdsi.resume`尝试恢复原轮，不保证原请求会变小，也不跳过未完成轮。相关生成／发送仍在途时，方案本身还要求保持原对话段。

即使某个段正常关闭，完整原文仍可能处于最近4段窗口内；关段也不等于删除它的上下文。因此不能把等待15分钟写成可靠的超限恢复操作。

正确口径：保留错误和未完成现场，不自动删减／摘要／跳轮；人工核实接口容量及实际配置，明确处理导致超限的条件后再恢复。若条件没有改变，恢复可能再次报错。用户在后续回复中进一步确认“真有问题报错就行”，本期不增加强制关段、清空当前段或其他脱困命令，也不承诺所有超限现场都能通过现有命令恢复。细化只说明实际错误和恢复行为，不把未实现的操作写成可用办法。

应增加离线验收：容量错误导致暂停并保留未完成轮；通知可观察；等待15分钟或追加输入不会自动绕过它；恢复无静默删减；后处理失败保留已确认输出。真实模型长上下文承载能力另行验证，不能用合成HTTP错误测试代替。

## 3. 旧库回建：采纳连续性要求，补足已有证据

DSH关于确认输出时间的检查成立。除此之外，目前 [`types.ts`](../../../src/types.ts)的消息还具有可选 `sharedActivityId`：

- [`input.ts`](../../../src/host/input.ts)给共同活动中的真实输入保存活动ID。
- [`recovery.ts`](../../../src/recovery.ts)给已确认输出保存活动ID；活动开始轮即使没有 `sharedMeta`，也可以从冻结的下一状态取得ID。
- [`shared.ts`](../../../src/host/shared.ts)会给开始时转入活动的未读消息补活动归属。

因此近期已有这些字段的记录不只是无标记的时间序列。应优先使用可靠活动ID，以及关联的 turn／确认输出证据，保持同一活动跨度内的段连续；不能无视ID，仅因两条消息相隔15分钟就拆开。

但 `Runtime.sharedClock`只是当前活动时钟，活动完成后会清空；已完成 turn 的 `frozenResult`也会清空。**不能声称仅凭当前 clock 或已清空的候选，就能完整恢复所有旧活动的精确起止时刻。** 更早版本可能缺少活动ID，需检查具体记录。

建议回建规则：

1. 普通交互依可靠时间序列切段；已知同一共同活动的跨度覆盖普通静默切点。
2. 在有证据限定的候选活动跨度内，归属边界不清时可以保守合并，并在迁移报告说明依据和不确定项。
3. 不对所有缺失归属的旧记录一律跨间隔合并，否则可能把数周普通对话合成一段；也不凭猜测创建活动ID或精确结束时间。无法可靠恢复的部分保留原记录并在迁移报告列明处理口径。

采纳验收：最新真实交互在索引的最后一段内，已知同一共同活动不得跨两段；同时验证已知不同活动／普通对话不因无界合并而丢失段边界。阶段可见性投影仍需独立验证，“索引最新”不意味着普通主叙事可以看到未读新消息。

## 4. `【推进】`：明确不刷新对话段的真实交互锚点

REVIEW20 §2.3 所举“推进之后15分钟就会关段”的前提不成立：方案 §7.5 明确规定共同活动从确认开始到实际结束保持连续，活动未结束时不能因无消息15分钟关段；结束后至少再等15分钟。

建议沿原方案补一句明确规则：**`【推进】`只改变推进控制，不开启对话段、不刷新对话段的真实交互锚点、不进入原文或记忆事实。**

| 情况 | 对话段处理 |
| --- | --- |
| 活动中发送有效 `【推进】`，本轮没有公开输出 | 活动连续规则保持原段；控制请求本身不刷新真实交互锚点 |
| 推进后确有公开输出 | 按输出的实际确认时间刷新 |
| 共同活动实际结束 | 从最后真实交互与实际结束时刻的较晚者再等15分钟 |
| 没有共同活动时发送 `【推进】` | 不开启／延长对话段；“当前没有共同活动”是系统通知，不是角色对话 |

现有 `MemoryIdle`仍会把控制接收记为 input；这服务于“刚有用户操作时不要立即深度整理”，可以保留。两套时钟的职责不同，不需要为了数值一致而扩大原文窗口。验收时分别检查这两个口径，避免把差异误判为计时错误。

## 5. 两项小注的核对

### 5.1 当前仍为 `json_object`

因此当前不能删除提示中的 Schema，并指望 `json_schema`替代它。重复 Schema 的优化仍只适用于以后明确启用且验证可用的 `json_schema`模式，不因本次 review 提前切换生产接口模式。

### 5.2 学校恢复需区分已解析结果与模型候选

采纳“旧 `ready`独立验收”。但 [`environment/runtime.ts`](../../../src/environment/runtime.ts)中，`ready.frozenResult`已经是经过 `resolveSchoolWeek`等处理的 **`EnvironmentChangeSet`**；恢复时直接提交，不再调用模型或重新解析模型候选。

所以若第二批只改模型候选合同、保留解析后变更集合同，旧 `ready`不应仅因候选合同变化就被作废。应验证直接提交、历史保护和幂等行为；若确实也改变持久化变更集合同，再明确迁移办法。

另外单独检查旧 `running`的冻结输入、网页／补查 checkpoint及尚未解析的模型结果：这些才可能仍引用旧候选字段。不得把 `ready`兼容测试当作全部恢复兼容已经覆盖。

### 8.1 超限后的人工关段命令：技术观察成立，本期不采纳功能建议

DSH指出现有 `hdsi.resume`不能保证减小请求，这一判断成立，§2.2已保留该限制。但是否提供额外操作属于产品范围选择，用户已明确不需要，因此不增加 `hdsi.segment close`，也不以其他命令名实现同类功能。

另外，“强制关段／开新段”与“把超大段移出输入”是两件事：最近窗口为4段，关闭的大段仍可能作为前3个历史段之一进入下一次请求；未完成轮也不能仅靠开新段被跳过。因此即使以后考虑该命令，也不能只改段状态就声称解决超限。需要另行定义它对窗口和未完成轮的作用，不是本期补一句命令即可解决的问题。

本期规则到报错、暂停、保留现场及显式恢复重试为止；不自动裁剪，不增加手动窗口排除、清空、跳轮功能。增加错误可观测性验收即可，无需用户再确认一次。

### 8.2 对话段持久化一致性：采纳问题，选择同事务的显式索引

这条有必要纳入实施细化。采用原方案的**持久化显式段索引**，不改成每次读取重算的缓存视图。消息仍是原文与实际交互证据，段索引固定已提交的归属和边界；升级回建是一次迁移，日常读取不重新决定历史段边界。

理由：本项目的分段还依赖在途生成／发送和共同活动连续性，仅按消息间隔和活动ID重算不足以稳定恢复所有边界。已完成 turn 的候选及活动 clock又可能清空，不能把读取时总能完整重建当成前提。现有SQLite事务已经能支持以下写入规则，不需要额外事务系统。

**落库边界：**

| 事件 | 应扩展的现有事务及原子写入内容 |
| --- | --- |
| 接收真实用户消息 | `InputBuffer.acceptInput`的事务中，一起决定旧段是否到期、新段是否建立，并保存消息、唯一段归属及真实交互锚点；任何一步失败全部回滚 |
| 接收重复平台消息 | 沿现有消息ID去重；不重复建段、不重新归属、不再次刷新计时 |
| 确认角色公开输出 | `sendFrozen`取得发送确认后的事务中，一起保存确认状态、outgoing消息、段归属及确认时间锚点；同一回复的后续分段沿用已确定的段归属 |
| 共同活动开始／结束 | 在已有确认／提交事务中同步记录活动与段的关联及真实起止证据；确认的结束时刻必须留下索引记录，不能在清空 `sharedClock`后再猜测 |
| 普通段到期关闭 | 独立的短事务内重新检查最后交互、相关生成／发送是否仍在途及活动门禁，再关闭；新输入已经刷新时不得按旧截止时间关段 |

段建立与首条原文关联同事务提交，不先持久化一个空段再另写首条消息。真实入站／确认出站消息各有且仅有一个段归属；控制请求和系统通知不是这一覆盖要求的对象。活动关联可以维持连续段，但静默推进本身不伪造消息，也不刷新真实交互锚点。

共同活动结束后的迟到消息、未读消息路由调整，应沿既有活动／消息规则处理；不能只为了修正路由重新复制原文或凭重试建立另一份归属。阶段可见性继续独立投影，归入某段不等于已被角色阅读。

**启动与恢复：**

- 旧库升级时一次性回建及核对全部需要纳入索引的历史消息，按§3证据规则处理，保存索引版本和迁移报告。
- 正常启动在接纳新输入／恢复故事之前，做一次轻量结构核对：消息归属唯一且目标段存在、当前段状态无冲突、未完成轮与发送项的段关联完整。只核对必要元数据，不复制正文，也不因重启重算历史切点。
- 恢复继续使用已提交的消息／轮／输出关联；未提交事务由SQLite回滚，重试沿消息ID和输出序号保持幂等。段的归属关联需在模型调用／分段发送前固定，具体承载字段由实施细化列明。
- 不采纳“孤立消息一律并入最近段、重叠段一律合并”的自动修复默认值。时间相邻不证明同一段；无法由已有证据可靠处理的不一致应明确报错并保留现场，不静默改变历史。合法的旧库回建和有证据的合并仍按§3执行。

**单独验收：**在入站消息＋段索引写入、出站确认＋索引写入、段关闭＋新输入竞争、活动结束＋时钟清理处模拟中断／回滚；重启和重复接纳后仍无孤立消息、无重复归属、无多余空段，同一回复与同一共同活动不被误拆。模型已发送确认而本地尚未提交的恢复仍沿现有outbox规则，不把本次索引事务误称为能保证QQ网络发送恰好一次。
