## 1. 建议先定的六处

### 1.1〈最重要〉四个串行环境步骤会把"全局暂停"的暴露概率放大数倍

细化 §4.3 写得很诚实："失败步骤不标成功，不跳过依赖继续下游；记录具体失败阶段"，并明确"是否将环境错误从全局暂停中隔离，属于后续独立改造，不冒充本次已有能力"。

但现在的实际语义是：**任何模型任务失败都会 `runtime.paused = true` 并暂停整个故事**（`app.ts` 的异常路径），环境轮也不例外。于是这条链一旦落地，每天早晨会有 **4 次连续的远程模型调用**，其中任意一次失败（配置错误、额度、超时、格式修补耗尽）都会让当天的聊天在 06:00 就停住，需要人工 `hdsi.resume`。

按单次失败率哪怕只有 2～5% 估算，四个步骤的日失败率就是 8～19%——**大约每周到每两周就会遇到一次需要人工介入的清晨暂停**，而这与方案自己的目标（"争取 07:00 前完成""不设等学校链完成才可聊天的门禁"）是矛盾的。

建议把"环境步骤失败不进入全局暂停"提到第一阶段，并且**不需要**引入完整的异步准备／短事务发布机制（那是 §4.2 提到的更重的替代方案）。最小做法是复用记忆维护已有的模式：环境步骤失败只写 `retryAt` 与后台错误记录、按退避重试、不设 `paused`；前台故事（主叙事／个人／表达／记忆整理）失败保持现有暂停语义。这一条属于"让新链可用"，不是防御性编程。

### 1.2 通知方案由哪个任务生成，没有归属

§7.1 说"模型可给特定事件选择不提醒或补充合理通知方案，程序根据结构化时间展开"，但 §3.1 的三任务表里没有一处明确**通知记录由谁产出**：

- `school_campus` 管学期计划（含考试／典礼／假期／班会）；
- `school_group` 管导师要求与组会、聚餐、游玩；
- `school_week` 管"由它展开的实例及通知方案"。

§6 又说客观固定事项（课程／组会／班会／考试／集体活动）由周导演落实为周实例。所以"通知挂在实例上"时，作者应当是周导演；但校园与课题组导演对自己拥有的一次性事项（典礼、临时改期）也有更早的信息。建议明确一句：

> 通知方案由**创建该日程实例的任务**产出（周导演为其展开的实例产出；校园／课题组在其自有的一次性事项上产出），并一律关联上游条目 ID 与版本，不靠描述文本匹配。

否则实施时容易变成四个任务各写一份通知，而 §7.1 最后一句"一天两次检查同一事件不新造两套提醒"就是靠身份去重来保证的——身份由谁生成必须先定。

### 1.3 每日批次与现有 `nextWorldAt`／`nextSchoolAt` 的关系需要写清

§2 提到要取消固定的 16:00 学校检查，但没说 `schoolTimes` 这个**配置项本身**怎么办（保留但只用于批次起点？删除？迁移时如何兼容用户已有配置？）。更需要写清的是**下一步骤的定时资格**：

- 现在环境轮的下一步截止是在段 B 用 `nextDaily(completedAt, 对应的 times, tz)` 重算的（`recovery.ts:96-97`）；
- 新的批次要求"每一步成功提交后才能选下一步"，也就是下一步的资格应当来自**批次记录**（步骤状态 + 完成时刻），而不是 `schoolTimes` 的下一个时刻。

建议写成："世界步骤仍用 `worldTimes`（默认 06:00）；学校三步的启动时刻来自当日批次记录（当前步骤完成即进入下一步），`schoolTimes` 不再直接决定环境轮时刻，迁移时把用户已配置的值作为批次启动时刻的默认。"并补一条当日批次的**未完成处理**（例如：允许在本地产日内继续；跨到次日仍未完成则显式标记为"被当日检查替代"，保留已提交步骤、不并行补跑）。

### 1.4 个人视角的过滤需要点到具体字段，`relatedEventIds` 是主要的隐藏泄漏面

§7.3 要求"个人导演不再直接取得所有尚未发布、未读的学校事件"。现在 `app.ts:96` 取全部 active 事件，然后**同一个数组**同时进了四处：个人导演输入（`app.ts:129`）、主叙事输入（`:104`）、主叙事查询串（`:98`）、主叙事合同的事件 ID 白名单（`:106`）。

要提醒两点：

1. 个人视角应当用**过滤后的数组**（已发布且已读 + 本轮主叙事实际实现获知的），不能只把未读项从提示词里删掉却仍留在 `relatedEventIds` 或检索查询里——否则未读的导师任务、未发邀请仍会经由 `relatedEventIds` 的白名单与查询串影响个人导演。
2. **主叙事仍应保留完整客观日程**（它要按客观事实实现"今天有几节课"），但它必须在没有阅读条件时不写成已经看到。这一点方案已经写了，只是要明确"完整日程只进主叙事，不进个人"。

### 1.5 没有现有故事时"由学校通知触发的轮"要落成一个具体的触发种类

§7.2 允许"没有现成故事时选择一个学校通知触发轮"，并规定"纯学校通知不视为用户发言，也不自动获得自主联系用户的抽样资格"。现在 `TriggerKind` 只有 `input | autonomous | sleep | activity | appointment | check_messages | scene_step | environment`，需要一个新种类（例如 `notification`）。

它的连带影响要在细化里逐项点名，因为现有代码有几处按种类分支：自主资格判定（`autonomousEligible`）、主动联系抽样（要求 `triggerKinds` 含 `autonomous`）、共享活动的 60 秒资格、以及段 B 的自主重排（§7.2 已确认通知阅读轮属于前台故事、成功后重排 150～210 分钟）。建议直接写成一张"通知轮与各现有判定的关系"小表，避免实施时漏掉某一处。

### 1.6 学期计划与周实例进入上下文的方式需要一句约束

§8 说明了这些记录"不受长期记忆 90 天期限支配""不新增人为预算""未来故事只选当前／相关记录"。但一个学期的计划加上跨周实例会变成几十到上百条结构化记录，而现有检索是关键词驱动的：个人导演的查询串由经历与可见消息拼成，`runRelevant` 里没有时间窗或条数上限。

建议补一条上下文约束，例如："学校计划进入上下文时按（当前时刻 ± 时间窗）与所属任务筛选，已经读过的通知不重复注入，同一实例只出现一次；不把整学期实例塞进提示词。"这不是新增预算，而是避免关键词命中把整学期的课表一次性带进来。

## 2. 三处提醒

### 2.1 研究进展的来源链要落到具体字段

§5.2 的原则完全正确（"下发导演负责要求、期限和导师反馈；只有主叙事已经实现的经历／模拟反馈才能支持进展或完成结果""周计划排出'完成实验'也不代表实验已经成功"）。实施时建议明确研究进展记录里保存的是**经历 ID 或模拟反馈 ID**（即现有 `experiences`／记忆来源体系），而不是一句由周导演或组导演自己写的摘要——否则"进展"会变成第二个可以凭空制造事实的入口，与 MEMORY V0.3 的来源门禁冲突。

### 2.2 规则型提醒与暂定日期

§7.1 写了"没有确切开始时间时只发暂定安排／确认通知，不猜'前 2 小时'的时刻"，§5.1 也要求"缺确切时刻的事项保存为暂定日期／时间范围，接近日期后由归属导演明确时刻，再落实提醒"。这两条已经覆盖了主要情形，但建议再补一句**改期后已发布提醒的失效规则**：现有一句"使旧时刻尚未读取的提醒失效，必要时生成新时刻提醒"是放在"临时改期／取消"行里的，建议提升为通用规则（任何时间变更都按"事件 ID + 版本"失效旧提醒），这样规则型提醒（课前约 1 小时）在改期后不会留下按旧时刻排的提醒。

### 2.3 学校导演的"虚构权限"与现有合同字段的关系

§5.3 说生成的模拟计划"不能反称它是某大学真实官方课表、真实导师通知或真实研究结果"，现实校历／法定假期要有可核验来源。现有环境事件合同已经有 `basis: 'fiction' | 'web_reference'` 与 `sourceUrls`，并且学校导演已经不允许在无资料时声称联网。建议明确：**模拟生成的学校计划一律 `basis = 'fiction'`**，即使它描述的是"北京"这种真实地点；只有真正引用了提供的网页资料才标 `web_reference` 并附 URL。这样 §5.3 的意图就落在了一个已有字段上，不需要新机制。

## 3. 我核对后确认成立、建议保留的设计

- **基线准确**：`config.ts:18` 的 `worldTimes: ['06:00']`、`schoolTimes: ['06:10','16:00']`；`scheduler.ts:25` 的 `due(nextWorldAt) ? 'world' : due(nextSchoolAt) ? 'school'`；`environmentKind` 目前只有两个取值；`app.ts:96` 确实把全部 active 事件同时给主叙事与个人导演。方案表格里这些判断都对。
- **"提醒由程序展开、不靠导演频繁运行"**是这份方案最重要的结构性改进：它把"一天两次检查"和"提前两小时提醒"解耦，避免了为了提醒而反复调用模型。
- **发布 ≠ 已读 ≠ 参加**三段式（§7.2 的流程图）与现有"未来安排不进已发生经历""通知已读只能证明获知安排"的口径一致，可以直接落到现有 `events` + 新通知表的组合上。
- **三个学校任务共用日程、各自持有写权限**（§3.1）避免了"三个代理各造一份学校"，与现有单进程串行架构相容；"每日检查允许返回空变更"也给稳定周课表留出了空间。
- **共同活动与学校提醒的关系**（§6 末段、§7.2）处理得对：不因提醒绕过 60 秒窗口、不自动开始第二场活动、真实共同预约不自动取消学校活动，冲突留给个人导演协调。
- **首建不等于补历史**（§4.3）：新库建立当前学期／本周而不是生成已错过的整个学期，也不伪造"已经通知／已经参加"，与现有"未来安排不写成已经出席"的规则一致。
- **环境轮不补生活、不推进 `narratedUntil`、不重置自主周期、不计共同轮数**（§3 末）与现有实现一致。

## 4. 补遗：对 CODEX 回应的确认与两处新增

CODEX 的回应（`CODEX_REBUTTAL_WORLD_SCHOOL_V0.4_20261008.md`）整体成立。我采纳它以下四点修正，并在核对它的方案时发现两处它没有展开的问题。

### 4.1 我采纳的四点修正

1. **失败隔离不能只删 `paused` 赋值。** 我原来说"只写 `retryAt`、不设 `paused`"是不完整的：`storage.ts:72` 的 `unfinishedTurn()` 查询**所有** `done=false` 的 turn，失败的环境轮仍在其中，于是 `Scheduler` 不选新轮、`SerialHost` 先恢复它、`runTurn` 也拒绝开新轮——**前台仍被挡住**。正确做法是把待重试的环境步骤移出前台未完成轮门禁（独立持久化步骤状态），并且不能为了解锁把失败冒充成功。它同时提醒"数据库提交与存储错误不能被笼统当作模型失败去重试"，这点也对。
2. **通知归属**：采纳它的划分（上游条目给通知策略与提醒时距；`school_week` **唯一**展开实例与通知候选；程序生成稳定身份、保存、到期发布与失效）。这比我原来"由创建实例的任务产出"更清晰，也避免了多个写入者。
3. **每日批次改用单一启动配置**（例如 `environmentDailyAt='06:00'`），不把旧的 `schoolTimes` 映射成批次起点——用户已明确选定 06:00，映射旧数组会造出"两个起点"。同意；迁移期需明确标注旧键已弃用。
4. **`relatedEventIds` 不是泄漏本身**：我把它称作"主要的隐藏泄漏面"是夸张了。个人查询串来自 scene／经历／可见消息，不复用 `narrativeQuery`；白名单只校验引用合法性，不会把事件正文注入个人检索。它是**需要约束的通道**（查询、`lookupDetails`、引用展开都要受个人已知范围限制），而不是已经泄漏。主叙事保留完整客观范围与一致的白名单，这一点我不应改动。

### 4.2〈新增·会直接阻塞启动〉`modelRoles` 扩容后，现有配置会让插件起不来

`settings.ts:37` 的 `models` 是**要求全部角色键都存在**的 Zod 对象，`index.ts:33` 又在启动时对每个角色调用 `connectionFor`，缺键即抛 `configure model for <task>`。现有正式配置（`config.local.json`）只有 `world` 与 `school` 两个环境角色：

```
narrative, narrative_shared, personal_chat, personal_life, personal_shared,
expression, memory, world, school, memory_consolidation
```

而 §9 要把 `school` 拆成 `school_campus / school_group / school_week`。**只要按新角色表实现，现有配置在解析阶段就会失败**，而报错是 Zod 的字段缺失，不会告诉用户"你的 school 需要拆成三项"。方案 §9 提到了"迁移时旧 school 连接可以作为三个新项的初始值"，但那是**迁移**动作；启动路径的顺序是"先 `loadSettings` 解析、再 `connectionFor` 逐项校验"，所以必须明确一种不依赖人工迁移的方式，三选一：

- **A（推荐，沿用既有模式）**：初始化时为缺失的三个新角色**从 `school` 派生**（`settings.ts:56` 对 `stickerDescriptionModel` 已有"缺省回落到另一个键"的先例），这样旧配置能直接启动，迁移只是把派生结果写成显式配置；
- **B**：把 `school` 保留为三个新角色的**后备键**（新键缺失时读旧键），并在文档里写清"旧键仍被读取"；
- **C**：解析放宽为"角色表可缺项"，由启动检查给出**指名道姓**的报错（"缺少 school_campus / school_group / school_week，请从 school 复制"）。

无论选哪种，都要在细化里写死，并补一条"用现有配置启动"的验收——否则第一次正式启动会因为配置而失败，而失败原因藏在 Zod 报错里。

### 4.3〈新增〉旧库中未完成的环境轮需要明确处置

`unfinishedTurn()` 会把环境轮也算作未完成轮（它只按 `done` 过滤）。当环境步骤改成独立持久化之后，**升级前遗留的未完成环境轮**（`done=false` 且 `environmentKind` 有值）必须有明确归宿：

- 迁移时标记为"被当前日期检查替代"并记录（保留历史），或
- 继续按旧语义恢复一次。

不能只是把它排除在新门禁之外——那样它会永远停留在 `done=false`，既不会被恢复也不会被清理，而 `unfinishedTurn()` 仍会把它报给宿主。这与 4.2 一样属于"升级路径"问题：临时测试库永远测不出来，只有正式库会遇到。

## 5. 本次复核的边界

**没有做**：运行测试／构建／demo；连接模型或 QQ；检查正式库；修改任何文件。

**因此无法验证**：06:00 批次在真实网络与模型延迟下的完成时间；四个步骤连续调用对每日费用的实际影响；每周五生成下周计划的节奏是否够用；以及"个人导演看不到未读通知"在真实故事里的观感（她会不会显得对已存在的安排一无所知）。这些都需要真实多日运行才能判断，静态复核不能替代。

**给用户的两个可调整默认**（方案 §12 自己列出的）：提醒时距（一天／两小时／课前约一小时）与下周计划的生成日（周五）。我的建议是沿用方案默认，因为它们正好覆盖"提前一天知道"和"临出门前再想起来"两种需求，而课前约一小时对常规课足够。
