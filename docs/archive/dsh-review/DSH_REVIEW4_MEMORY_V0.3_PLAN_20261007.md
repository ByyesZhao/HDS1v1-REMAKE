## 1. 必须先定的四条

### 1.1 唤醒记录的唯一约束与"合并去重"会冲突

细化 §5.1 定 `memory_awakenings` 的**唯一约束是记忆 ID + localDate**，§5.2 又要求合并时"同一天在不同副本上的记录选择最早 `firstEffectiveAt`，来源并集"。

但合并前的当日唤醒行是以**副本 ID** 存进去的。合并时必须把这些行改挂到主 ID，而主 ID 当天很可能已经有一行 —— 按现有约束，改挂即冲突。更麻烦的是同一事务内"先插主行、再删副行"也会瞬时冲突。

建议在细化里明确其中一种：

- **A（推荐）**：唯一键改为（canonicalId, localDate），合并时同事务内先把副本行按日期并入主行（取最早 `firstEffectiveAt`、`sourceIds` 并集）再删除副本行；
- **B**：约束保留原样，但业务层读计数时一律按 `canonicalMemoryId` 过滤，副本行只做追溯；
- **C**：约束放宽为普通索引，唯一性完全由业务保证。

三者都可实现，但**不定就会被实现者按当时方便选一种**，而这条直接决定"三日续期"和"三十次候选"的计数是否精确。

### 1.2 维护批次的 cutoff 会漏掉"在批次处理期间才到期"的事件

计划任务5 写"固定 cutoff 后新增到期内容不混入当前周期"，细化 §7.3 写"批次只消化该 cutoff 范围，完成后推进 nextMaintenanceAt"。问题在于：**到期的判定时刻是 04:30，而短期到期可能发生在 04:30 之后、维护仍在处理这批的过程中**。那部分在"捕获时未到期、推进后已过期"，既不进本批、也要等一整天。

建议按容量而不是按时刻切批：批次选"已到期 + 已就绪"的项，取最早 20 条 / 12000 字符为一批，消费到哪里就记到哪里（watermark 用被消费项的到期时间，而不是捕获时刻）；只要本地还有到期项且前台空闲，就继续下一批。这样"停机后补办"和"当天分批消化"是同一套规则。请把这条写进细化 §7.3。

### 1.3 "同日最多一次"与"真实新进展延长七天"在长期窗口已生效时会打架

细化 §2.3 说七天窗口依据"本轮真实事件更新的处理时刻"，§5.1 说**每个记忆每天最多计一次有效唤醒**。当同一事件跨天持续发展（第二天考完一门、第三天出成绩）时：

- 短期锚点按 `hasNewEventProgress` 推进 → 详细窗口延长，这没问题；
- 但长期窗口已经生效时，后续进展如果落在同一天，按 §5.1 就不计唤醒，因此不参与"三日续期"。

这本身是"每天一次"的必然结果，可以接受；但需要明确一句：**"新进展"延长的是短期详细窗口，不等于一次有效唤醒**，二者是两条独立的线。否则实现者容易把 `hasNewEventProgress=true` 顺带当成一次唤醒（或反过来），让续期提前触发。

### 1.4 预备长期摘要与"重要事件立即长期"的期限起点不同，需要写成规则而不是巧合

细化 §3 的表格：普通新事件的长期 `retainedFrom = shortExpiresAt`（七天后的时刻）；明显重要事件的长期"从本轮 at 立即进入长期"。也就是说**同样是长期记录，起点分别取 at 和 at+7天**，到期时间相差七天。

另外，普通事件在建立时就写出了预备长期行（只是 `retainedFrom` 前不提供），它的 `createdAt` 是建立时刻、`retainedFrom` 是七天后 —— 细化 §2.3 要求"事件发生时间与记录创建时间分开"已经覆盖了这点，但没写清**"到期时间从哪算"**由什么决定（重要度？是否立即生效？）。建议把这两行直接写成规则："长期保留起点 = 该记录首次对检索生效的时刻（普通事件为 shortExpiresAt，重要事件为 at）；创建时刻不参与计算。"这样 §5.2 的合并与 §8 的迁移都能引用同一条。

## 2. 值得补一句的八处

1. **`MemoryCandidate` 缺少校准字段。** 执行计划"文件与类型约定"里 `MemoryCandidate` 的跨模块字段是 content／sourceIds／createdAt／状态期限／可选向量，**没有 `revision` 与 `stateVersion`**。但任务5 要求维护单元保存 `readSet` 的 `ownerId/stateVersion` 并在应用前比对，`selectCandidates` 又是它唯一的候选入口。建议把 `OwnerVersion（含 revision/stateVersion）` 补进 `MemoryCandidate`，否则维护层只能再查一次库。

2. **批次状态机缺 `stale`，且一次只能有一个在途批次。** 细化 §8 的状态是 `pending/computing/ready/done`，`appliedUnitKeys/staleUnitKeys` 记在 job 里。若"冲突单元重新准备"要排进下一批，就等于需要第二个在途批次；而 §7.1 的后台槽只有一个。建议明确：**stale 单元在下一批重新准备**（而不是当前 job 内重试），并说明"一个在途批次 + 若干 ready 单元"是允许的组合。

3. **`IndexJob` 状态里没有 `ready` 之外的"已应用"语义。** `ready` 表示向量已算好但尚未挂到 owner；提交后是 `done`。细化 §7.5 与任务5 要求"ready 索引提交同样由 `applyOneReady` 校验 owner revision／配置后完成"，这一条已经写了，但类型里 `IndexResult` 只带 `jobId/owner/configSignature/vector`，**没有"被哪次应用消费"的标记**。建议与 `appliedUnitKeys` 对称地加一个字段，方便重放与排查。

4. **`stop()` 的顺序需要写死。** 细化 §7.5 说"AbortSignal 取消后台 HTTP，等待后台收尾后再关 SQLite"，但现有 `index.ts:100` 的 dispose 是 `await host.stop(); storage.close()`。维护协调器必须先于 `storage.close()` 收尾，且它不在 `SerialHost.active` 上（任务6 明确不纳入）。建议在细化里把 dispose 顺序写成：`host.stop()` → `maintenance.stop()` → `storage.close()`，并注明"回调必须检查实例仍有效"。

5. **`stop()` 与"在途 HTTP 无法真正取消"**：AbortSignal 只能让 fetch 提前返回，供应商侧仍在跑。建议补一句"取消后的结果丢弃、不写入 ready"，避免实现者把 abort 当成"没有产生远程调用"。

6. **04:30 的"标记当天到期"与"扫描捕获 cutoff"是两个动作。** 细化 §7.3 混在一句里。建议写成：① 04:30 时若没有当天周期，则建立当日周期并记录 `cutoff = now`；② 扫描时按 `cutoff` 之外的"已到期项"分批消费；③ 全部消费完才推进 `nextMaintenanceAt`。这样"停机三个月后启动"与"当天正常消化"走同一条路径。

7. **80 字符与 800 字符的口径要统一。** 方案 §8 写"常驻文字总额最多 800 可见字符"，细化 §5.3 写"稳定认识最多 800 可见字符可常驻"。请明确是**所有 alwaysInclude 条目的总额**，而不是单条上限，否则实现者会按单条理解，几十条认识就会全量注入。

8. **`queryTimeoutMs=1500` 之后要记录放弃率。** 细化 §6.2 说超时走词法，这是对的；但 1500ms 对首字延迟较高的端点可能经常打满，而"超时→词法"是静默降级。建议把"本轮向量查询超时/失败次数"计入 `hdsi.status` 或实施记录，否则上线后无法判断混合检索到底有没有在生效。
