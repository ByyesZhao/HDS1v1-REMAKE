## 2. §5.5：需要对照既有例外，不能只读V0.5概括句

### 2.1 当前行为与历史合同一致

DSH对源码的读取成立：[lifecycle.merge](../../../src/memory/lifecycle.ts)在有未归档成员时解除合并身份的归档标记，迁移已有唤醒日期及grants；[promotionEligible](../../../src/memory/capacity.ts)随后可以认定该身份符合晋升资格。

但这一行为不是本轮漏加的旁路。[容量细化§3.1](../topics/memory-capacity-idle/MEMORY_CAPACITY_IDLE_V0.4_IMPLEMENTATION_20261008.md)明确规定：

> 正式同事件合并继承既有活跃成员资格是身份合并，沿用该成员真实grant，不是凭维护now重新激活；全归档成员合并保留最早真实归档锚点。

[同文§7.2](../topics/memory-capacity-idle/MEMORY_CAPACITY_IDLE_V0.4_IMPLEMENTATION_20261008.md)还明确要求同事件长期合并迁移、去重有效日期，并保留已有真实有效期限；有活跃成员继承现有资格，全归档保留最早归档起点。[DSH REVIEW17 §3](DSH_REVIEW17_MEMORY_CAPACITY_IDLE_DELIVERY_20261008.md)也曾确认“只要有活跃成员就清空归档／容量标记”的实现正确。

用户后来确认的“先真实重谈恢复，再晋升”已经用于禁止**仍独立归档的主项直接promote**；相关候选、冻结合同、应用时刻及Lifecycle都已设门禁。已确认回应没有提出撤销上述同事件身份归并例外。

三种情况应分别说明：

| 情况 | 既有合同 |
| --- | --- |
| 独立归档事件，直接晋升 | 禁止，须先合法awaken恢复 |
| 同一事件的多个身份全部归档后合并 | 仍归档，最早真实起点不后移，不能直接晋升 |
| 同一事件仍有现成未归档身份，合并重复记录 | 归并到现有事件资格，去重已有有效日期，不因维护时刻发新恢复许可 |

第三种情况的30个日期是这个规范事件原有的合法日期并集，不是合并额外制造的唤醒。前提仍是**同一事件**；不同经历不得以相似关键词合并，语义判断依旧由整理模型负责，不增加新审核模型。

V0.5记忆§5“后台不能靠整理自动恢复”确实写得过于概括，应补上上述身份合并例外，避免读者误认为以前允许的归并现在被禁止。它应描述当前已批准实现，不能从这一遗漏反向推导必须收紧代码。

### 2.2 不直接采用A或B

- A给出的`live.length === unique.length ? null : 最早归档锚点`实际上表示：**任一成员归档，整组就归档**。这会把已有活跃记录拉回归档，与A的文字解释及原合同都不一致。
- B一律排除归档维护对象过宽。归档记录仍可能作为稳定认识审核的只读依据，或属于受阻短期的合法摘要修复依赖。禁止它直接晋升，不等于禁止后台看到、精炼或合法归并它。
- 如果以后要禁止第三种混合状态归并，这是收紧既有功能规则，应明确变更合并资格及其依赖处理；不能作为“按原合同修bug”悄悄实施。

建议本次保留原合同、补文档；把测试拆成“全归档合并不恢复”和“同事件合并继承现有活跃资格”两个用例。现测试名`merge_does_not_awaken_or_restore_archive`过宽，应改名／拆分，但不把合法混合归并断言改成拒绝。

### 2.3 隔离观察不等于推翻合同

本次合成内存库复现确认：全归档归并保留最早锚点且不满足晋升；随后与同事件活跃身份归并，归档判定变为null、已有30个合成有效日期保留、晋升资格成立，新增reactivate grant为0。

这证明DSH说的现象可达，也证明它是需要明写的例外；是否违约还必须结合前述已经批准的专门合同。若用户希望连这一例外也撤销，应另作明确变更；本次默认不推翻既有细化。

## 3. §5.6：预备期create条件缺口成立

[lifecycle.apply](../../../src/memory/lifecycle.ts)在`create + existingLongId`路径中，无条件更新已有长期的`lastEventUpdateAt`；只要本轮时刻早于`retainedFrom`，就把生效时刻及initial grant改成新短期截止。[ShortCreate](../../../src/memory/types.ts)和[基础合同](../../../src/model/contracts.ts)没有可用于区别真实进展与重谈的字段。

这与[既有记忆细化](../topics/memory-v0.3/MEMORY_V0.3_IMPLEMENTATION_20261007.md)及V0.5“预备窗口只随真实进展顺延”不一致。不能仅凭有新合法sourceId就认定旧事件有新进展：sourceId证明本轮确有来源，来源可能只是再次谈及同一件事。

本次隔离复现：1月1日新建普通短期，关联长期原本1月8日生效；1月2日提交有合法新来源、相同事件／感受摘要的linked create，合同接受，无新进展字段，长期生效时刻与initial grant均变成1月9日。复现证明程序没有判断分支，不宣称模型在真实聊天中必然这么输出。

建议后续最小修复：

1. 对引用已有长期的create明确提供真实新进展判断，联动类型、模型合同与提示，不让程序从“create”或“新来源”自动推断。
2. 没有新进展时，不移动已有长期的预备生效／initial grant，也不刷新它的有意义事件更新时间；合法正文及来源仍按相应记录合同处理。
3. 有真实新进展且仍在预备期才允许顺延；已经生效的长期不因此重开90天，新事件首次建档仍沿原规则。
4. 覆盖预备期无进展／有进展、已生效、update对照及initial grant只有一份；不要只改那条文字说明。

不需要用户重新决定期限或模型。这是在落实“重谈／改写不延长”的既有规则。本次尚未实施修复。

## 5. §7：55与64没有冲突

当前目录静态统计：64个平铺文件，其中9个`main-*`文件，其余55个。原[交付记录](../topics/prompt-context/PROMPT_CONTEXT_OPTIMIZATION_V0.1_DELIVERY_REVIEW_20261008.md)说的是“55份工作树记录，以及主目录最终检查输出”；[实施日志](../topics/prompt-context/PROMPT_CONTEXT_OPTIMIZATION_V0.1_IMPLEMENTATION_LOG_20261008.md)也明确两者分开。

所以“47个task前缀”不是工作树记录总数；工作树还含baseline、progress、review等记录。不能用总数64或task前缀47推翻55份复制记录。MAP可以补明“该批复制的55份工作树记录，另有主目录报告”，不必抹掉历史数量。
