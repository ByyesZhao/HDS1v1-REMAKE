## 2. 建议开工前定的三处

### 2.1 §10.4 的通知正文映射需要写清"哪个课次"和"绑定哪个实例"

细化 §10.4 让程序从冻结的 `SchoolExpansionInput` 生成全部 `requiredOccurrences` 与 `requiredNoticeKeys` 的声明实体，模型只回 `noticeTexts[{key, text}]`。我核对了一个关键细节：**通知的 `occurrenceKey` 并不总是 null**。

`calendar.ts:62` 的条目级通知（`issue`／`change`／`cancel`）确实是 `occurrenceKey: null`，但**提醒类（`reminder`）与部分变更通知带具体 `occurrenceKey`**，而且提醒原本是靠这个字段绑定到具体实例的（下一段里 `addNotice` 用 `occurrenceKey: occurrence.occurrenceKey`）。新合同里模型不再声明 `entityRefs`，所以：

1. **模型凭什么写出"几点上课"**？如果输入里的通知描述只有 `kind / publishAt / channel / 声明实体`，模型就不知道这个提醒对应的是**哪一次课、什么时间、什么地点**，"课前 60 分钟提醒"这种正文很容易写成一个模糊或错误的时间。建议明确：通知描述里必须带上该通知对应 occurrence 的**时间／地点与稳定身份**（没有 occurrence 的条目级通知才只给条目信息）。
2. **`instanceId` 由谁落**？新候选结构里没有它，程序需要从该必需 key 的 `occurrenceKey` 反查实例并写入通知行，否则提醒会失去与课次的关联（现有 `legal()` 会据此判定"课次已过期则提醒失效"，`notices.ts:8`）。建议写一句并由验收项钉住：**提醒类通知的 `instanceId` 必须指向它声明的那一次 occurrence**。

执行计划的 `fixed_notice_entities_text_per_key` 覆盖了"每个必需 key 给一次非空正文"，但**没有一条断言"正文对应的时间与声明 occurrence 一致"或"instanceId 指向正确"**。这两点建议补进任务 11 的验收——否则结构全通过、正文把周三的课写成周四，程序看不出来。

### 2.2 "无必需通知时跳过周模型"与 `weekNotes` 的关系要写死

§10.4 末句："没有必需通知且机械工作无需模型说明时可不调用周模型，仍解析机械实例并保存覆盖／已有 conflicts"。

这里有个歧义：**`weekNotes`（含 `conflictNotes`）只在"调用模型"时才可能产生**。所以当上游出现冲突（比如同一时段两个安排）而恰好没有必需通知时，按字面就会**跳过模型，于是当周的 conflictNotes 就没有了**。请明确二选一：

- **A**：冲突说明也算"需要模型说明"的一种，因此**不得跳过**（把"无需模型说明"定义为"无必需通知且无冲突"）；或
- **B**：允许跳过，并明确"冲突仍存在于程序保存的 conflicts 里，只是没有自然语言说明"，且验收按 B 写。

我倾向 **A**：细化 §10.4 那句"必要冲突说明"本来就在模型职责里（`weekNotes` 的定义），A 与它一致，也不会让冲突悄无声息。

### 2.3 对话段窗口要替换的旧条款，文档同步范围没列全

`recentMessagesLimit` 的使用点我全查了一遍，只有三处：`settings.ts:34`（配置默认）、`memory/types.ts:36,38`（类型与默认值）、`memory/retrieval.ts:55`（`.slice(-N)` 这一处实际截断）。所以**代码改动面很小**，细化 §3.2 的处理（旧字段只作解析入口、不参与运行时截断、解析前移除并记诊断）也是对的。

但**文档面**不止执行计划任务 8 列的那几份：`docs/MEMORY_V0.3_IMPLEMENTATION_20261007.md` 与记忆执行计划里明确写着"近期原文窗口 30 条"，`REMAKE_V0.2_*` 系里也有同一口径。任务 8 的 Files 只列了 `README.md`、`IMPLEMENTATION_HANDOFF`、`DOCUMENT_AUDIT`、示例与脚本。建议把"记忆 V0.3 的近期窗口条款"也加进任务 8 的同步清单，否则实施完会留下"文档说 30 条、代码用 4 段"的长期矛盾——这正是前几轮反复出现过的那类问题。

## 3. 三处小项

### 3.1 `recent()` 的"最近段"排序键建议点明

细化 §4.4 说"选最多 4 个**有该阶段可见原文**的最近段"，执行计划任务 2 的断言是 `recent.episodeIds).toEqual(['B','C','D','E'])`。这里"最近"是按 `lastInteractionAt` 还是 `openedAt` 排，建议写死（我建议 `lastInteractionAt`，它天然满足"当前段在最后"）。这个选择也决定了"当前段只含未读输入时返回 A／B／C／D"那条断言的分母，写清了实现者就不会各按各的理解排。

### 3.2 §4.3 的硬失败范围，建议按记录类别区分

"发现无法由已保存证据解释的孤立／冲突关联，报错并保留现场"这条我认同原则，但**范围偏宽**：一条崩溃遗留的**孤立消息**（比如事务回滚边界）如果让插件**启动即失败**，而用户又没有手动命令可用（§1 已定），那就无路可走了。建议按类别区分处置：

- **必须硬失败**：当前段冲突（`activeDialogueEpisodeId` 指向的段状态不一致）、跨活动的归属冲突、未完成轮缺失关联——这些会让后续写入继续错下去；
- **可降级**：孤立消息／重复归属，记入 `DialogueConsistencyReport` 并在启动日志给出 ID 与原因，程序继续按"不猜测"的方式跳过它们。

这与"不默认合并、不新增自动修复后台任务"并不冲突——降级不等于修复，只是不让一条历史毛刺把服务卡住。

### 3.3 §4.3 末句的措辞可以更精确

"不默认'孤立消息并入最近段'或'重叠段全合并'；常规一致性由写事务保证，**不新增自动历史修复后台任务**"——建议补一句"仅保留程序内部的自动关闭（`closeDue`）与保持释放（`releaseReply`），**不新增用户可见命令**"。现在这句话在细化 §4.3 读起来是"不做任何自动动作"，而 §3.1／§4.2 又描述了自动关闭，两者并列时容易被误读成"也不自动关段"。

- **`json_object` 下保留提示 Schema**（§6.2）：与 CODEX 的只读核对一致（`settings.ts:23` 与 `client.ts:72` 默认都是 `json_object`），没有为了去重提前切模式。
- **`contactEligible=false` 用 Schema 分支固定**（§6.2）：把"提示要求"变成"程序确定的输出空间"，同时保留发送层门禁和 `true` 时仍可不联系——这比只改提示词更彻底，也没有把"有资格"变成"必须联系"。
