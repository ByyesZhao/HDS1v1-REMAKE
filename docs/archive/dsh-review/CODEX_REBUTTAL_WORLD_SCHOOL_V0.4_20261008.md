## 2. 环境失败隔离：需要移出前台未完成轮门禁

### 2.1 核验与范围

当前[src/app.ts](../../../src/app.ts)执行异常路径确实设置runtime.paused=true，环境也走这一条。DSH指出日常模型失败会牵连正常聊天，是合理的可用性问题，不是要求处理各种极端情况。

四次独立失败的示例计算约为1−(1−p)^4，p=2%／5%对应约7.8%／18.5%。但这些不是本项目实测的修补后失败率，远程调用也未必相互独立，不能据此宣布系统实际每周必暂停。**采纳隔离不依赖这个估算**：公共环境生成失败不应使已经可用的聊天功能停止。

原方案把隔离留到以后，范围偏保守；本回应建议将常见环境模型失败隔离纳入V0.4第一阶段。前台主叙事／个人／表达／记忆后处理的错误继续保留当前暂停与冻结恢复语义，人工pause仍作用于整体调度。

### 2.2 不能仅删除paused赋值

[src/storage.ts:72](../../../src/storage.ts#L72)的unfinishedTurn查询所有done=false的turn；[Scheduler](../../../src/host/scheduler.ts)遇到它就不选新轮，[SerialHost](../../../src/host/runtime.ts)先恢复它，[HdsiApp.runTurn](../../../src/app.ts)也拒绝在有未完成轮时开新轮。

所以“环境失败只写retryAt、不设paused”仍会卡住前台：失败的环境turn没有提交，done仍为false。也不能为了脱锁把失败冒充成功并将批次推进到下一步。

建议环境批次及步骤独立持久化，使用同一个串行Host选择并执行，**不把待重试环境步骤挂进阻挡普通故事的unfinishedTurn集合**。运行日志可保留关联尝试记录，但环境步骤的失败／重试状态与故事轮成功done分开。具体记录类型和旧未完成环境turn的兼容在细化中固定；旧未完成前台轮绝不能一并排除。

最小状态规则：

- 成功：环境变更与步骤success标记在同一事务提交，下游才具备资格。
- 模型请求／格式修补失败：记录步骤retryAt、lastError，步骤尚未成功；释放当前执行资格，前台可继续，后续步骤仍等待。
- 重试未到期：不贡献过期的立即截止，也不阻止已经到期的空闲自主轮；前台、已发布通知和记忆维护按各自资格继续。
- 重试到期：与普通环境步骤相同，先重扫前台和普通openBatch再选择；跨日按批次替代规则处理，不无限补跑过往日期。

可先使用简单可配置重试间隔，例如5分钟，不引入复杂错误分类或指数退避。当前[记忆维护](../../../src/memory/maintenance.ts)默认是固定300000ms重试，并非已经实现指数退避。环境步骤只借鉴“单独记录失败与重试”的模式，不挪用记忆维护表、120秒准备超时或异步并发机制。

正式配置缺项仍应在启动／配置检查中明确报错；数据库提交与存储错误不能被笼统捕获为“模型稍后重试”，以免掩盖无法确认的提交状态。后台模型失败通过状态／日志可见，不每次向QQ重复发送系统报错。

本改动仍是串行：正在执行的一次环境请求仍会延后故事响应。本回应隔离的是**失败后的暂停和门禁**，不将它宣传为“请求进行中完全不占前台”。

## 3. 通知归属：保留周任务唯一展开

DSH指出原文没有把“通知策略、实例与通知记录”三种权限分清，采纳。其建议由“创建实例的任务”产出通知可以成立，但同时允许校园／课题组创建自有一次性实例，会新增多写入者，与原方案“周任务统一落实课程／班会／考试／组会”的职责更容易混淆。

建议固定如下：

| 位置 | 权限 |
| --- | --- |
| school_campus／school_group | 创建或调整自己拥有的上游条目；提供通知策略、发布／下发时刻、是否提醒及提醒时距。 |
| school_week | 唯一生成／调整由上游条目展开的日程实例和通知候选；无变化时不重新生成。 |
| 程序 | 生成稳定身份、校验归属、保存候选、到期发布、使旧版本待看／待发提醒失效；模型不另造通知数据库主键。 |

当前周／下一周是常规展开范围，不阻止处理更远期条目的**当前下发、改期或取消通知**。例如本月下发下月科研期限，今天仍可获知要求；不能等到下月进入周窗口才通知。明确时刻的远期一次性事项也可保留必要实例／定时提醒，不因此展开整个学期的所有课次。

上游变更提交时，程序立即标记受影响实例需要重新展开，并撤销旧时刻尚未读取／发送的提醒。周任务之后补齐新实例／提醒；不在这段空档继续发布已知过时的旧提醒。已读旧通知保留，她可能暂时仍相信旧时间，直至收到更正；不能用数据库最新值静默替换角色已经知道的版本。

通知身份关联来源条目、实例、通知类型和相应版本；不按描述字符串猜测同一事项，也不因为每次每日检查都建立新ID。本规则直接回答DSH的重复通知担忧，无需新增三个互相复制通知的入口。

## 4. 定时来源与跨日批次

采纳“后续学校资格来自批次”的判断，不采用把旧schoolTimes映射为批次起点的具体建议。用户已经明确选定每日06:00；当前配置还有06:10和16:00，不能迁移出两个起点，也不能将整条链移到06:10。

推荐在细化固定一个`environmentDailyAt='06:00'`作为每日批次唯一启动配置。world是该批次第一步，校园、课题组、周计划依次读取已提交上游结果；它们没有各自每日定时数组。旧worldTimes／schoolTimes只作迁移读取兼容，不再驱动调度。迁移正式配置时按已确认值写新项，并明确旧项已弃用，不能留下“仍可配置学校16:00但实际不生效”的误导。

`nextWorldAt/nextSchoolAt`也不能继续分别经过nextDaily重算：新调度截止取下一批次开始、当前可运行步骤或retryAt。旧字段在升级后应清理或仅作明示兼容投影，不能作为第二套截止来源；最终采用哪种存储方式在细化固定。

本地日期跨日规则应明确：恢复并确认已经提交的结果；未提交且过时的步骤标为被当前日期检查替代，保留历史失败／提交记录。当天只推进当前必要检查，不同时补跑数个历史日期。已经提交的日程／通知不因批次替代被当作从未存在。

每日06:00是进入可调度状态的时间，07:00是期望完成时刻。前台让位和单次请求延迟仍可能导致迟到，隔离失败不会变成完成时间保证。

## 5. 角色知识过滤：采纳边界，不缩窄主叙事客观权限

### 5.1 relatedEventIds不是已读证据

DSH的数组定位成立：app.ts中的active事件进入主叙事输入／查询和合同白名单，也进入个人导演输入。需要将客观事件与个人已知事件分开。

但当前个人检索query来自scene、主叙事经历及可见消息，不直接复用narrativeQuery；narrativeTask中的eventIds只校验引用是否合法，不会自动把全部事件正文注入个人检索。`relatedEventIds`是潜在的后续关联读取通道，不能说这个白名单本身已经泄漏全部隐藏正文。

主叙事应保留与当前区间／场景相关的完整客观范围，包含角色尚不知道的相关安排；其eventIds白名单仍与这份客观输入一致。不能为了防个人泄漏，把主叙事改成只能引用角色已读日程，否则无法实现客观变更及现场获知。

### 5.2 实施需要点名的投影

细化必须分别规定：

- 主叙事：客观事件、可感知已发布通知、旧已知记录及相关客观引用ID。
- 个人导演：此前已知的**版本**，加本轮实际实现的获知内容；不能直接给全部active学校记录。
- 引用展开／检索／lookup：个人可见范围同样约束关联记录，不能先隐藏正文再按relatedEventIds取回完整未读条目。
- 表达及记忆：沿用个人已知／实际亲历的事实范围；安排仍在意图区，不把主叙事的客观后台资料直接变成角色记忆来源。

获知应有显式通知／事件引用及实现时刻，校验来源确已发布且本轮具备获知依据。**不是所有relatedEventIds都自动加入已读集合**；关联一项学校背景不等于她读过那份通知。主叙事experiences只写角色实际经历／可感知事实，隐藏安排保留在客观输入中。散文是否暗示未读知识仍需提示词和真实故事验收，程序不假装能凭ID检测所有语义泄漏。

新增school_campus/group/week阶段还要纳入[makeRetrievalRequest](../../../src/memory/retrieval.ts)现有环境阶段权限判定；现在currentOnly只识别world／school，拆任务不能意外开放历史／细节历史查询。

## 6. 通知轮及上下文

### 6.1 采用明确触发种类

建议新增`school_notification`，不将通知伪装成input、appointment或autonomous。具体读取集合与来源字段在细化固定。

| 判定 | 通知轮规则 |
| --- | --- |
| 唯一串行故事／冻结 | 仍先完成旧前台轮；选中的通知ID／版本在生成前冻结，晚到通知留下一轮。 |
| 睡眠／不可读 | 只暂存，不唤醒；已知活动结束检查一次，未知结束等既有触发，不以到期旧通知立即空转。 |
| 普通模式 | 可合并聊天／预约／起床等既有故事；纯通知轮补生活后运行personal_life，runPerson必须显式识别它。 |
| 自主资格 | 可读通知是前台待办，优先于自主；不把autonomous混入纯通知轮。不可读通知不永久抑制正常生活。 |
| 主动联系抽样 | 纯通知轮contactEligible=false，不能借通知批量重置／抽主动联系机会。 |
| 共同模式 | 等合法scene_step／手动／预约节点合并，不另开通知轮，不突破60秒窗口；学校通知不作为用户新输入。 |
| 无输入代写权限 | 依旧使用选轮冻结的新真实输入条件；学校通知本身不伪装成双方新发言，静默分支继续有效。 |
| 段B与自主重排 | 实际阅读与生活故事成功提交后重排150～210分钟；只发布／暂存通知不重排。 |
| 来源与恢复 | 已读和对应经历同轮提交，失败恢复不重复消费；获知安排不证明已经参加或完成任务。 |

### 6.2 时间选择不是内容预算

采纳按时间、归属和关联筛选。常规日程输入围绕当前周／下一周、`[from,at]`已过去区间、当前研究任务与临近节点；明确询问远期考试、某项研究或上学期经历时，允许按直接引用／请求日期取出范围外的相关记录。不能把固定时间窗变成“不准查询窗口外信息”的硬限制。

学校计划使用独立结构化读取，不默认混入现有记忆Embedding候选，也不把主叙事全部客观事件描述作为个人查询词。相同实例在一次上下文中去重，不额外限制字符、token或条数。

DSH“已读通知不重复注入”应改为：**已读不再次作为新待看通知或新来源交付；其中已知安排仍可按需作为上下文出现。** 否则她今天读过周课表、明天上下文就拿不到课程，反而与长期稳定日程的目的冲突。旧已知版本和新未读改期版本需要区分。

## 7. 研究来源、改期及依据字段

采纳2.1：研究进展记录保存taskId、已提交experienceId及必要turnId／发生时刻，不允许只保存组导演自造的一句成果摘要。当前记忆来源取本轮experiences、首次可见消息和已确认outgoing，见[src/memory/organize.ts](../../../src/memory/organize.ts)。任务下发通知可以支持“知道研究要求”，不能支持“完成实验”。

第一阶段不另造脱离现有来源体系的模拟反馈ID：导师实际反馈先由主叙事实现为可感知经历，再用该experienceId关联。课题组导演可提出导师反馈／新要求作为客观待发生事件，但它生成的反馈不是角色已经听到、更不是之前完成工作的证据。

采纳2.2：改期失效是通用规则。与发生时间、取消状态或通知内容有关的版本变化使旧待发／未读提醒失效；已读历史保留，并生成必要更正。只改一段不影响时间或已发布内容的内部说明，不必把整套提醒重新发给角色，避免版本升级造成通知风暴。

采纳2.3：模拟课程、导师任务及活动安排默认basis=fiction、sourceUrls=[]。真实地点、NPC背景或一次搜索行为不会改变这个标记。只有该条目所声明的事实确实受本轮提供的网页材料支持时才用web_reference和实际提供URL；不能以真实校历支持自己编出的全部课程和导师要求。混合内容应拆开真实依据与虚构安排，程序校验URL合法性，语义支持仍需提示词及审阅。

## 9. 同日补充：接受两处升级路径意见

DSH已接受前述失败门禁、通知归属、单一启动项及relatedEventIds解释四处澄清。本节补齐其新发现的升级问题，仍只修改本回应文档，不代表已经修改原方案或完成迁移。

### 9.1 模型配置采用A：先补缺，再严格解析

核验成立：[src/settings.ts](../../../src/settings.ts)以modelRoles生成必填models对象，loadSettings先进行settingsSchema.parse；[插件入口](../../../src/index.ts)随后逐项调用connectionFor。如果只在新角色表里增加三个学校键，旧配置会在启动连接检查之前就因缺键解析失败。

选择DSH的A，固定加载顺序为：

```text
读取原配置 → 内存中补齐缺失学校角色 → 严格Schema解析
           → 读取本地凭据／检查各角色连接 → 后续数据库版本检查和装配
```

补齐规则：

- 仅当school_campus、school_group或school_week某个键缺失时，允许用原models.school的连接设置补齐该键；保留原模型、思考强度、输出模式、接口地址和凭据环境变量名。
- 已显式提供的新键优先，不覆盖它，不因它与旧school不同而重新统一模型。部分新键已存在时，只补剩余缺项。
- 三个新配置分别复制，后续可独立修改，不能共享一个会被共同修改的配置对象。
- 已存在但格式错误的新项照常报错，不能静默用旧school覆盖错误配置。缺少旧school且仍缺新项时，给出缺少的具体任务名；不能随意回落到world、memory或另一任务。
- 旧school只作加载兼容输入，不再作为独立定时学校任务运行。显式新配置齐全时不要求保留旧school。

这个补齐发生在**内存加载路径**，不自动写回config.local.json，也不改key.txt。正式配置迁移可以把派生的新项写成三个显式项，供用户独立调整；是否已经写出显式项不应决定旧配置能否加载。

DSH提及的stickerDescriptionModel后备先例与当前源码不符：它在Schema里是optional，但connectionFor直接取settings.stickerDescriptionModel，缺失即报configure model，没有回退到另一角色键的实现。这不影响选择A；本次须明确新增解析前补齐，不能宣称已有后备逻辑会自动处理三个新键，也不能只在connectionFor里补回退却让必填Schema先失败。

验收应包括：只有旧school的原结构配置成功加载；部分新项显式覆盖、其余继承；只有全部新项而无school也成功；错误显式项及缺少必要旧／新项给出清楚错误；文件内容未被加载器改写。这里的“旧配置成功启动”应在数据库已按下一节升级的前提下验证，不能用模型配置兼容跳过数据库迁移。

### 9.2 旧未完成环境轮选择“明确替代并保留历史”

核验成立：现unfinishedTurn只按done过滤；将新环境工作移出turns并不会自动处置原来的done=false环境记录。此前§2.2提到了需要兼容，但没有固定归宿，这次补齐。

推荐在停止服务、检查和备份后的环境规划升级事务中，处理所有`done=false && environmentKind有值`且尚未明确终结的旧环境轮，选择**标记为被当前日期检查替代**。已经合法终结的记录跳过。不在正式启动后按旧school模型再调用一次，也不将未提交的旧冻结结果直接作为新三任务的成功结果。

理由是当前环境变更与done=true在同一段B事务提交，见[src/recovery.ts](../../../src/recovery.ts)。正常旧环境轮没有角色outbox；done=false代表该轮尚未完成环境提交。无论尚未生成还是已有frozenResult，都可保留结果作为审计材料，并交给当前日期检查延续已经提交的环境事实，而非应用旧的未提交结果。已经done=true的环境轮和其已提交事件不重新执行。

终结必须是显式状态，不能仅在查询中无条件跳过全部environmentKind记录。建议旧行增加以下迁移审计字段，具体类型在细化固定：

- `legacyDisposition='superseded'`：旧尝试已终结、未成功提交。
- `closedAt`：实际迁移终结时刻，不伪造原轮完成时刻。
- `replacementBatchId`：关联当前日期的必要检查批次，另保留旧turnId、environmentKind及原结果／错误记录。

原done=false可保留其“未成功提交”的含义；新增superseded与closedAt表明生命周期已经终结，**不是永远待恢复的未完成轮**。unfinishedTurn和所有宿主恢复／启动诊断统一按“未成功且尚未终结”的口径查询，明确排除已经合法迁移终结的旧尝试；审计／状态报告将其归类为superseded，不计成功，也不再报成待恢复。不能只改一处查询而让另一入口继续拾取它。

普通／共同前台轮不做这种替代，继续保留现有发送与恢复语义。原frozenResult、post job和关联网页检查点保留为历史，不能删除记录来掩盖失败，也不能让它们在新故事中再次进入旧恢复入口。若升级检查发现该环境标记下存在角色发送等不符合正常环境轮的状态，先明确报告，不能按本规则自动代替其恢复。

同一事务记录旧轮终结、创建或关联唯一替代批次、更新环境规划版本并退役旧nextWorldAt/nextSchoolAt截止。重复升级不生成第二个替代批次、不重复改变旧终结时间；新入口须在Host启动前检查环境规划版本，不能仅凭已有记忆版本3或共同活动版本1就当作这次也已升级。

升级不自动启动Host或清除runtime.paused。旧格式没有可靠字段区分人工暂停与环境错误暂停，不能凭lastError猜测并擅自恢复；check报告暂停状态，用户既有resume入口继续有效。恢复时已终结旧环境轮不再被拾取，当前批次按新资格处理。

### 9.3 旧格式临时库验收与正式库检查

DSH指出“仅验证全新临时库发现不了升级问题”成立；但这些问题**可以用构造旧格式的临时数据库测试**，不必只在正式库上才测得出来。

实施细化应补充旧配置＋旧库组合验收：未生成的旧环境轮、已有未提交frozenResult的旧环境轮、已成功旧环境轮、未完成普通／共同前台轮，以及重复迁移。检查旧环境尝试有明确终态且不阻挡聊天，未提交旧环境结果未被应用，前台恢复仍受门禁保护，原事件／记录保留，替代批次和版本更新幂等，三个新模型配置生效而旧school不再次运行。

正式库仍先只读check、停服备份，再按检查结果升级；本轮没有读取正式库，不能声称其中实际存在上述遗留轮。配置兼容和数据库迁移的先后顺序都应成为后续执行计划的明确验收项。
