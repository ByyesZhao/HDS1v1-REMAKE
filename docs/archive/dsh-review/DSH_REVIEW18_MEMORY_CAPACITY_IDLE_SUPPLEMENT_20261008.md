## 1. 你问的"先真实重谈恢复，再晋升常驻"

**是的，你的理解正确**，而且这条规则正好把"归档池上限是软的"堵住。完整链条是：

```text
归档（archiveStart ≠ null，status 仍是 'active'）
   │
   │  ① 必须先"真实重谈恢复"：本轮有合法来源 + 模型显式 awaken
   ▼
活跃普通长期池（清空归档标记，回到 1000 池里）
   │
   │  ② 再按正常门槛：累计 30 个有效唤醒日期
   ▼
常驻审核候选 → 审核通过才成为 durable
```

两个容易混的点，我按源码说清：

- **"真实重谈"是什么**：这一轮的 `sourceIds` 必须落在**本轮合法来源**里（`lifecycle.ts:72` 的 `requireSources`），并且记忆模型要**显式**给出 `awaken`。检索命中、后台复读、摘要改写、索引重建都不算——这也是 v0.3 起就有的口径。所以要求"从聊天里找到明确证据"是对的：证据就是她这一轮真的又说起／经历了这件事。
- **恢复不等于绕过证据门槛**：恢复只把长期放回**活跃池**（`capacity.ts:68-74` 清掉三个归档字段并写一条 `reactivate` grant、给 90 天窗口）。要进常驻还得**另攒**到 30 个不同有效日期，而每一天的计数本身仍要求当天的真实重谈证据。所以"先恢复、再晋升"是两道独立的门，不是一条捷径。
- **它只限制"被晋升的那条主 long"**：不自动删除已有 durable，也不否定"多个真实历史事件可作为稳定认识证据"的既有规则。

**当前代码还没实现这条**：`promotionCandidates()`（`lifecycle.ts:128`）会把归档项选出来，`promote`（`:144-149`）也不检查归档状态——它的复现脚本已经证明"归档计数 1 → 0、status 变 durable"。

它提的落实方式我认可，而且比我上一轮的建议更完整：**不要只在 `lifecycle.promote` 里 `throw`**——那样 ready 的冻结 `promote` 结果会进入应用失败后的 5 分钟重试，反复重试同一份结果。正确做法是三处联动：候选与模型输入就不给已归档主项晋升资格；合同按**冻结评估时刻**检查；应用时按**当前时刻**再检查一次，准备期间自然归档的判 stale 并重排合法工作，其余单元继续。`lifecycle` 仍作为最终收口禁止归档直接晋升。

## 2. 我接受的三处修正

### 2.1 我读错了源码：归档不是 `status='archived'`

我上一轮写"`promotionCandidates()` 的 SQL 带了 `status='active'`，说明设计者的本意是把归档排除在外"——**这句是错的**。普通归档**不是一种 status**：`capacity.ts:64` 只写 `capacityExitedAt`／`archiveEnteredAt`，行的 `status` 仍然是 `'active'`，是否归档由 `archiveStart` 判定（`capacity.ts:6-10`）。所以那句 `status='active'` 只是"是普通活跃身份"的常规条件，**并不排除归档**，SQL 选出归档项是必然的，不是疏漏。

我核查了全仓：`'archived'` 只出现在升级／迁移脚本里，普通记忆没有这个状态。

结论不变（风险路径成立、需要收口），但**我的推论依据要撤回**——这条也说明"从条件推测意图"不可靠，要以 `archiveStart` 这种显式谓词为准。

### 2.2 我说"500 条是最容易命中 30 日期门槛的群体"缺少依据

这条我接受。容量排序本来就更早挤出**唤醒数低**的普通项，而 30 日期门槛要求唤醒数高——两个方向相反，所以我说"500 条正好是门槛最容易命中的群体"是**没有依据的推测**。应修的是合法性边界，不应该据此放大发生规模。

### 2.3 空摘要保护不"省容量"，我的说法要收窄

我写"保住这条空摘要长期不占有效容量"——**不准确**。`longOccupied`／`longArchive` 是按**身份**计数的，与正文长短无关；受保护项仍会计入占用，所以可能长期显示可见差额。

正确的定位是：**保护的目的只是避免悬空引用与丢失记忆层内唯一的详情**，不是省容量。所以它不能当作"空摘要问题的完整修复"，必须配一个真正的闭环——它给的方案我认可，四步：

1. **源头合同**：新基础记忆结果的 `eventSummary`／`feelingSummary` 合成后至少有一个非空白（仍允许一侧为空，空摘要走既有格式修补重试）。这才是"以后不再产生"的保证；
2. **存量保护**：对已存在的到期受阻 short，保护其仍存活的 canonical long，并保留明确的 `missing_summary` 状态，**不从维护 now 给事件续期**；
3. **登记修复**：把可修复项登记到增量事件整理，用存活 short 详情与合法历史来源请模型生成非空简要摘要，仍受 15 分钟／活动门禁与正常重试；同版本不反复排空转任务；
4. **补偿清理**：摘要成功后沿原清理入口先删到期 short 及派生副本，再按**原归档锚点**判断 long；不复制 short 全文进 long，也不重扫原始日志重建旧记忆。

验收也要按这条闭环看：到期前／到期后保护、超量／超龄 long 不先删、一次合法摘要修复后详情与派生副本真正清空、未修好时无 0 ms 循环——**不能只看"long 还在"就认为修好了**。

## 3. 它补强或新增的几处（我都认可）

- **保护不延长归档窗口**（§3.3）：采用我 §4.5 的第一种解释——到期 short 先清理、long 后删除，但 long 的归档起点仍是真实的容量退出／自然到期锚点，**不从 short 清理截止再加 90 天**；也不把 `normalize` 改成一律保护全部暂存 short（那会改变活跃 1000 的归一资格）。补一句"删除保护不改变归档起点；保护解除时若已超量／超龄即继续清理"即可。复现报告的 `archiveProtectionClock` 正好证明锚点前后都是真实退出时刻。
- **`LIKE` 的问题参数化没有解决**（§3.4）：已复现 `LIKE 'detail:phone_brand:%'` 实际删了 2 条，其中一条目标是 `phoneXbrand`——因为 `_` 是单字符通配符。修法是精确匹配固定 decision 报告 ID、或字面前缀比较、或转义 `_`／`%` 并指定 `ESCAPE`。它说得对："不要再加一层参数化就宣称修复。"
- **性能可以便宜地修**（§4）：复现显示满池 1000 条、无变更时 `normalize` 仍执行 **16872 次 `listAwakenings`、约 206 ms**。它建议"有超量才排序"＋单次排序复用唤醒元数据——这比"整套性能重构"合适得多，我同意不作为修复前提，但值得同批顺手做。
- **低优先项的当前状态已被只读核对**（§4）：正式库三张 owner 表都是 0 行、三组跨表 ID 交集都是 0，所以跨表 id 冲突、缺 `kind`、缺 `retainedFrom` 这几项**当前不会触发**。按它的处理方式记着即可（将来有新导入库时再按来源校验），不为空库检查扩展一套修复框架。
