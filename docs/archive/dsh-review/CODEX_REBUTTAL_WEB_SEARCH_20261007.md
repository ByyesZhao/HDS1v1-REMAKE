# 共享网页搜索第六轮审查回应（Codex）

日期：2026-10-07。回应：[DSH REVIEW6](DSH_REVIEW6_WEB_SEARCH_20261007.md)。核对：[搜索设计](../topics/web-search/WEB_SEARCH_SUBSYSTEM_DESIGN_20261007.md)、[当前模型客户端](../../../src/model/client.ts)、[故事生成](../../../src/app.ts)、[后处理与恢复](../../../src/recovery.ts)。本次新增回应，并将可采纳澄清并入搜索设计；用户随后补充的生活个人导演查阅来源同步记忆实施细化及执行计划。不修改代码，不运行项目测试、服务、真实搜索或模型请求。

结论：**大部分意见可采纳为澄清；需要回应的主要是空结果额度的含义、单轮220页的计算和验收举例。** 原20／40独立额度、全阶段可搜索、默认无总字符预算、实际超限不自动删历史及可替换接口继续保留。不需要再让用户为工程性细节作一轮选择。

## 1. 空结果：建议保留原稿的B口径，区分原因

原设计§3.2已明确“搜索接口失败或无候选也计一次”，并单独解释了这个选择。因此它并非未定参数；REVIEW6的B与原稿一致。空结果确实不是技术故障，但可以被定义为一次**未取得可用资料的尝试**。

建议保留B并改清措辞：

> failures是未取得可用资料的尝试次数，不等于网络故障次数。结果原因分开记录：搜索接口错误、无候选、页面读取错误、无可用正文；前两者和读页失败都消耗同一个40次失败尝试额度，同一原因不重复扣额。无候选正常返回no_candidates，不向用户伪报网络错误。

它的后果是有意的：本逻辑任务累计40次无资料尝试后，结束该任务的网络探索，模型使用已有资料或承认未找到；不是把模型永久禁用，也不是以后任何独立任务都不能查。下一独立任务仍有自己的20／40。

不建议直接采纳A。按query去重只能阻止相同查询，不能限制40个甚至更多不同查询；“高度相似”也没有稳定定义。若空结果完全不扣额，模型不断改关键词仍可能在两个计数均未到上限时持续搜索，反而需要另加查询次数规则。

保留B不新增第三套次数上限，符合原设计的有限尝试意图。可以按严格规范化query复用候选／结果，作为减少重复请求的方法，不把模糊相似判定当额度控制。

需补验收：40次无候选最终successReads=0、failures=40，第41次不发请求；原因标为no_candidates而非网络故障；下一独立session可以继续搜索。接口报错和空结果的原因统计分别核对。

## 2. 逻辑任务序号：采纳，补上恢复例外

REVIEW6关于序号应对应runModel逻辑任务、不能对应transport.complete的判断正确。还需要防止恢复时重新进入runModel却分配新序号。

建议明确：

> 序号由业务层为一次新的逻辑任务分配一次并持久化，形成runId/sessionId。首次请求、工具续调用、细节补查和格式修补不增加序号。同一已记录任务恢复时即使再次进入runModel，也使用原runId，不当作新任务。只有业务上真正新建的同名逻辑任务才分配下一序号。

因此不能用transport请求次数，也不能用“每次执行到runModel函数就自增”的进程计数器代替逻辑身份。owner仍是turnId／jobId／独立工具任务ID，恢复时从已保存的阶段归属读取身份。

这是一条身份规则，无需新模型或新业务判断。

## 3. 恢复后配额与缓存：采纳，区分重放和新读取

采纳REVIEW6三条建议：

1. 原successReads／failures继续累加，不重置，不产生新的20／40。
2. 同session恢复后，把已计数材料再次提供给模型，不再计成功。
3. 已完成操作重放，复用已保存材料和计数，不重新请求搜索服务或网页。

应补一个区分：**相同query不一定是同一个工具操作。** 同一关键词默认先读1页，模型随后可能想读该查询的其他候选；不能因为query相同就永远只返回第一页。操作重放按已保存的operationId识别，新操作可复用候选缓存并读取尚未读过的URL，首次取得该材料时才增加成功次数。

缓存口径统一为：

- 同session已经拥有的材料／已完成操作重放：不再次扣额。
- 同session新取得的可用材料，包括从公共缓存首次取得：成功+1。
- 不同session从公共缓存首次取得相同网页：各自成功+1，互不共享额度。
- 新读取失败：本session失败+1；不把已保存失败结果重放再算一次。

材料、已确认计数和操作完成标记同事务保存，再用于模型续调用。仍不要求推断进程退出时未知的远程结果。

验收可用临时文件库：保存2成功／1失败，重开并重放材料仍为2／1且provider零调用；再读一个新URL成功后为3／1；另一个session使用公共缓存从自己的0／0变为1／0。

## 4. 单轮总量：220页不是当前单轮上界，不新增全局控制

REVIEW6用11种任务乘20得到“单轮220页”，混淆了**可配置模型种类**和**一轮实际执行的逻辑阶段**。

当前[src/app.ts](../../../src/app.ts)和[src/recovery.ts](../../../src/recovery.ts)的控制流表明：

- 普通／共同主叙事选其中一种，不会同时执行。
- 聊天／生活／共同个人导演选其中一种，也可能跳过。
- 表达仅在确需输出时执行。
- 普通故事后处理可执行记忆整理。
- 世界／学校是独立环境轮，二者不在同一普通故事轮里并行执行；环境轮后处理不再调用记忆模型。
- memory_consolidation属于后台维护，sticker_description属于素材描述工具，不属于每个故事轮必跑阶段。

所以按当前控制流，完整普通故事轮至多是主叙事、个人、表达、记忆四个逻辑模型阶段。若四者均实际用满额度，可有**80次成功取得正文**；环境轮有自己的20次。公共缓存命中也计本session成功，所以成功读取数不等于HTTP请求数或不同网页总数。今后增加真正的新逻辑阶段，应按实际会话集合重新统计。

用户已选择各任务独立额度，并允许更久等待，但不能把它写成用户明确接受了“单轮220页”。阶段独立计数不会自动把所有阶段材料汇总成一个巨大的模型请求。

不建议本期增加maxTotalReadsPerTurn：它不是原任务缺失的正确性规则，默认null也不改变当前行为；启用时还会改变不同阶段的独立额度语义。先提供按turnId／jobId汇总的读取与失败统计，保留20／40。将来用户确实要求跨阶段控费／控时再加该选项，不作为开工前置条件。

## 5. 验收：采纳真实边界，不构造越界正常状态

### 5.1 谁先达到额度

原设计已经举出20成功＋5失败停止、8成功＋40失败停止，并不是只覆盖“还能继续”。可以补为真实操作序列：

- 15成功＋39失败，再失败一次，停在15／40，下一操作不发请求。
- 19成功＋10失败，再成功一次，停在20／10，下一操作不发请求。
- 19成功＋39失败，最后一次成功则20／39，失败则19／40；两条路径均拒绝之后的新操作。
- requestedPages大于剩余成功额度时只读剩余份额；session内逐个派发读取，不能先发一批再在回调超扣。

25成功或45失败不是正常可达状态，恰好应该由门禁防止。无需为了验收正常额度额外建立“数据库已损坏为25／45”的防御性测试。

### 5.2 正常请求规模与真实容量

采纳记录正常输入规模分布和真实容量错误频率的建议，但需要区分证据：

- 离线三／六个月样本可检验相关性、候选量、各阶段实际注入字符数，以及人工预算未被恢复。
- 离线字符数不能直接证明供应商容量错误概率。真实比例要有所用端点／模型的实际调用结果，不能用未验证的字符到token换算宣布通过。
- 正式联调时记录调用数／容量错误数，若出现实际问题再展示样本和原因供用户决定，不现在替用户改成自动删条。

容量错误模拟验证与正常规模测试各有作用；不能因为前者只验证错误处理就取消它。本轮不执行在线测试，也不扩大此前固定测试的授权范围。

## 7. 用户后续补充：生活个人导演查阅内容可记忆

用户明确允许“生活个人导演（模拟虚拟角色本人）网页搜索的内容，允许进入短期记忆”。这项许可覆盖实际读到的知识／资料细节，以及由此产生且在个人导演输出中有依据的想法、感受；不能收窄成只记“访问了某网页”。

这是原“网页不能单独作为角色记忆来源”规则的明确例外：personal_life收到成功正文后，程序登记本轮self_web_read来源并交给记忆整理，可独立支持查阅类短期create/update，不要求额外聊天消息。原网页仍是external_reference，新增ID表达角色本人查阅行为，其他阶段搜索不自动获得该身份。

短期内容和后续简要长期应保留“她查阅资料了解到……”的性质，不把网页中他人的事件变成亲历；知识可以保留，感受依据实际个人导演输出。七天归档、长期期限和维护规则不变，不要求每页必建记忆，也不整页自动保存。仅扩充shortTermChanges来源白名单；私人细节变更及长期唤醒继续使用原合法当前来源，检索命中本身不加唤醒次数。恢复来源ID不变，重放不创造新查阅进展。

已同步搜索设计§3.3／§4／§7、[记忆实施细化](../topics/memory-v0.3/MEMORY_V0.3_IMPLEMENTATION_20261007.md)§2.3／§4.1和[执行计划](../topics/memory-v0.3/MEMORY_V0.3_EXECUTION_PLAN_20261007.md)共享类型／任务2。真实搜索的工具循环、持久化与装配仍须后续拆分实施任务，这次没有改代码。

## 9. DSH后续追问：同轮跨阶段公共缓存计数

核对后保留B，并已在搜索设计§3.2及验收项12明确后果。原§3.2和本回应§3已规定不同session各自计数，这不是遗漏的计数规则；新增四阶段用例使它更易理解。

主叙事、个人导演、表达、记忆若分别申请并首次取得同一网页，四者各成功1次、各剩19次。公共缓存让后三次不用重新抓取网页；四次本地额度计数不等于四次网络读取，也不代表四次服务收费。没有共享20次池，因此不是“只抓一页，某阶段额度就被四个阶段扣了四次”。同session重放计0，未申请的阶段不自动注入或扣额。

20次控制每个任务首次取得的可用页面份数。若改A，后续阶段可能先免费取得多个已缓存页面，再取得20份其他资料，改变原每阶段20页口径；C还会让额度受整个进程的缓存历史影响。两种都可以另行设计，但无需为澄清已有独立额度而改成它们。

验收固定：四阶段依次取得同一缓存材料，各为1／0；实际读取provider调用仅一次；同session重放不增加计数。来源可见性、生活个人导演查阅身份及来源门禁继续单独校验，公共缓存不赋予额外记忆权限。本次仍仅修改文档。
