## 2. 收束集合：区分文本身份与语义质量

实施细化§6和执行计划任务4已经明确：wrap_up只能保留或删除旧字符串，保留项沿用原文本；进展写入progress/publicNarration。用户确认的第九轮后续意见也认可“字符串集合包含校验，不加线索ID”，并明确goal/endingCondition的语义连续性另做真实验收。

因此，“还没决定吃什么”改成“晚饭吃什么尚未决定”虽可能语义一致，仍违反此处已经选定的条目身份约定。拒绝它不是实现误把合法轮次判错。DSH方案A的trim／空白归一化只能处理空白差异，不能解决这个语义改写示例，两者需分开描述。

可以采用的有限兼容：匹配时去除首尾空白、合并连续空白；匹配成功仍保存对应旧条目的原文。未匹配项仍交原任务修补，不能把同义改写自动视为旧项，也不进行语义映射。这是格式兼容建议，并未在本轮实施。

不采用方案B。违规时恢复整份旧集合可能重新加入模型已经解决／删除的事项；直接撤销检查则重新允许新增支线。两者都会改变已确认的“只减不增”，也不能证明剧情更正确。

现有修补会保留原业务输入（含旧outline）和具体错误，同一角色最多修补两次。离线探针验证：首次同义改写被拒绝，下一次复制旧原文即可通过，总共2次调用。若模型持续不遵守，仍可能暂停；“未完成轮保留”不意味着恢复必然永久失败，也不应因此无限重试或静默改剧情。此类真实模型遵循情况继续纳入实测。

## 3. 公开开场和提前收尾：接受实质问题

当前合同只强制final旁白非空。首节点可以建立outline却不输出publicNarration；提前end同样可以没有旁白和角色表达。`tests/shared-scene.test.ts`的最后一例确实允许只发送开始／结束两个标志。DSH对此的事实判断成立，建议完善而不是把设计中“用户看到开头／合理公开收尾”统一降为建议。

后续最小约束：

1. 以`sharedMeta.stepNumber === 1`识别首节点并要求公开旁白非空，不能只看phase=opening：较小maxSteps的首节点可能已经是wrap_up或final。
2. 非final提前end必须有公开收尾正文。建议将当前主叙事的publicNarration作为共同个人合同的校验上下文，避免只在段B事务中临时抛错；保持主叙事负责公共剧情，个人导演负责是否结束与角色反应。
3. 仍允许角色reply=none，以及中间轮无新增公开节点；不将“首／末有正文”扩大为“每轮必须回复用户”。

注意跨合同修补的边界：个人导演的格式修补不能改写已返回的主叙事。若本轮旁白为空，个人合同可修补为暂不end、留下后续收尾意图；不能声称在同一轮通过个人修补补出了主叙事。若要支持回主叙事当轮补写，需明确重生成顺序、旧结果替换及调用边界，不能暗加流水线。final已有主叙事非空约束，不存在这一缺口。

补验至少覆盖：默认首轮及小上限首轮拒绝空旁白；非final的空收尾拒绝／原任务修补；非空提前收尾且角色不发言可结束；中间静默轮仍合法；失败不发结束标志、不消费控制、不计数。真实“自然收尾”仍需模型多轮验收，非空字符串不能替代质量判断。

## 4. 两处源码推导错误和一个定时修法问题

### 4.1 §6.1：end且meta=null已经被守卫挡住

`src/host/shared.ts:77`实际是：

```ts
if (!meta && change?.action !== 'start') return;
```

代入meta=null、action=end：`!meta=true`、`end !== start=true`，所以条件为true，函数立即return，不会读到`state.scene.shared!.activityId`。这不只是“版本门禁下不可达”，即使直接调用该函数也不会发生报告所述TypeError。

局部探针传入end/null-meta，同时令任何Storage访问立即抛错，函数正常返回undefined，说明它根本没有访问Storage。无需再添加相同的no-op守卫。本结论只纠正该函数的具体推导，不表示任意伪造旧轮都能绕过版本门禁安全运行。

### 4.2 §5.5：结束轮各项会更新输出锚点，遗漏的是开始准备轮后续项

`src/host/shared.ts:62`中，`starting`仅在start准备轮第0项成立；其它情况取`turn.sharedMeta?.activityId`。正常结束轮有sharedMeta，因此该轮文字／动作／表情及末标志都会更新对应clock，最后一项才设ended。

探针确认结束轮第0项文字更新lastOutputAt且保持active，第1项末标志再次更新并设ended。DSH“结束轮只有seq=0被识别”的说法不成立。

实际小差异是：普通start准备轮没有sharedMeta，开始标志之后的角色表达目前不更新共享clock。首节点仍按startedAt立即选，完成首节点后按实际输出或静默completedAt建立下一窗口，所以目前没有节奏错误。建议将细化§5.1的“每个共享输出”明确区分准备轮与正式共享节点；也可后续让start候选身份覆盖准备轮其它已确认输出，但不把它作为结束轮错误修补。

### 4.3 §6.2：身份对齐建议合理，不能用“现在已可运行”取代未来定时资格

nextDeadline的共享截止分支没有再次比对clock/activityId，selectSharedMeta和refreshSharedStep有比对；在人工制造不一致状态下，报告描述的过去截止空转推导成立。现有正式流水线未发现产生该状态的路径，属于一致性改善，不是已证实的正常故事故障。

可做最小改进：下一截止资格同样要求活动身份一致，或抽取“不含是否已到期”的共同资格谓词。无需新增自愈。

不采用“只有foreground(now)返回共同轮才加入sharedDeadline”。合法等待窗口里，当前没有手动／预约、60秒尚未到，foreground本来就返回null；按该建议就丢失未来活动截止，可能直到别的环境／输入触发才推进。定时器负责未来唤醒，collectReady负责现在能否运行，二者共享资格但不能共享“已到期才返回请求”的结果。
