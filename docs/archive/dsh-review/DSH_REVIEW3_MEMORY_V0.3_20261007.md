# MEMORY V0.3 方案复核（DSH）

日期：2026-10-07。复核对象：[MEMORY_V0.3_PROPOSAL_20261007.md](MEMORY_V0.3_PROPOSAL_20261007.md)。

方式：只读文档与源码，**没有运行测试或服务，没有调用在线 Embedding，没有修改任何文件**。

结论：**方案方向正确，可以进入实施细化；但有 1 处机制性冲突和 5 处缺口建议先补，否则会在实现时被"顺手"改成另一种语义。** 第 2 节是我核算过的部分（方案自称的设计判断），第 3 节是与现有代码的衔接风险（最需要看的一节），第 4 节是缺口，第 5 节是文档一致性。

## 1. 我认为方案做对的地方

1. **对 7／90／3／30 的解读准确。** 明确指出"现有长期排序中的 `/ (1 + 距最近加强天数 / 90)` 是衰减参数，不是九十天保留期限""短期七天仅为检索窗口，不是七天后自动转长期"，并据此提出"稳定事实不因九十天未提及而遗忘""客观细节不走长期过期规则"。这三点把用户给的数字翻译成了正确的语义，没有把它们套到不该套的表上。
2. **删除与遗忘分开。** 到期只标 `archived`、退出日常检索，明确追问时才查归档，原始记录不物理删除——与 V0.2"短期淡出不代表这段生活从未发生"的原则一致。
3. **计数只由真实重谈产生。** 明确排除"向量命中、进入提示词、生成查询、定时压缩、模型复述旧资料、把 `reconsiderMessages` 当新来源"，还堵住了"用自己的输出给自己制造一次加强"这条旁路（`outgoing` 不能单独作为依据）。这是整套方案里最容易被实现成 bug 的地方，方案提前写死了。
4. **常驻不等于改设定。** 三十次只产生候选、只有两类出口（重要经历／跨事件稳定认识）、不自动写回 `梁思璃设定.txt`、涉及身份与作者指定性格的变更留给用户。这条边界保住了"次数不能改变人物身份"。
5. **向量是派生索引。** 段落 11.2 把"业务提交登记索引版本、Embedding 在事务外、失败记待办不影响故事提交、正文更新或归档后旧向量不得继续返回当前记录"写清楚了。这正是把 Embedding 接进"段 B 一次提交"结构里最容易出错的地方。
6. **不改冻结与恢复语义。** 启动顺序（先续办未完成故事轮 → 再续办未完成维护 → 随后到期维护与原调度）、`hdsi.pause` 同时暂停新压缩任务、维护不推进 `narratedUntil`、不生成"角色今天回忆了一下"的经历，都与现有实现对齐。

## 2. 我核算过的部分（结论：一致或可接受）

- **三段例子的数字对**：10-14 进入长期 → 到期 2027-01-12；三次唤醒（10-20、11-02、11-15）后刷新为 2027-02-13，`totalAwakenings = 3`、窗口计数归零。`retainedFrom` 取"本轮时刻"而非"上一次窗口起点"，与"三次续期"的字面含义一致。
- **流程图的"每三次有效唤醒 → 刷新窗口"与正文一致**（3 次窗口计数触发刷新），不是两套规则。
- **存储量估算合理**：1024 维 float32 ≈ 4 KiB，一万条约 39 MiB，与方案给的数字吻合；用 float32 BLOB 而非 JSON 数字数组也是对的（JSON 会放大 3～5 倍）。
- **"同日最多计一次"是必要的补充判断**，不是过度设计：没有它，一场长对话几轮就能刷满三次续期，窗口机制会退化成"聊得多就永不过期"。

## 3. 与现有实现的衔接：一处机制冲突 + 四个必须先定的点

这一节是本次复核的主要价值。方案在"数据表加字段"的层面描述得很清楚，但下面几处是**现有代码的结构前提**，不先改就会被实现成另一套语义。

### 3.1〈机制冲突〉"更新已有短期事件"与现有行身份不兼容

现有记忆行的 ID 是**按轮次派生的**（`src/memory/organize.ts:24-26,30-32`）：

```ts
const id = `${turnId}:short:${i}`;
const id = `${turnId}:long:${i}`;
```

`applyMemory` 对短期/长期创建行都是用这个 ID 直接 `save`。方案要求"本轮是新增事件、延续已有事件，还是没有新内容"，并且"延续同一事件时增量更新"、长期"已有同事件长期记录时更新或合并"、唤醒"引用记忆 ID + `revision`"。

但按现在的 ID 方案，**跨轮没有稳定的行身份**：第 N 轮创建的短期条目在数据库中叫 `<turnN>:short:0`，模型在第 N+1 轮拿到的就是这个名字，而这个名字本身把"创建它的那一轮"编码进去了。这会带来三个问题：

1. 语义上，条目一旦被后续轮次更新，它的 ID 就与内容来源不符（名字说它属于第 N 轮，内容却来自第 N+1 轮）；
2. 同一轮内多次更新同一事件时，`i` 是结果数组下标，同一个事件在两次整理里可能落到不同下标，等于换了一个 ID，`revision` 与唤醒计数会跟丢；
3. `index_jobs`／`memory_index` 按 `ownerId + revision` 记录派生索引，ID 不稳定会让"旧向量不得继续返回"这条规则无法可靠实现。

**建议在实施细化里先定行身份规则**：例如创建时分配一个与轮次无关的稳定 ID（`mem_<uuid>`），轮次 ID 只作为"创建来源"存在 `sourceTurnId` 字段里；同一轮内的多次变更按事件 ID 合并。这条不定，后面 `revision`、合并、计数迁移都会各自发明一套。

### 3.2 检索层现在完全没有状态/有效期/版本过滤

`src/memory/context.ts:38` 选长期只按 `kind === 'long'`，:55 选短期只按 `kind === 'short'` 加七天窗口——**没有任何 `status`/`expiresAt`/`revision`/`archived` 判定**（现在也没有这些字段）。

所以方案第 9.3 节的"先排除不在日常有效期的记录""归档只在明确历史追问时查""旧值只在明确问'以前'时查 `detail_history`"，全部是新逻辑，需要一并加进 `ContextBuilder`：候选筛选、归档分支、以及"明确追问"的判定入口。方案已写了 `memory_time` 类索引不再每次全表扫描，但**没说由谁做"这是明确历史追问"的判断**——靠关键词（现有 `wantsHistory` 正则那种）还是靠任务提示？建议明确，否则归档检索要么永不触发，要么每次都被触发。

顺带：现有 `memory_time` 索引（`storage.ts:25`）至今没有任何查询使用，正好在这次改造里真正用起来。

### 3.3 三个计数器与唤醒判定的归属还没落到合同上

方案第 7.3 节的 `totalAwakenings / awakeningsSinceRenewal / retainedFrom / expiresAt / lastAwakenedAt / lastCountedLocalDate` 是清晰的，但**"怎样算一次有效唤醒"在程序侧还没有可校验的形式**。现有 `memoryTask` 对 `reinforce` 只校验 ID 在本次检索集合内（`contracts.ts:88`），而新规则要求"必须提供所引用记忆 ID **和至少一个本轮经历／首次可见输入／实际输出的来源**，说明本轮怎样触及该记忆"。

建议在合同层写成硬校验：`reinforce` 必须带非空 `sourceIds`，且这些 ID 必须落在本轮合法来源集合内（与 `detailChanges` 现在的校验方式一致）；同时用 `lastCountedLocalDate`（Asia/Shanghai）在**事务内**做同日去重，避免同一天多轮重复 +1。

### 3.4 维护任务需要新的调度槽与新的 job 表

- `Runtime` 现在只有 `nextWorldAt / nextSchoolAt`（`types.ts:26`），04:30 的记忆维护需要第三个时间字段，并进入 `collectReady`/`nextDeadline` 的候选集合；方案第 11.3 节写的"停机错过后下次启动补处理"要在这里体现。
- 现有 `post_jobs` 只有 `{ turnId, result }`（`types.ts:79`），装不下方案第 12 节的 `memory_maintenance_jobs`（批次、输入版本、选定 ID、done）。这确实是新表，但**恢复判定必须把它算进去**：方案说"先续办未完成故事轮，再续办未完成记忆维护"，需要同步更新 `REMAKE_V0.2_RECOVERY.md` 的恢复表，否则实现者只会在故事轮上接恢复。
- `hdsi.pause` 要同时拦住"新压缩任务"，也就是 `collectReady` 里维护候选也要受 `paused` 约束（现有代码只在故事轮上拦）。

### 3.5 合同与新字段

`MemoryResult` 现在只有 `shortTerm / longTermChanges / detailChanges`（`types.ts:52-56`）。方案要求的能力（延续已有短期事件、明确丢弃琐碎事件、合并同事件长期、常驻候选、批次维护用单独合同）都需要扩合同，并且**要明确哪些字段由模型给、哪些由程序生成**：例如 `revision`、`retainedFrom`、`expiresAt`、两个计数、`lastCountedLocalDate` 都应该是程序字段，模型只给"内容 + 引用 + 意图"。这与 V0.2"程序负责 ID、时间和落库"的分工一致，但方案没有逐项点名。

## 4. 缺口（方案未覆盖，建议在实施细化里补）

1. **别名合并规则仍未定。** 方案第 4.1 节说"更新同 key、保存历史、重算当前向量"，但没有说 `aliases` 为空时是覆盖还是沿用。上一轮 DSH 复核的 I9 就是这个问题（`organize.ts:44` 现在整体替换，空数组会抹掉旧别名，静默削弱关键词召回），V0.3 正好是最合适的落点：建议定成"新别名非空则替换，为空则沿用旧别名"，并写明"不把过时属性值无限保留为别名"。
2. **合并语义未定。** 方案说"已有同事件长期记录时更新或合并，不能再创建一份并分别累计唤醒""合并前计数迁移不能把同一天重复项相加"——方向对，但**谁赢**没写：两条长期记录的感受不同、时间不同、来源不同时，是新内容替换旧内容、按字段各自保留，还是保留两条并在检索时去重？建议按字段定规则（例如 `content` 由模型重写、`sourceIds` 并集、时间取最早事件时间、计数取较大者而不是相加）。
3. **向量归一化与两段检索的实现约定。** 方案第 9.3 节说"先用 SQL 按种类、有效期和状态筛候选，再取向量"，这已经解决了我最担心的全表加载问题；建议再补两点：入库时把向量归一化（查询侧只需点积，省掉每条的 `norm()` 计算），以及明确"每轮每任务最多一次查询向量、同一文本可缓存"。第 9.3 节第 2 点提到了缓存，但没有说缓存范围（进程内还是入库）。
4. **迁移细节只写了一半。** 第 13 节定了"旧长期统一给 90 天观察窗口""`mentions` 不迁移为 `totalAwakenings`"，这是对的，但没写：旧短期记录迁移时如何补 `expiresAt`（按 `createdAt + 7 天`？）、`revision` 从什么值开始、旧 `mentions` 字段是否保留为历史（方案说保留，但没说是否继续维护）。
5. **需要同步的文档清单没有列。** 这次改造会同时影响 `REMAKE_V0.2_MEMORY.md`（层结构、保留与唤醒规则）、`REMAKE_V0.2_INTERFACES.md`（合同、表、查询）、`REMAKE_V0.2_IMPLEMENTATION.md`（维护任务、索引待办、预算分块）、`REMAKE_V0.2_RECOVERY.md`（维护续办与恢复顺序）。方案第 14 节只说"用户审核后再形成实施细化"，建议把"哪些文档要同步"直接点出来，避免实现完只改了记忆文档。

## 6. 建议顺序

1. **先定行身份与 `revision` 规则**（3.1），以及别名合并与合并语义（4.1、4.2）——这三件是纯设计决定，定了才能写合同。
2. **再补"有效唤醒"的合同级校验与同日去重**（3.3），以及维护任务的调度槽、job 表与恢复顺序（3.4）。
3. **然后按方案第 13 节的三步实施**：先 details／长期摘要的独立索引与混合检索（能最快看到效果，也不动现有事务结构），再做七天短期与到期压缩，最后加唤醒续期与常驻候选。
4. 每一步都保留"段 B 一次提交 + 向量在事务外 + 失败不回滚故事"这三条不变量，并把方案第 13 节那七条验收补成可执行的测试名。

**边界**：本复核没有运行任何测试或服务，没有验证 Embedding 端点、模型质量或实际召回效果；第 3 节的判断来自静态阅读现有源码与方案文本。
