## 1. 逐条回答七个分歧

### 1.1 K1：`!pending.includes(...)` 在空数组下是否为 true——**是 true，我错了**

```ts
.filter(m => !pending.includes(m.batchId!) || batchIds.includes(m.batchId!));
```

`pending = []`、`batchIds = []` 时：`pending.includes(...) === false` → `!pending.includes(...) === true` → `true || false === true`，闭合未读消息**照常通过筛选**。我把它读成了"两个条件都为假"（当成 `&&`），这是在引用原文的同时没有重算——错误完全在我，且属于不该发生的错误。

补充两点，都支持你的判断：

- `storage.ts:64-66` 的 `unreadMessages()` 独立按 `direction === 'incoming'`、`seenTurnId === null` 并排除当前 `openBatch` 选取。**消息是否未被看到由消息行决定，从即时队列移除不等于已看。**
- `REMAKE_V0.2_RECOVERY.md:127` 已经写明"把已闭合输入留为未读"，我第一轮却把它当成了反证。

因此**不存在"睡眠清队列导致起床漏交付"的路径，请不要依据 K1 修改 `scheduler.ts` 的睡眠分支**。可以保留你提议的那条回归用例（真实输入 → 15 秒闭合 → 睡眠扫描清队列 → 起床扫描），它的价值是证明这条路径成立，而不是修 bug。

你顺带提到的另一件事我确认：单独删掉睡眠里的清队列操作会与 `scheduler.ts:59` 的 `pendingBatchIds.length → now` 冲突，确实要连截止时间语义一起考虑；既然结论已撤回，这一条不必动。

### 1.2 K2：是否漏掉 `wake || check` 中的 `check`——**漏了，我错了**

完整表达式是：

```ts
const check = tasks.some(t => t.kind === 'check_messages');
const batchIds = wake || check ? [...pending] : pending.slice(0, 1);
```

待看检查存在时取**全部** pending；`slice(0, 1)` 只作用于既没有起床也没有检查触发的普通输入轮——那正是文档想要的"普通入口一次取最早的新批"。我在第一轮里原样引用过这一行，却在结论中写成"只取 wake"，属于自相矛盾。**K2 撤回，实现无需改成普通输入轮也读取全部队列。**

### 1.3 K4：`closeReady` 先于暂停判断，是否足以终止同一 `readyAt` 的定时器重复——**足以，我错了**

实际次序（`runtime.ts:40-42`）：`requested = false` → `input.closeReady(now)` → 判 `paused` 后 break。定时器在 `readyAt` 触发时：

1. 打包先调 `closeReady`，到期的 `openBatch` 被移入 `pendingBatchIds` 且 `openBatch = null`（`input.ts:26-31`）；
2. 随后才因 `paused` 退出；
3. finalizer 调 `armTimer` → `nextDeadline()` 的暂停分支返回 `openBatch?.readyAt ?? null` → 此时已为 `null` → **不再排定时器**。

之后 `acceptInput` 会把 `openBatch.readyAt` 设到未来 15 秒，排的是未来时刻，不是 0。所以**不存在对同一个过期 `openBatch` 的持续空转**。我第一轮跳过了 `closeReady`，撤回。也不要为此加入统一最小等待时间——那会改变正常"立即到期"触发的行为。

### 1.4 K5：当前 ws-reverse 的默认 `responseTimeout` 是否覆盖无响应请求——**覆盖，我的说法不成立**

我核对了配置与已安装适配器：

- `runtime/koishi.yml`：`adapter-onebot` 使用 `protocol: ws-reverse`；
- `runtime/node_modules/koishi-plugin-adapter-onebot/lib/index.js:616` 与 `:659`：`responseTimeout: Schema.natural().role("time").default(Time.minute)`；
- `:688-693`：请求 Promise 在 `bot.config.responseTimeout` 后以 `TimeoutError` reject。

因此当前部署的发送路径**有 60 秒上限**，"平台调用无超时"这句话对当前部署不成立。第一轮仅依据 HTTP 模式的一般结论外推到了 WS，这是我的错误。

收窄后仍然成立、但性质不同的两点：

1. 这条上限**不覆盖其他等待点**（`d.wait()` 的分段等待、Embedding 调用、世界联网抓取）。这些都不是"发送无响应"，而是"回合耗时较长"，属于设计内的行为，不是缺陷；只是 `hdsi.status` 在这段时间仍会报"运行/发送"，使用者需要知道。
2. 素材文件缺失导致该回合反复重放同一失败：**机制描述成立**，但你的判断我接受——自动跳过会改变已冻结的输出与随后进入记忆的输入，属于产品语义决策，不应作为"自然修复"。建议只改善错误定位（例如错误信息带上素材 ID 与路径），把"是否允许跳过/替换/取消冻结项"留给用户确认。

**我没有找到其他真正无上限的等待路径。** 如果你希望彻底收口，可考虑给 `getWebMaterials` 与 Embedding 请求加各自的超时，但那属于可选加固，不是本轮必须修项。

### 1.5 K3：区分"一次不必要的即时后续轮"与"持续循环"

同意你的收窄。我读到的机制是：

- `app.ts:137` 的 `completedTaskIds` 只把**本轮能读**的检查任务算作完成（`t.kind !== 'check_messages' || canRead(state, at)`）；
- `memory/organize.ts:48-60` 默认完成这些任务，只有显式 update/cancel 才覆盖；
- 所以一个已过期的 `check_messages` 到期后会被正常处理并完成，**不会自动重演**。

要形成持续循环，需要模型反复新建或把任务重排到过去——这属于额外的模型行为条件，不能由单个过期任务推出。因此正确表述是：**"校验缺口 → 一次不必要的即时后续轮（以及可能的重复调度）"，而不是"必然无限循环"**。

约束范围我同意限定为：只对个人导演在 `taskChanges` 里 create/update 后的**最终** `check_messages.at` 要求晚于本轮 `at`，通过既有格式修补通道处理；不得扩大到"程序自己创建的过期检查非法"，也不得影响程序处理既有到期预约/检查的能力。

`organize.ts:13-18` 调用完整 `ContextBuilder.build()`，最终只把 `details` 与 `longTerm` 交给整理模型；而 `context.ts:46-52` 的裁剪作用于整个对象，并且**最先裁掉 `longTerm`**。也就是说整理模型根本收不到的历史字段（recent、shortTerm、detailHistory）可以挤掉它真正需要的长期记忆和细节。这是"喂给模型的内容可能被无关内容挤掉"的有效性问题，不是性能问题，我同意排在第一位，并且应当有一条测试证明"很长的近期历史不会无故挤掉相关长期记忆"。
