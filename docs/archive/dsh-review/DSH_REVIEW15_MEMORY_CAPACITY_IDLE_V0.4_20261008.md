## 1. 建议开工前定的六处

### 1.1〈已撤回〉~~短期退出的排序键到底是"自身"还是"关联长期"的唤醒计数~~

**本条撤回，我原来的建议会把排序弄坏。** 我核实了：`lifecycle.ts:70-76` 的 `awaken` 明确要求 `row.kind === 'long'`（`const row=this.store.canonical(input.id); if(!row||row.kind!=='long')throw …`），而 `totalAwakenings` 的**唯一**写入点是 `lifecycle.ts:85`（长期续期时 `totalAwakenings = dates.length`）。`store.ts:22` 虽然给所有 owner 初始化 `totalAwakenings=0`，但**短期行从来没有累计过唤醒日期的业务路径**。

所以按"短期自身计数"排序会让几乎所有短期都是 0、退化成按衰减和时间排——恰好丢掉"反复提及优先保留"的效果。CODEX 的结论正确：**短期用关联 canonical 长期的有效日期数排序**（用来表示这件事是否被反复提及），长期保护是另一层候选排除规则，两者不能混同；而且这不会让短期无限占位，因为短期仍在最后一次真实新进展后 7 天自然退出，只重谈／长期续期／检索命中都不延长它。

### 1.2〈已纠正〉总量与可见量：可见层不可能超过上限

我把标题写成"可见层可能远超 3000"是**反了**。正确关系是 CODEX §2.2 给的那个：

```text
普通长期占用 = 尚未可见的预备长期 + 当前可见普通长期
正常归一后 占用 <= 目标；因此 可见 <= 占用
```

可见层是占用的**子集**，永远不会超过上限。我真正想说的是"预备项会占掉一部分位置、可见层因此少于上限"——这个观察本身成立，但方向写错、也不构成"可见层失控"。按其新口径保留四个统计（占用／预备／可见／归档）即可，**不另设可见配额**。（目标也已从 3000 改为 **1000**，见下。）

### 1.3〈已纠正〉15 分钟是资格门槛，不是调用周期

我按"睡 8 小时 ÷ 15 分钟 ≈ 30 批"估算是错的。按 CODEX §2.3：**首次满足资格后，只要没有新的有效交互／故事完成、没有受保护活动或可执行前台轮，就可以逐批继续处理尚未完成的增量**；维护完成不刷新锚点，没待办时不调用模型。所以实际调用量取决于未处理版本数、每批候选量、调用耗时、冲突与重试，不能这样静态推算。

它对我"不同槽 = 无资源竞争"的纠正也对：世界／学校链与后台准备确实用不同执行槽、在途请求可与 06:00 环境链并行，但 `Host.pump` 是**先处理到期前台、随后才申请新后台准备或应用单元**，所以仍要让位。

### 1.4〈已纠正〉保护对象不额外占用容量

我写"长期池有效容量长期比上限少约 100"是重复扣减：那 100 个受保护长期**本来就计在 1000 里**，已经可见的受保护项就是可见容量的一部分，不能再从 1000 里减掉。CODEX 的说明正确。

### 1.5 短期提前退出时，初始 grant 的锚点该往前还是往后

§5.1 第 3 条："对尚未生效的普通预备长期，保留起点改为实际退出详细层的时刻，并同步原预备初始 grant；90 天从这个新起点计算。"

现在的规则相反：`lifecycle.ts:36` 在"生成时刻早于 `retainedFrom`"时把锚点**推后**到 `short.shortExpiresAt`（即 +7 天），并重算 90 天。而容量退出发生在 7 天**之内**，所以按"实际退出时刻"是把锚点**提前**——这与既有规则方向相反，但恰好是 §5.1 第 2 条要的效果（"避免详细记录退出了、摘要还要再等几天"）。

我读下来认为方案想要的是**提前**（day 3 退出 → 摘要 day 3 立即可见、90 天从 day 3 起算）。但因为既有代码的同类分支是往后的，实现者很可能沿用旧方向，导致第 101 条进来后出现"短期没了、长期还没到可见期"的空档——正是 §9 验收场景 1 要防的。

建议写死一句："短期因容量提前退出时，预备长期的 `retainedFrom` 与初始 grant 锚点**改为实际退出时刻**（该时刻必然早于原 `shortExpiresAt`），`expiresAt = 新锚点 + 90 天`；§9 场景 1 的'不会产生几天无记忆的空档'以此为准。"

### 1.6 §4 的伪代码没有覆盖它自己列出的全部排序层

§4 的排序列表有 4 层（保护身份与普通重要度优先 → 唤醒日期数升序 → 衰减比例降序 → 时间与 ID 决胜），但下面的伪代码只给了 `lastMeaningfulAt / decayRatio` 的算法，**没有表达前两层**。建议把完整次序写成一份可直接实现的规则，例如：

```text
1. 排除受保护身份（§3.3）
2. importance: 'normal' 先于 'high'        ← 当前伪代码未包含
3. totalAwakenings 升序
4. decayRatio 降序
5. lastMeaningfulAt 升序 → happenedAt 升序 → createdAt 升序 → id 升序
```

现有 `importance` 的取值就是 `'normal' | 'high'`（`memory/types.ts:8`），所以第 2 层可以直接落地；把它漏在伪代码外，实现者很可能只写第 3-5 层，而"普通重要度先于 high"恰恰是 §9 场景 3 明确要验收的（"刚提取的重要一次性经历优先于普通琐事"）。

### 1.7 空闲锚点必须点名"哪些完成算、哪些不算"

§6.1 列举了 5 类时刻，但现有系统的对应物已经变了：

- 环境／学校轮在 V0.4 里**不再产生 `TurnRecord`**，而是 `environment_steps`（`environment/runtime.ts:41` 写的是步骤状态，不是轮完成）；
- 索引与维护的完成也各有自己的 job 状态（`memory_maintenance_jobs`）。

所以"最近一个**非环境**故事轮 `completedAt`"这句必须配一份明确的写入点清单：哪些事件会写这个锚点、哪些明确不写（方案已列"计划开始、未发草稿、世界／学校仅写客观安排、索引或维护自身完成"不算，很好）。建议再补两点：

- **环境步骤的 `completedAt` 绝不算**（否则 06:00 的链会每天把空闲窗口推到 06:15 之后）；
- 受保护活动的"开始／实际结束"锚点写在哪张表上（现有 `Scene.shared` 的 `sharedClock` 只管共同活动，普通 `scene.activity` 没有起止提交点）。

## 2. 两处小项

### 2.1 `refine`／`merge` 合同对"短期"是空转的

§7.1 说"当前 consolidation 的 merge 合同只支持至少两个长期主身份；将短期重复项合成一个详细主记录需要新增正式合同"——这句核对无误（`contracts.ts:161` 要求 `ids` 里至少两个 `long`）。但还有一处方案没提到：

`maintenance.ts:94` 的 `refine` 分支写作 `rows.filter(r => r.kind === 'long')`，**短期行会被静默跳过**；而合同又要求"短期带 `linkedLongId` 时 `ids` 必须同时含该 long"（`contracts.ts:159`）。合起来是：**当前没有任何路径能改进一条短期记录的摘要**。

这直接影响 §5.1 第 4 条"空闲后可改进简要摘要"——那句话描述的时机在长期层是可行的（`refine` 走 long），但如果方案期望改进的是短期原文，就需要新合同。建议在 §7.1 点明，避免实现时误以为现有 `refine` 能覆盖。

### 2.2 索引与深度整理共用一个槽时的优先顺序

§6.4 说索引"不必满 15 分钟"、§6.2 说"一次背景请求最多一个，与索引共用已有槽"。两者同时可行时谁先？建议写一句（例如"索引待办优先，因为它不影响事实认定且无需门禁"），否则实现者会各按各的理解排，表现为"新记忆的向量时快时慢"。



§3.3 的保护规则是"仍服务于活跃短期的关联长期先保护"，§3.4 又允许临时超量并逐单元处理。若短期池长期满载（100 条），其关联长期就一直是 100 条受保护对象——这不构成错误，但会让"长期池的有效容量"始终比 3000 少约 100。建议在细化里说明这只是常数级占用，不额外处理。

## 4. 针对新要求（100／1000／500 + 真实清理）的两点提醒

CODEX 本轮把用户的最新要求并进来了：普通长期目标 **3000 → 1000**，新增**有限归档池 500 个 canonical 主身份**，且归档也有 90 天出口、超量时**真实删除**（含正文、向量、唤醒、grants、派生 job 数据）。这比原方案严格得多（原方案是"归档会继续占磁盘、不声称磁盘封顶"），方向我认同——但它引入了两类**悬空引用**和两个执行细节，建议在细化里写死。

### 4.1 清理一条长期时，指向它的短期的 `linkedLongId` 会悬空

现有代码有三处依赖这个指针：

- `contracts.ts:159`：`refine／discard／merge` 对带 `linkedLongId` 的短期要求"该 long 必须在同一个 unit 的 `ids` 里"；
- `maintenance.ts:24-25`：挑选候选时会把短期关联的长期**补进快照**；
- `lifecycle.ts:102`：合并长期时把 grants 迁移到主身份。

如果被清理的长期**还有活跃短期指向它**，上面三处都会拿到 `undefined`——合同校验会以"linked long 不在 unit 里"的形式失败，或快照里出现空位。§4.4 只说了"仍被正式引用的身份按保护规则另行处理"，但没有点名**短期指向归档长期**这一情形（短期是活跃的，长期已在归档池等待清理，两者可以同时成立）。

建议明确：清理一个长期身份时，同事务内**先处理指向它的短期**——要么该短期也退出（它的 7 天本来也在走），要么把 `linkedLongId` 重指到合并后的主身份；并且"仍被活跃短期引用"应该在 §4.3 的排除清单里被显式列出。

### 4.2 删除 owner 后，"在途／ready 的维护单元"需要显式判存活

`maintenance.ts:77` 的冲突检查是 `unit.readSet.every(ref => this.store.owner(ref)?.stateVersion === ref.stateVersion)`。**owner 被删除时 `?.` 返回 `undefined`**，于是 `undefined === 数字` 为 false → `valid=false` → 单元被记为 `stale`。这一步是**幸运地安全**的（会走 stale 分支）。

但 `maintenance.ts:89` 是另一回事：

```ts
const rows = unit.ids.map(id => job.snapshot.find(r => r.id === id)!).map(r => this.store.owner(r)!);
```

这里对 `owner` 用了非空断言。若某个 `unit.ids` 指向已被清理的身份，而 `readSet` 恰好没有覆盖它（合同允许 `ids` 与 `readSet` 不完全重合），`owner(r)` 返回 `undefined` 后**会在应用阶段抛错**。§4.4 说"涉及已清理 owner 的正文快照也要退出持久化留存""已清理的 ID 不能被旧后台结果重新写回；owner 不存在视为该单元过时"——方向对，但建议在细化里直接写成两条可验收的规则：① `:89` 前先判 `owner` 是否存在，不存在按 `stale` 处理；② 删除时同步裁掉在途 `memory_maintenance_jobs.snapshot` 里对应的项。

### 4.3 两个执行细节

- **`job.snapshot` 本身保存着完整的候选正文**（`maintenance.ts:27`：`snapshot` 是 `MemoryCandidate[]`）。所以"清理记忆数据"必须包含 job 快照中的对应项，否则删了 `memories` 行、正文仍留在待办里，"真实清理"就没有生效。
- **删除要跨 6 个数据面**：`memories`／`memory_awakenings`／`memory_retention_grants`／`learned_background`／`memory_index`／job 快照，其中后四个是各自建 DDL 的专用表（`storage.ts:17` 的通用表注册只含 12 张基础表），不能用 `storage.remove('memories', id)` 一把删掉。建议在细化里列出这张"删除面清单"，并明确"同一事务 + 已删 ID 不可被旧结果写回"。

### 4.4 新口径下我保留的两条观察

- **归档清理的触发条件建议写成"两个条件都满足才删"**（超过归档 90 天**且**归档池超 500），否则可能出现"某条刚进归档、因池满而立即被清"，用户就没有 90 天的找回窗口了。§4.3 的"先清超期、仍超 500 再按排序删"已经接近这个意思，只是没写明"未超期的条目在池满时也要删"这一点——建议直接说明它是有意的（池满优先于 90 天保护）。
- **`importance` 层在归档清理与活跃退出里的顺序是相反的**（活跃池先保 high；归档池把 high 排在唤醒数和时间**之后**）。这是有意的设计，但两处排序放在一起看容易被实现者写混，建议在细化里并排放两张排序表并注明差别。

**没有做**：运行测试／构建／demo；连接模型或 QQ；检查正式库；修改任何文件。

**因此无法验证**：100／3000 这两个初始值是否合适（依赖真实新增量与提前转层频率，方案自己也说"不能仅凭月数推定"）；空闲 15 分钟在真实使用节奏下的观感（是否会出现"刚想聊天就被后台占用"）；以及睡眠例外下整夜连续整理的模型费用。这些都需要真实运行数据，静态复核不能替代。

**给用户的一句话**：方案的三个可调项（睡眠是否沿用后台例外、是否采用归档而非删除、100／3000 是否作为初始目标）我建议全部沿用方案默认——它们彼此自洽，而且方案已经把"以后要改"的入口（`null` 关闭容量、睡眠例外可取消）都留好了。
