## 3. 需要修正或补全的建议

### 3.1 空摘要：保护是第一步，不能当作完整清理修复

DSH的保护建议采纳，但“保住空摘要不占有效容量”不能等同于“不占池子”：当前空正文不影响longOccupied／longArchive的身份计数，受保护项仍可能带来可见差额。保护目的应是避免悬空和丢失记忆层内唯一详情，不能依赖空正文自动不计数。

当前§5.2要求先有摘要再清short，故不能直接删唯一详情；但仅保护long也不会保证以后必有用户重谈或模型refine。建议后续修复同时包含：

1. 新基础记忆结果的eventSummary／feelingSummary合成后至少有一个非空白内容，空摘要通过既有格式修补重试；这不是字数／token上限，仍允许一侧为空。
2. 对已存在的到期阻挡short，保护其仍存活的canonical long，保留明确missing_summary状态，不从维护now给事件续期。
3. 把可修复项登记到增量事件整理，使用存活short详情及合法历史来源，请模型生成非空简要摘要；仍受15分钟／活动门禁和正常重试。同版本不能反复排空转任务，已经没有合法身份或来源的项明确阻挡，不凭空补造。
4. 摘要成功后，沿原清理入口先删到期short及派生副本，再按原归档锚点判断long；不复制short全文到long，也不重扫原始日志重建旧记忆。

至少验收到期前／到期后保护、超量／超龄long不先删、一次合法摘要修复后详情与派生副本真正清空、未修好时无0ms循环。是否修复成功应以这条闭环验证，不能只看long还存在。

### 3.2 晋升：归档不是status='archived'，不能靠active筛选排除

普通归档仍是`status='active'`，由archiveStart判定。故DSH“promotionCandidates的active条件说明本意排除归档”不成立；该SQL目前确实选出归档30次项，已复现。风险路径成立，不需要这条推论支持。

另“500条归档正好是30日期门槛最容易命中的群体”缺少实际依据：容量排序本来就优先挤出较低唤醒普通项，不能据此推算大量归档晋升。应修合法性边界，但不放大发生规模。

现规范分别说“真实awaken才能恢复普通长期”和“30日期进入常驻审核”；从普通层转常驻层是否允许跳过真实恢复，之前未单独写死。**用户现已确认B：必须先真实重谈恢复活跃，再允许晋升常驻。** 这与有限普通记忆、真实重谈恢复的方向一致，不新增后台直接复活通道。

落实B时，不建议只在lifecycle.promote里throw：ready的冻结promote结果会进入应用失败后的5分钟重试，反复重试同一份结果。应同步：候选与模型输入不给已归档主项晋升资格；合同按冻结评估时间检查；应用按当前时间再次检查，准备期间自然归档则判stale并重排合法工作，其他单元继续。Lifecycle作为最终收口也禁止归档直接晋升，但不能让正常调度变成无限重试。

这只限制本次被晋升的主long，不自动删除既有learned，也不否定多个真实历史事件可作为稳定认识证据的既有规则。该产品规则已经确认；本轮只记录，尚未修改源码和实施主文档。

### 3.3 保护不延长归档窗口

采用DSH§4.5的第一种解释：到期short先清理、long后删除；在原7天内暂存的short使long暂缓删除。long的归档起点仍为真实容量退出／自然到期锚点，不能从short清理截止再加90天。

不把normalize改成一律保护全部暂存short来延后归档，那会改变活跃1000的归一资格。只需在细化补一句“删除保护不改变归档起点；保护解除时若已超量／超龄即继续清理”，并补对应回归。摘要缺失的引用保护是§4.3要修的实际缺口，不能用本条的正常截止口径掩盖。

### 3.4 LIKE：已经参数化，仍要字面身份匹配

`DELETE ... WHERE id LIKE ?`已经参数化；参数化不转义LIKE通配符。`_`是普通字段key中容易出现的字符，已复现删除其他对象报告，建议同批修正。

可精确匹配目标身份对应的固定decision报告ID，或用字面前缀比较；若沿用LIKE，须转义`_`／`%`并指定ESCAPE。不要再加一层参数化就宣称修复。无需添加通用SQL防御框架。

## 4. 低优先项与只读核对

正式库三张owner表目前都为0行，三组跨表ID交集均0；不存在本次可观测的缺kind或long缺retainedFrom记录。空表的SQL SUM输出null代表没有行，不是有异常。此检查只排除当前正式空库的问题，不能保证任何未来导入库都没有冲突。

- 跨表ID冲突、缺kind、缺retainedFrom：本轮无实际数据触发；有新迁移输入时再针对来源校验，不因空库检查扩展一套修复框架。
- merge_short跨long的同事件判断：现规范已允许，由模型语义判断；不新增语义裁判或线索ID。重复ID是另一个合同缺陷，应单独修。
- 预备摘要被挤出后计入归档：有意，1000包含preview，存活的退出普通身份统一进500池。无需新产品决定。
- 未完成turn的全局门禁：现阶段保守保护与单Host恢复一致；不缩小到更多并发清理范围。
- 空闲／同步异常防御、asset不可达checkpoint、at未使用、暂时陈旧status等：没有定位到新的常规业务失败，暂不加防御性改造。
- 决胜ID序、learned历史status、读截止写共享节点等：保留核对备注，不凭可能性宣称当前交付错误；目前也不新增产品规则。
- 性能：冗余排序已实测，可优先考虑“有超量才排序”及单次排序复用唤醒元数据。未证明影响正常聊天，不把整套性能重构作为本轮修复前提。
- 页面正文业务留存是明确设计；100／1000／500仍不是整个数据库文件大小上限。

## 5. 建议后续修复验收顺序

1. 重复short ID／不同有效身份不足两项：合同与应用拒绝，正常同事件合并仍通过。
2. 生产入口的同平台消息重复投递：普通消息及【推进】均只接纳一次，不刷新idle／批次／共同活动计时；无平台ID的不同输入不误去重。
3. 空摘要合同及已有阻挡项：先保护、合法整理后先清short、再按原期限删long；向量、job、dirty、快照清理完整且无零间隔循环。
4. 按用户已确认的B规则，覆盖容量归档／自然到期、准备到应用间越过期限、stale后其他单元继续；不能用throw＋同结果重试代替资格处理。
5. 审计key含`_`／`%`只替换本目标报告。
6. 同步细化／计划／过程记录，相关回归、全套检查和隔离混合验收后再交付。无需重新选模型、Embedding或启动服务。
