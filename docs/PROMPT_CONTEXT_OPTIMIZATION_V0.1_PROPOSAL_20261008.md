## 1. 目标与结论

本轮目标：核对所有模型输入位置，减少同一次请求内的重复内容，按阶段整理必要资料，把程序能够确定的权限与结构规则提前计算，再向模型发送适用的提示词。保留模型对生活、叙事、情绪、意愿和语义的判断。

沿用已确认边界：输入字符预算、检索条数上限默认不限；保留相关性筛选与最近原文窗口；接口超限仍报错，不自动裁低相关记忆。不以“优化”为由减少记忆保存期限、改变容量清理规则或强制每条消息都回复。

结论：有明确优化空间，优先做“相同内容只放一份、程序已知条件只给当前分支”。不建议先让另一个模型把全部上下文再摘要一遍，也不建议把主叙事、个人导演、表达和记忆整理合并成一次调用。

主要发现：

1. 主叙事同一次请求内重复发送整个最近消息数组：`recent` 与 `history.recent`。
2. 表达阶段直接收到个人导演的整套 `history`，包括短期／长期记忆与细节，任务范围却主要是草稿润色。
3. 网页正文同时进入 `webMaterials` 与 `webResults[].materials`；续调用还会携带累计工具结果。
4. 检索返回完整持久化 owner，存在正文与摘要、`content/value`、身份及后台状态字段重复；不是向量泄漏，向量已在序列化前排除。
5. 共同活动代写权限已使用程序分支；主动联系、模式、轮次和可用工具等仍可进一步分支化。
6. 背景拆分尚未在生产入口应用；当前仍读作者背景全文，部分固定细节重复出现。
7. 实际语义召回阈值尚未标定，当前 `semantic=null`；检索路径仍可能先请求查询 embedding，再发现不能使用向量结果。

## 2. 现在一次对话实际输入什么

普通可运行故事轮大致为：主叙事补生活 → 个人导演反应／决定是否回复 → 有已选草稿时表达 → 确认发送后提取记忆。睡眠等原有门禁及不需要个人反应的轮次存在例外；本方案不改唤醒流程。

### 2.1 主叙事

输入完整 `background`、补生活的 `from/at`、角色状态、当前世界事件、客观学校实例／本轮可交付通知／已有认识、到期个人任务，以及检索历史。普通主叙事不接收本轮尚未看见的新私聊正文；共同主叙事才显式接收本轮共同输入。

检索查询主要来自当前计划、场景、任务及世界事件，共同模式再加入共同消息。因此主叙事与个人导演检索结果未必相同。

### 2.2 个人导演

输入完整 `background`、补生活后的状态、新经历、当前真正可见的用户消息、延期复议的旧消息、到期任务和全部待办任务、角色已知学校资料、环境事件及本阶段检索结果。

`history` 包括：

- `recent`：默认最近 **30 条消息记录**，不是30轮对话；角色分段回复可能占多条。只纳入 outgoing 和已标记看过的 incoming，未读新私聊不会因历史装配直接泄漏。
- `shortTerm`：相关且有当前活跃资格的短期详情，不是固定取最新几条。
- `longTerm`：相关且当前可见的普通长期摘要。尚未进入可用时间的预备摘要不直接进入普通检索。
- `details`：按明确 key／别名或相关性命中的具体事实，不是把所有细节一次全发。
- `learned`：按相关性命中的常驻内容，以及全部 `alwaysInclude` 常驻稳定认识；后者不要求相关命中，当前没有800字符配额。
- `detailHistory`：请求和权限允许时，检索命中细节的旧版本。

当查询明确涉及回忆或旧事实时，现有程序允许相应归档／历史查询。没有“每轮一并发送全部短期和长期记忆”的行为。

当前本地配置：`historyBudget=null`；候选路、短期、长期、细节条数与常驻字符限额均为 `null`；`recentMessagesLimit=30`。**默认不限数量并不等于不筛相关性。** 后续建议把这项30条窗口替换为§7.5的4个对话段，不把两种窗口叠加使用。

补充实际状态：生产检索模块支持 Qwen 查询向量与词法融合，但所用标定文件 `runtime/data/memory-retrieval-calibration.json` 的 `semantic=null`。目前不能称为“已通过语义向量召回相关长期记忆”；实际相关召回靠确定 key／别名和已标定词法入口，查询向量尚未成为语义召回依据。启用语义路需要单独标定，不在本次检查中联网完成。

### 2.3 表达与记忆整理

表达目前不直接接收完整 `background`，接收 `intent`、模式、角色状态、已知学校资料、当前可见消息、整套个人导演 `history` 和聊天范例。

基础记忆提取接收完整 `background`、本轮经历、首次可见消息、复议消息、实际已确认 outgoing、计划意图区、相关 details／retrieved、学校已知资料，以及生活个人导演本人网页查阅来源及材料。它不把整套最近30条原文作为独立 recent 数组发送。

核心装配证据：[app.ts](../src/app.ts)、[retrieval.ts](../src/memory/retrieval.ts)、[context.ts](../src/memory/context.ts)、[organize.ts](../src/memory/organize.ts)。

## 4. 重复的性质与建议

### 4.1 同一次请求中可确定去重的内容

| 发现 | 当前证据／表现 | 建议 |
| --- | --- | --- |
| 两份最近消息 | `app.ts` 的narrativeInput同时带recent及完整history，二者最近消息数组相同 | 只保留history.recent或统一消息池，避免两份全文 |
| 到期任务与全部任务 | 个人input的dueTasks是tasks的子集 | 一份任务正文＋dueTaskIds，语义不变 |
| 复议原文与最近原文重叠 | 复议消息已看过，可能也在history.recent | 以消息ID去重，保留recent／reconsider角色标签。新visible首次未读时通常不在recent，不能声称每次都重复 |
| 共同状态字段重复 | state.scene.shared与显式outline、publicNarration、meta／remainingSteps部分重叠 | 共同状态用一份权威视图。当前publicNarration=null与历史lastPublicNode有不同含义，不能强行合并成同一值 |
| detail正文重复 | owner的content与value通常相同 | facts视图只保留一份有效value及key／别名／必要来源 |
| long摘要重复 | 常见content就是eventSummary＋feelingSummary，整个owner仍同时发送三者 | 检查确定相同时只展示结构化事件／感受或合成正文之一；不相同时保留额外内容，不能假定所有长期正文都可重建 |
| 网页正文重复 | transport同发webMaterials及webResults[].materials；后者又是累计工具结果 | 每次请求正文按materialId一份；工具结果仅保留materialIds、计数、不足／错误／停止原因等元信息 |
| 补查与初始资料重叠 | lookupResult可能重新包含原input已有事实／记忆／recent | 相同ID及版本只展示一份；确有新版本／新增资料明确标记，不改变补查返回的合法可写ID集合 |
| 共享公开内容重复 | 基础记忆同时有已发送outgoing，以及sharedPublicExperience中的同轮裸旁白／代写动作 | 保留原始outgoing作为合法来源，代写解释标注引用对应outgoing ID；若格式规范化展示，不能丢原文与公开依据 |
| 本人网页材料关联重复 | selfWebReadMaterials按source逐条映射完整material | 材料表按materialId唯一，selfRead source保留自身ID、时间与材料关联；不创造新的记忆来源ID |

去重依据优先是消息ID、owner类型＋ID＋版本、materialId及已确认来源身份；不以两段自然语言“看起来差不多”就合并。短期详情、长期摘要、常驻认识即使指向同一事件，也承担不同职责，不能随意只留一个。

### 4.2 owner模型视图，避免直接发送整个持久化对象

`memoryOwnerData`已剔除normalizedVector，当前没有把1024维向量发送给生成模型。问题是它仍保留大量应用／后台字段：ownerType/ownerId/id/kind、期限、版本、合并及容量状态、整理标记等，许多还为null。

建议增加按任务的显式模型资料视图。叙事／个人／表达只拿可理解内容、必要ID、事实时间及当前依据；固定认识保留learnedKind、canonical关联及projectionBasis等影响解释的内容。普通对话无需自行判断容量、期限或版本有效性。

基础提取仍须看到可更新short、可明确唤醒long、detail key及合法当前来源；空闲整理必须有完整语义证据及相关对象身份。Host继续保存原完整snapshot、revision/stateVersion、readSet和应用时校验，不能通过缩小模型视图缩小事务证据集。模型只引用ID，Host可从冻结snapshot重建必要版本。

### 4.3 跨任务／跨HTTP重复不能一概删除

当前每次HTTP请求都是重新构建system和user两条消息，没有把整轮聊天作为供应商端永久会话追加。换阶段、补查、修补及网页续调用都不能假设模型记得上一次HTTP内容。

因此，主叙事、个人导演和基础记忆都拿背景，有一部分属于独立任务的必要重复；个人导演看到主叙事经历是职责交接。最近原文与已整理记忆的并存，也分别提供精确措辞与事件认识。优化应先删除同次请求内的副本，再确定各阶段究竟需要哪些内容。

网页续调用仍应带该阶段可用的正文各一份，不应只发本次新增网页然后依赖不存在的远程上下文。修补仍带原任务资料、当前错误及待修原响应；若待修原响应恰好是全文副本，可统一引用，但不能通用地删掉它。

`response_format=json_schema`时Schema同时出现在system文字和response_format；当前默认json_object则没有这处双份Schema。后续可在已验证可用的json_schema模式下只保留结构化Schema及短输出要求，不在所有接口模式中直接取消提示Schema。

## 5. 哪些判断交给程序，哪些继续给模型

### 5.1 已由程序处理的条件

- 选普通／共同主叙事，聊天／生活／共同个人导演；决定是否调用表达。
- 私聊在本轮是否可见、哪些是复议消息；睡眠、活动手机权限等已有门禁。
- 共同轮号、phase、硬上限、倒计时、手动推进；约10轮收尾是叙事软目标，不是新的硬门禁。
- 共同主叙事代写提示二选一；冻结后修补／恢复仍用同一分支。
- 空闲整理／审核的kind；晋升合法候选；网页工具是否可用、剩余20／40额度及本地补查是否已使用。
- 时间区间、ID合法性、来源、版本、Schema及很多控制字段已有程序校验。

**代写权限的准确现行口径**：`selectSharedMeta`以“本次选中的待处理真实用户输入为空”固定allowSimulatedUserActions；角色上轮实际输出参与60秒静默计时。不是拿全部历史incoming/outgoing是否非空判断，也不预测本轮稍后个人导演是否会说话。`【推进】`是控制而非用户剧情输入。新输入在选轮后到达沿既有规则留给下一轮，不在修补中翻转本轮权限。该口径已写在共同活动细化中，本期建议保持。

证据：[shared.ts](../src/host/shared.ts)、[narrativeTask及personalTask](../src/model/contracts.ts)、[冻结代写提示](../src/model/prompts.ts)。

### 5.2 建议进一步程序化

| 条件／字段 | 程序如何决定 | 模型仍负责什么 |
| --- | --- | --- |
| 共同输入代写权限 | 保持已有冻结boolean，提示只选允许或禁止块 | 被允许范围内的活动动作与结果 |
| 线上／线下模式 | 用固定入口mode；表达用实际outputMode，包括刚开始的活动模式 | 相应方式下自然交谈／表达，不自行挑模式 |
| 首节点／wrap_up／final | 本轮固定stepNumber/phase；首节点及final要求可以同时成立 | 开场和收尾怎么写，故事何时合理提前结束 |
| 能否共同结束 | final必须end；无本轮非空旁白则不能本轮end，提示及Schema固定对应分支 | 非final且有公开旁白时是否应结束、是否确实已公开合理收尾；非空旁白本身不证明收尾语义 |
| 主动联系资格 | 当前程序已有contactEligible；将它传入task生成器。false分支只允许contact.willing=false，同时保留发送层门禁 | 有资格时是否愿意分享、分享什么；不得改成有资格必联系 |
| 工具可用性 | lookup已使用／本阶段禁止则不提供相应指令；web未配置／耗尽不提供调用Schema和邀请使用的指令 | 有权限时是否需要搜索／查本地事实；结果不足时可保留未知／向用户询问 |
| 摘录来源资格 | 固定本轮source集合和角色本人查阅集合；旧复议／检索只作参考 | 哪些内容值得记、是否真是新进展或真实重谈 |
| 没有合法新来源 | experiences、首次visible、已确认outgoing、本人selfRead全部为空，可返回合法空记忆结果 | 有合法来源则仍判断有无值得记的内容，不能因角色沉默就跳过经历提取 |
| 维护修复／晋升资格 | 预计算缺摘要修复对、promotionEligibleIds及各owner结构可用动作 | 生成摘要；同事件合并、是否可形成稳定认识等语义判断 |
| merge_short主short身份 | 模型选定同事件成员后，程序按createdAt及ID排序算canonicalShortId | 确定是否同事件、选哪些short合并、保留哪些细节与感受 |
| 学校实例／默认提醒／周覆盖 | 现有requiredOccurrences、defaultPolicy、sourceVersions/checkedAt本就程序计算；可移除模型机械抄写部分 | 学期／组内合理安排、自然通知正文、必要冲突说明 |
| 语义查询embedding是否有用途 | 阈值及配置签名不合格时不请求；空有效查询或无可能参与语义的候选可明确跳过 | 标定完成后的正常相关性查询；不改变后台索引生成的用途 |

主动联系当前边界：personalTask没有接收contactEligible参数，Schema仍接受willing=true；提示要求false，而app另用contactEligible阻止发送。没有“无资格也实际发出主动消息”的结论，优化价值在于把提示要求变成程序确定的输出空间，减少无效推理和不一致结果。

### 5.3 不能机械接管的判断

应继续由模型完成：是否回复、情绪及下一步意愿；邀约是否确实双方确认；经历是否同事件、有没有新进展／真实重谈；通知是否在模拟经历中真正看到；科研是否进行了合理过程、结果和反馈；公开正文是否真正完成叙事收尾；goal/endingCondition语义是否漂移；固定认识是否与新证据冲突。

程序可限制可选对象、来源、时间和权限，并校验结构，但不能用几个关键词、字符串相等或单纯时间间隔冒充这些语义判断。权限已由程序授予也不等于强制模型使用该权限。

## 6. 提示词建议结构

采用可组合的少量提示块，不为所有boolean排列组合生成大量模板：

1. **基础协议**：当前任务职责、动态资料解释、自然中文及JSON输出约定。
2. **任务职责**：主叙事／个人导演／表达／记忆／世界／学校／看图各自的规则。
3. **冻结条件块**：代写允许／禁止、线上／线下、当前轮次阶段、主动联系资格，只提供本次适用分支。
4. **实际能力块**：本地补查和网页能力、结果不足处理；由真实tools及已有材料决定加入哪些内容。
5. **业务语义约束**：不把计划当已发生、不把公开资料当亲历、共享代写不推成现实用户稳定属性等，与适用任务绑定。

当前common把currentScene/activity、既有属性补查等规则也加给看图、世界、学校、空闲整理；Transport还给所有阶段追加“表达仅润色”和projectionBasis说明。这些无关规则可移到对应任务。记忆整理明确不做本地补查，却仍收到common的lookupDetails要求，尤其应统一能力与提示口径。

保留少量有作用的重复：JSON输出要求与结构Schema分工不同；职责与不可越界的语义约束需要模型理解，不能因为还有校验器就全部删去。程序规则负责固定可用空间，提示负责让合法输出仍自然且正确。

格式修补、网页／本地补查续调用使用同一冻结决策及任务名，保留原模型与思考强度，不另按新到消息改变权限。现有expression“通常1～25字，语义完整优先”是软风格提示，不是模型输入预算；后续可改成自然短句表述，QQ实际分段／动作格式约束继续由输出模块处理。

## 7. 各阶段上下文改造建议

### 7.1 统一资料池，再按任务投影

先依据阶段可见性取资料，再在该阶段内部统一身份：消息正文一份＋recentIds／visibleIds／reconsiderIds；任务正文一份＋dueTaskIds；记忆按owner身份及版本一份；网页正文按materialId一份。模型可见资料池必须先满足当前阶段权限，不能先把本轮全部消息放公共池再希望模型自己不看。

既有字面身份、当前／旧来源、已确认／拟发送、意图／经历等标签要保留。不同版本／不同时间角色认识不能为了去重强行覆盖。只在资料副本确定相同且用途可用引用表达时合并。

首批可以先去掉明确重复字段，不立刻同时改所有input合同；后续定义NarrativeContext、PersonalContext、ExpressionContext、MemoryExtractionContext和EnvironmentContext等显式视图，保留现有任务名与模型配置。

### 7.2 表达专用上下文

建议保留：已确定intention/draft/actions、实际模式、当前情绪、必要场景、当前对话及相关近期措辞、聊天范例／明确表达风格，以及解释草稿所需的已知事实。

学校只给已知且与当前草稿相关的资料。全套短／长经历、无关学校快照、下一自主时钟、睡眠安排等不必默认整包继承。相关事实筛选不是按固定条数截断；拿不准某项是否影响草稿时保留，不能靠窄关键词筛掉约定、否定、时间或称呼。

该改造需单独检查说话风格及信息保真，不能仅凭JSON变短就宣称更好。保留表达阶段网页核验能力，但不允许它引入新故事事实。

### 7.3 背景分层

当前backgroundFile仍为`梁思璃设定.txt`，本地字符串长度4070（包含换行，以UTF-16单位计，不是token）。配置有16项初始details，其中4项value全文字面出现在背景中；这是静态重叠证据，不表示这4项每轮都被检索，也不是全部语义重复的统计。

现有prepareCharacterBackground只输出审阅候选，不改变生产入口。建议后续形成明确来源映射：

- 角色核心：身份、性格、关系、价值观和长期生活约束，主叙事／个人导演保留。
- 表达风格：说话习惯及范例，用于表达。
- 世界／校园／课题组身份资料：相关导演使用，保留既有导师、方向、培养阶段等，避免因摘录漏项重新发明身份。
- 可变／低频具体事实：手机、室友专业等进入details，按相关性检索。需引用作者原文及对应key，不自动改写作者设定。

同一当前事实由details负责后，应从生产core移除旧副本，避免换手机后全文背景仍给旧值。作者源文件继续保留；正式拆分需先审阅映射和候选文件，不在本次自动删段。

### 7.4 世界学校资料收窄与机械工作移交

当前world／campus／group共用环境input构造；world也会拿全部学校plans/items与角色全文。建议各stage单独投影资料。校园／课题组保留自身持续计划的必要完整结构，以能更新旧ID；历史研究progress只在相关任务更新时汇入，保留事件出处，不把既有成果删成仅最后一句。

周计划当前要求模型复制requiredOccurrences的key和上游revision，这些都是程序已算好的内容。建议后续由程序生成instanceChanges并沿现有resolve／历史保护路径保存，模型仅生成按程序固定声明实体的通知正文和必要说明。覆盖sourceVersions/checkedAt继续程序保存；提醒默认值继续defaultPolicy。

这会改变学校模型返回合同和旧ready／恢复兼容，属于第二批接口改动，需要细化验收后实施。取消课次、after历史后继key、时区、提醒一致性、未读／已知边界全部沿现有规则，不借精简重设计日程。

只有在确定没有必需通知、实例机械工作可程序完成、也没有待模型解释的变化时，才考虑省略school_week模型调用并仍提交覆盖。不能仅因上游hash未变就跳过每日世界、校园或课题组检查：时间、科研进展、预约与外部环境仍可能改变。

### 7.5 最近原文按对话段保留，默认4段

**建议采纳用户方向。** “一次持续交谈，结束后15分钟没有新交互”比按30条记录更符合上下文连续性。角色一条回复拆成6条，不应导致可见历史比只发1条时缩短6倍。

为避免与现有概念混淆，名称用“对话段”（`dialogueEpisode`），不用现有`TurnRecord`的故事执行轮：一次对话段可以包含很多次主叙事／个人导演／发送／记忆提取，也可以包含一整场共同活动。段的开始与结束由程序记录，不让模型返回“这轮对话是否结束”。

#### 保留窗口

- 默认总计4个对话段：有当前正在进行的段时，保留**当前完整段＋最近3个已结束段**；没有当前段时，保留最近4个已结束段。不是“4个历史段再加当前段”。
- 段内原文完整保留，不再在最后额外截30条，也不加每段消息数／字符数限制。连续聊天几小时仍是一段，可以包含较多原文。
- 最近段按实际交互顺序选择，再在各阶段按现有可见权限投影。当前只含未读消息、尚无本阶段可见原文的段，不挤占该阶段的4段历史名额；当前新消息仍由visibleMessages单独授权，不能因为需要完整段就泄漏给普通主叙事。
- 原文退出最近4段，仅表示不再默认加入recent，不删除messages、经历或记忆，也不缩短短期／长期期限。更早的相关事件仍由既有记忆检索提供；本期不承诺新增对全部旧原文的语义检索。
- 这仍是明确的近期窗口，不是恢复字符／token预算。接口超限沿原报错流程，不能暗中裁掉长对话段。

#### 15分钟计时

普通对话用双方最后一次真实交互的时刻：用户发言／动作消息的实际接收时间，或角色公开输出的实际发送确认时间。输出包括构成对话／共同剧情的文字、动作、旁白和表情；分段发送以最后一项确认计时。草稿、发送失败／未确认输出、系统状态／错误通知不刷新。

新交互在空闲15分钟之前发生则继续同一段并刷新计时。空闲达到15分钟后，该段结束；之后的新交互开启新段。不需要模型额外判断“是否已经说完”，用户或角色没说“再见”也能按静默自然结束。

如果相关回复仍在生成或发送，先保持该段，不因单次请求／恢复超过15分钟将一轮回复拆到另一段。真正发送的回复重新刷新计时；若最终决定不回复，保留已接收的用户原文，按最后真实消息计时，已满足15分钟时可结束。基础记忆提取或其他后台作业本身不延长对话段，不把“模型尚有后台请求”等同于“还在聊天”。

延期复议若发生在原段已经正常结束之后，按新的实际交互处理；待复议旧消息由显式reconsider输入提供，保留原ID及来源角色，不为了塞进最近4段而改写旧消息时间或重新认定首次来源。角色主动联系可以开启新段；没有用户新消息不妨碍它成为真实对话原文。

#### 共同活动与非对话事件

共同活动从已确认开始到实际结束作为连续互动，不因中间没有台词、一次剧情生成较慢或自动推进间隔超过15分钟拆段。开始前正在进行的普通对话可以直接延续进去，结束后继续聊天也属于同一段；活动结束后，从`max(最后真实交互时刻, 实际活动结束时刻)`再等待15分钟，无新交互才结束。

因此，静默共同活动照常有一个连续段；公开的`【…】`剧情作为可见原文保留。`【推进】`仍是控制资料，不变成角色台词或记忆事实，活动本身的连续规则已经阻止误关段。

世界／学校更新、私下收到学校通知、后台整理、无公开输出的自主生活和普通不可查看消息活动，不自动开启对话段，也不刷新对话静默锚点。自主生活若确实主动发送公开消息，按实际交互记录。

**不要直接复用MemoryIdle的一个时间值。** 现有记忆深度整理还会被故事完成、活动变化及当前活动阻挡；其15分钟门禁与“原文是否仍属同一段”用途不同。二者可以读取相同的真实输入／确认输出事件，但保持各自规则，避免无声自主生活把全天合成一段，也避免对话关段改变现有深度整理门禁。

#### 示例

| 情形 | 建议结果 |
| --- | --- |
| 10:00发消息，角色10:02回复，最后一个短段10:02:20确认，之后无交互 | 10:17:20关段；分段数量不影响保留多少个对话段 |
| 上述情形在10:16又发消息 | 继续同一段，计时从新输入及之后确认输出刷新 |
| 10:00发消息，模型很快决定不回复，之后无消息 | 10:15可关段；用户原文仍属于该段 |
| 同一回复仍在生成／发送，超过15分钟才最终确认 | 保持原段，最后确认后重新等待15分钟 |
| 共同活动20:00开始，20:40实际结束，其后没有聊天 | 全场连续保留；最早20:55关段，若更晚有确认输出则从其后15分钟算 |
| 上午对话已结束，下午无声自主生活发生 | 不把上午段延长到下午，也不新增空对话段 |
| 已有A、B、C、D四段，新段E开始并有本阶段可见原文 | 最近窗口为B、C、D、E；A的消息和相关记忆仍留在数据库 |

#### 后续实现边界

建议配置改为`recentDialogueSegments=4`与`dialogueIdleMinutes=15`，移除生产装配对`recentMessagesLimit=30`的消息条数裁剪。对话段只保存身份、起止／最近真实交互、相关消息／活动归属等轻量索引，正文继续使用原messages，不复制一份。

显式对话段记录更适合本项目：可以固定分段回复、正在发送与共同活动归属，重启后不临时重新拼段。旧消息按已有时间、看见／发送记录、turn及可确认活动归属回建；信息不足的旧记录不编造归属，也不为了重建修改原始来源ID、时间、记忆或正文。部署旧配置的迁移口径须在实施细化中明确，不能静默保留30条二次裁剪。

当前可见／复议消息及整个近期段若引用同一消息ID，仍按§7.1只发送一份正文，保留不同角色标签。对话段结束不触发新的记忆提取模型调用：每轮基础提取、空闲深度整理继续按现行流程，避免把“4段原文窗口”变成新的记忆制度。

该项纳入第一批设计，但它比删重复字段多一层归属记录／恢复逻辑；实施时应单独成任务和回归，不把纯去重成功当作分段功能已完成。

## 8. 推荐范围和实施顺序

| 选择 | 内容 | 取舍 |
| --- | --- | --- |
| A：仅字面去重 | recent、任务副本、网页正文、同ID同版本资料 | 最容易验证，但表达／背景和机械字段问题仍在 |
| B：去重＋程序分支＋任务视图（推荐） | 先完成A和明确权限分支，再分批收窄表达、背景及学校机械工作 | 信息保留可逐项审核，收益更完整；语义敏感改动需分批验收 |
| C：统一摘要或合并模型阶段 | 另用模型压缩总上下文，或一次调用兼做多个角色 | 会增加摘要误差／职责耦合，不作为本期默认方案 |

建议第一批：同次请求确定重复消除；§7.5的4个对话段原文窗口；主动联系／共同阶段／模式／能力块分支；普通调用的轻量资料视图；无用途查询embedding免调用；没有合法新来源时基础记忆空结果。保留原背景及表达有效内容作为基线，方便逐项对照。

建议第二批：表达专用资料、背景审阅拆分、学校周计划机械输出移交、环境历史相关性投影。第二批不与第一批一次全部混改，避免无法判断角色行为变化来自哪里。

这份文档尚不是逐文件执行计划。用户／DSH确认建议范围后，再将第一批的字段、冻结依据、恢复兼容及测试落为实施细化；第二批涉及背景映射及学校返回合同，需要分别列清替代字段和兼容策略。

## 9. 后续验收要求

1. 同一请求中每条消息／每份网页正文只展示一次；ID和版本不同的资料不误合并；普通主叙事仍看不到新私聊。
2. 去重前后可用事实与合法来源集合一致；visible／reconsider／recent来源语义不变；共享记忆仍以实际确认outgoing为公开依据。
3. 有／无真实用户输入分别只出现对应代写块；冻结后到达的新消息不改变修补分支；线上／线下提示一致。
4. 首轮兼final、wrap_up只减线索、提前收尾和末轮end规则保持；公开收尾质量仍需真实多轮验收。
5. contactEligible=false不能输出非法willing=true；true仍允许不联系；发送层门禁保留。
