## 3. 推进命令与 60 秒规则

### 3.1 `【推进】`

仅目标用户的绑定私聊中，去除首尾空白后全文等于 `【推进】` 才作为控制指令。嵌在句子、引用或动作中的同样文字仍是普通内容。

共同活动开始标志已确认发送后（输入路由立即绑定活动，故事仍等段 B 正式提交后才选下一轮）：

1. 持久化本活动的推进请求，然后唤醒串行调度器，不等待 60 秒或 15 秒合批。
2. 调度器空闲时，立即选择下一共同回合，连同截至选择时尚未处理的共同输入一起交付。
3. 正在生成、发送或后处理时，先完成旧轮；指令请求保留，随后立即进入下一轮。不会中断冻结输出，也不会承诺模型即时返回。
4. 同一次下一轮选择前收到多个推进指令，合并为一个请求；不按按钮次数排成多轮。选择以后新收到的指令属于下一次请求。
5. 系统暂停时只保存请求，恢复后遵守未完成轮优先规则。

指令是控制信息，不当作角色说过的话、剧情行动或记忆事实；模型接收结构化 `advanceReason=manual`，而不是把原始命令当对话。输入入口即时分类，被判为控制指令的内容不写入 `messages`，不进入普通合批、未读集合、近期原文或记忆来源。

推进请求及审计用独立控制记录持久化，包含 ID、活动 ID、接收时间、平台消息 ID 和 pending/consumed/cancelled 状态；选中的 ID 随 TurnRecord 固定，段 B 同事务标记消费。命令身份在接收时确定，等待调度器的是执行，不是到执行时才判断它是否为命令。

活动外的命令不创建待生效请求，不启动活动，也不调用模型；可返回固定系统提示“当前没有共同活动”。请求绑定活动 ID，旧活动结束时取消它尚未消费的请求，不泄漏到下一活动。

### 3.2 自动推进时间

共同活动普通输入立即落库，但不再以 15 秒截止触发共同故事。自动下一轮的候选时间为：

```text
idleAnchor = max(本活动最近用户输入接收时间,
                 本活动最近一轮最后一个剧情／角色输出项的发送确认时间,
                 最近一次无可见输出的共同轮完成时间)
autoAdvanceAt = idleAnchor + 60 秒
```

用户侧使用 `receivedAt`，因为现接口能可靠记录的是接收时间；角色侧使用现有 outbox 的 `confirmedAt`，不使用生成起点。旁白、角色文字／动作和随轮发送的表情都算本轮输出，取最后一个确认时间。后台日志、状态查询、错误提示、搜索工具消息不重置活动计时。

这刻意给用户在本轮最后一项可见输出发送完成后留出 60 秒，不能改成从模型开始时刻或仅最后一段 text 起算；若之后用户又输入，以较新的用户接收时间重新计时。

无可见输出时用完成时间补充，是为了避免一轮沉默后马上命中旧截止，连续空转。它不是强迫角色发言。60 秒是静默窗口，不是模型超时：从一次输入到看到回应，还会包含生成、工具调用、表达及发送时间。

举例：用户 22:31:00 发言；模型 22:31:30 才发完，本轮自动下一步最早为 22:32:30。如果用户 22:32:00 再发一句，改为 22:33:00。若此时发送 `【推进】`，跳过剩余等待。

每个活动只保留一个有效自动节点。新输入与新输出更新同一个截止；过期计时被新输入延后，不补跑错过的节点。手动请求和已到期自动节点同时存在只生成一轮。

### 3.3 生成期间的输入

回合在选择时固定本轮输入集合。选择后到达的输入立即保存，供下一轮使用，不塞进已经生成到一半的上下文。

如果这些输入在旧轮发完前已经等满 60 秒，仍以旧轮最后输出重新计算下一截止，让用户看到完整结果后有参与时间；已有手动请求则继续优先，不再等待。

发送确认可以提前记录下一截止，但只有上一轮完成后处理和正式提交后才能开新轮。后处理若耗时超过 60 秒，完成后最多开一轮，不追补多轮。

手动、自动和预约协调共用一次回合选择。该轮覆盖的当前自动节点关联到冻结回合，不在原截止再启动；完成后依最新锚点维护唯一下一节点，无输出轮同样重算。不能借消费旧节点删除选择后新到达的普通输入或推进请求；失败仍先恢复同一轮。

### 3.4 与首次节点及模型时间建议的关系

保留确认开始后立即生成首个公开节点的现有行为：开始标志是进入通知，用户不必再等 60 秒才能看到场景开头。首节点完成后才采用日常 60 秒规则。

共同活动的下一轮调度由程序负责，模型不再通过 `nextStepAt` 自行加快、延长或取消这个窗口。下一步实施时调整共同主叙事合同，取消其可写调度字段，继续保留 `Scene.shared.nextStepAt` 作为程序计算结果及 `scene_step` 的语义来源。

活动内 `reply=later` 表示以后再考虑该消息，不创建另一个会绕过 60 秒的额外共同回合；在之后合适的共同回合重新提供已看消息，到期检查与共同推进合并。未到合适时机仍可不回复。活动结束时，把仍有效的延后回复检查交回普通私聊接收规则。

活动中途用户连续发消息会延后自动推进；这是等待用户表达完成的预期行为，用户随时可用指令推进。

### 3.5 双方都没有新的对话时继续推进

用户已确认：没有用户新消息、角色也选择不说话时，公开剧情仍允许按 60 秒规则持续推进，直到活动自然演完，最晚在第 20 轮完成收尾。公开旁白、动作和环境变化不要求附带角色台词；沉默不是暂停活动或等待确认的控制信号。

不新增“连续 3 轮无输入，下一轮强制结束”的固定策略。活动目标提前完成或角色基于生活情况选择合理结束时，仍可提前自然收尾，不必凑满 20 轮。

按2026-10-08用户追加确认，在选轮时双方没有新输入的推进段，主叙事可以生成双方在本次已确认共同活动中的行动选择及客观结果，不必每一步等待真实输入。这是对普通叙事行动职责的有条件例外；有输入的共同回合禁止新增用户动作，角色自愿配合交给个人导演。程序选择互斥提示分支，不把判断权交给模型；普通私聊沿用原规则。

每一项双方代写行为都必须包含在本轮`publicNarration`中，通过既有`OutboxItem.kind=narration`发送为`【…】`，不能只存在于experiences、progress或内部计划中，也不伪装成用户消息或角色台词。simulatedUserActions只逐项列用户动作，不收角色动作。正文使用裸文本，程序统一加外层括号，避免重复包裹。

静默授权依据选轮时已有输入判断，不预测随后个人导演是否开口；旧轮角色输出不重复当作新输入，现串行结构没有角色跨轮独立发送通道，实际仍用冻结的inputMessageIds为空判断。生成后才到达的输入留下一轮；修补及未发送恢复沿用原分支。静默分支不替双方新增台词、心理或活动外重大决定；已公开角色动作成为经历，个人导演负责感受、台词和接下来的意图，不倒改已实现动作。

代写只推动已经确认的活动，不用此前代写自我放大成用户的新长期意愿、活动以外的新承诺或重大关系决定。活动内正常操作和推进选择仍允许；这条不恢复为“一切关键动作都必须等待用户输入”。角色及用户已知习惯、既有公开事实继续作为叙事依据，不仅凭连续代写就认定用户现实习惯改变。

自动演完是持续公开推进，代写行为作为本次模拟活动的剧情经历处理，不据此推断用户在现实世界做过同样行为或修改用户真实背景。剧情走向无需靠用户不断答题才能收尾，也不在后台私下完成后只补一句总结。

### 3.6 公开代写作为共享经历进入记忆

采用用户确认的 A：成功发送的 `【…】` 代写旁白是双方共享的模拟剧情。用户返回后按这些记录继续交流；角色可以记住活动过程、结果及自己的感受，也可以自然提起“上次你拿下了那个补给点”。不因用户当时没有回复而降为“角色独自想象、双方没有经历”。

这是剧情共同事实的约定，不是技术上声称已经取得用户阅读回执。现有发送确认和段 B 提交足够，不新增用户已读标记、在场轮／不在场轮、静默代写记忆归属字段，也不要求用户回来补确认每一轮。

记忆仍依现有本轮来源规则：公开正文成功发送后，整理读取已发生经历及实际确认的输出，至少引用一个合法本轮来源并随段 B 正式提交。代写的共享行为必须能在本轮已确认公开旁白中找到依据；未发送的候选、内部计划及仅写在 experiences/progress 而没有公开的用户行为，不能当成共享经历。这里由原模型职责／提示词与既有发送流程落实，不新增独立语义审核模型。

模拟活动事实不会据此变成用户现实行为或真实背景；也不能仅凭连续代写把用户长期意愿／性格当成已证实信息。角色在活动中的真实主观感受按个人导演及既有记忆规则整理。

用户回来后与代写发生冲突时，复用现有公开剧情矛盾处理。例如已有 `【你走进店里】`，随后用户说“我还在外面”，共同主叙事及个人导演结合公开节点和本轮输入，自然澄清或识别这是用户提出剧情修正，在后续公开输出中说明并继续。普通一句话不在后台悄悄改写已公开结果；明确修正可通过既有后续状态及带本轮来源的记忆更新表达，已发送历史保留，不新增独立回滚／剧情改写系统。

### 3.7 用户输入 `【动作：…】` 的现有约定

此功能已有设计及输入传递路径，继续保留：在线下共同活动中，用户发送 `【动作：把水杯递给她】` 表示自己在场景中的行为或动作尝试，不表示口头说出“把水杯递给她”。普通文字如“给你喝点水”表示面对面的发言；同一消息内可以包含动作标记及其外部的发言，按原顺序理解。

动作文字与括号原样保存并交给共同主叙事和个人导演。当前没有把 incoming 拆成独立 action/text 数据类型的语法解析器，而是由模型结合共同模式及原文理解。已有 `tests/shared-scene.test.ts` 检查 `【动作：推门】` 在线上／线下模式都被交给两个共同模型；该测试验证传递，不等同于真实模型语义效果验收。

用户提交的动作不自动决定虚拟角色是否配合，例如用户伸手由主叙事描述，她是否回握仍由个人导演决定。真实输入的动作按 §3.5 优先于静默代写；线上共同活动中同样的动作写法结合虚拟活动解释。`【推进】` 是单独的控制指令，不能与 `【动作：…】` 混为一类。

角色输出的 `【动作：…】` 表示角色自己的行为，旁白输出的 `【…】` 表示公开场景及包括代写在内的剧情。输入发送者与输出种类共同确定行为归属，不因为括号形式相似就写错动作主体。

现有依据：`REMAKE_V0.2_LIFE.md` §6.3 明写用户动作语义；`src/index.ts:92～95` 保留提取的文字并送入输入缓冲；`src/model/prompts.ts` 的共同合同读取用户发言／动作。后续改造应把这条已定义约定明确延续到共同提示词，不新增动作解析子系统。

## 4. 20 轮计数与自然收尾

### 4.1 一轮如何计算

一次共同模式入轮、运行共同主叙事与个人导演、发送并完成段 B 提交，计一个共同推进轮。一次合并输入是一个轮次，不是每条消息一个轮次。

具体口径：

- 普通模式里确认开始的准备轮和开始标志不计；紧随其后的首节点计第 1 轮。
- 手动推进、自动推进和合并共同输入都使用同一轮数，不存在每种原因各有 20 轮。
- 一轮可没有角色台词，仍计一次；不靠“角色必须回复”来决定是否消费轮数。普通轮公开旁白也允许为空，但提示词要求每轮有合理进展，避免一直原地等待。
- 世界／学校更新、记忆整理、Embedding、工具续调用和格式修补不计共同轮数。
- 失败、恢复、冻结稿续发及同轮后处理重试不额外计数；正式提交只增加一次。
- 活动可提前结束；20 是上限，不是必须补满的配额。

每次共同模型调用都提供程序生成的 `stepNumber`、`maxSteps=20`、`remainingSteps` 和当前收尾阶段。程序校验不接受第 21 轮；模型不能自己修改计数。

### 4.2 不在第 20 轮突然掐断

程序阶段：第1轮通常opening，2～16轮ongoing，第17～19轮wrap_up，第20轮final；阶段由剩余轮数决定。按2026-10-08用户确认，普通活动以约10轮自然收尾为提示词软目标，通常约第7～8轮开始收束，不等到程序wrap_up才收尾。没有最少5轮的硬要求，不在10轮强制结束；完成活动、用户要求或合理生活需要可更早收尾，复杂活动可更长，20仍为硬上限。已确认内容与真实经过时间优先，不为轮数目标换目标、谎称完成或不合理压缩时长。小上限活动按实际maxSteps组织，maxSteps=1同一正文可以兼顾开场与收尾。

首节点让共同主叙事建立轻量的活动走向：当前目标、待处理线索、自然结束条件。不新增规划模型；后续随同原共同主叙事更新。这些是候选方向，不是已发生事实，不作为记忆来源。

收束阶段不新增支线，完成或合理交代已公开的重点：已有outline的wrap_up仅保留／删除旧openThreads字符串，开展阶段仍可建立必要线索，final列表为空。goal/endingCondition原则上沿用，有依据的必要调整及收尾自然性需要真实多轮验收；具体校验和首节点例外见实施细化§6。第20轮：

1. 主叙事给非空公开收尾节点，处理环境及结果；静默段可按§3.5代写双方活动动作并全部公开。有输入轮仍不新增用户动作，角色自愿反应交个人导演。
2. 个人导演决定角色的结束反应，合同要求 `sharedChange.end`。角色可发言、行动或不说话，但必须完成活动结束状态。
3. 输出本轮剧情和角色反应，最后发送既有 `【共同活动结束】`，再在段 B 一次提交模式切换和计数。
4. 不通过直接清空场景来掩盖不合格模型结果。缺必要收尾字段时，沿用对应任务的格式修补；重试仍不合格走既有报错／暂停，不能偷偷产生第 21 轮。

“自然结束”以完成本次活动的合理过程与结果为目标。静默段可以按授权生成用户活动行为及相应结果，但不能推翻已公开结果或不合理压缩经过时间；真实输入回合仍以用户实际选择为准。复杂的未决问题可以留待下次，但本次活动必须有完整收尾，不保证模型文学质量或长篇情节一定全部解决。

不为完成剧情而把一分钟叙述成已经过去三小时。继续沿用实际经过时间和已发生经历合同；游戏、吃饭等活动须在现有时间范围内安排合理片段，允许以暂停／稍后再继续的方式收束。

## 5. 日程优先级：承诺、接收门禁与计划分开处理

把全部事项直接按 `预约 > 睡觉 > 消息` 排列，会误把“已经睡着”和“今晚打算睡觉”当成同一件事，也容易让预约强行证明用户到场。推荐如下两层规则。

### 5.1 必须先遵守的执行条件

| 条件 | 规则 |
| --- | --- |
| 系统暂停、前一轮未完成 | 不启动新故事；输入和控制请求仍先落库。 |
| 已实际睡着，或普通模式确实不能看消息 | 输入暂存，预约可保持待处理；不能为了高优先级事项虚构醒来、手机可用或用户到场。 |
| 活动已经开始且角色清醒参与 | 继续采用共同模式输入可见规则，线上／线下不再被普通 `phoneAccess` 拦住；不允许主叙事无说明地把参与者改成洗澡且完全无法参与。 |
| 尚未实际入睡的预计睡眠时间 | 是可协调安排。活动中跨过旧 `sleepAt` 时，不直接变成“已睡着”并卡住活动。 |

当前代码用一个时间区间同时表示睡眠安排与实际门禁，这里必须调整共同模式下的判定顺序，而不能只在提示词说“预约优先”。普通模式已睡眠的接收行为保留。

采用第八轮回应的睡眠 A：普通模式开始活动前仍须通过睡眠／可参与判定；合法共同活动表示清醒参与，期间 `sleepAt` 作为可调整计划。角色需要睡觉或不再参与时先结束共同活动，段 B 切回普通模式后按完成时刻和新作息统一判定睡眠及自主截止，不建立“实际已睡着但活动仍在进行”的混合状态，也不新增实际睡眠标记。

统一规则须覆盖 Scheduler 收集和截止候选、`canRead`、`generateTurn` 的睡眠早退与 waking、段 B 自主安排及恢复。不能只绕过早退却在旧计划 `wakeAt` 到期时把仍在活动的角色误判为刚起床。缺合法活动身份的旧状态不得仅凭 mode 字段自动豁免睡眠，升级时先检查。

### 5.2 通过执行条件后的安排优先顺序

1. 已确认且正在进行的共同活动，以及到期的具体共同约定：优先协调。
2. 用户可见的新消息和确实需要重新考虑的回复：普通模式按现有合批处理，共同模式合并到下一共同轮。
3. 可调整的私人生活计划：例如“今晚 23:00 睡觉”、泛泛的“晚饭后复习”，由个人导演调整。
4. 私人自主周期：仅连续前台空闲时启动；前台故事回合统一重置间隔，不插入一轮无关私人生活。

正在进行的活动与新到期预约冲突时，在同一共同回合交付新预约，由个人导演选择收尾、改期或协调。不能后台直接开启第二个共同活动，不能默默标记约定已经完成；保留原始预约 ID 和时间说明迟到／调整原因。

具体预约到期需要及时协调，可以请求一轮共同处理，属于明确日程触发的例外，可早于 60 秒；与已有手动／自动推进合并，并计入同一个 20 轮上限。普通用户消息、私人自主周期和未来睡眠计划不成为这种例外。

世界／学校仍可后台更新，但调度选择时，已经可运行的前台共同轮或消息／预约轮优先于尚未启动的环境更新；已开始的环境模型调用仍先完成。无到期前台时可利用 60 秒窗口运行环境工作，维护继续遵守现有“一批后让位”规则。此排序不等于角色生活事件的价值排序。

### 5.3 22:30 游戏与 23:00 睡觉的例子

预约到期的普通回合：主叙事更新当前处境，个人导演知道已确认的游戏约定、睡眠安排及疲劳情况，可以表达邀请、等候或协调，必要时输出 `sleepPreference` 调整入睡时间。无需先额外运行自主生活轮。

双方确认开始后，旧 23:00 入睡边界不直接暂停活动。共同模型持续看到预计睡眠和疲劳，可以提前自然收尾；活动最晚第 20 轮结束。结束轮的个人导演重新协调实际作息并给出必要的时间偏好。

如果结束时旧入睡时间已经过去且没有另定时间，提交结束后按当时状态进入睡眠控制；若个人导演决定继续清醒，则输出有效新时间。未来已经确认的晨间预约继续进入现有起床协调。不能用“共同优先”强迫一个原本已经睡着的角色在 22:30 自动上线。

从计划睡眠到真实睡眠的控制，以及最终自主时间计算，要由同一个提交顺序处理；不能一处认为共同活动清醒、另一处又按旧 `sleepAt` 清空状态。

## 6. 每个可运行故事回合先补齐生活

### 6.1 这条顺序已经实现

用户希望虚拟角色接收消息、赴约、进入共同活动或自主行动前，先补齐上次处理以来的生活，避免生活只在约三小时的自主周期里才发生。现有前台流水线已经支持这一点，不需要新建一轮“先自主、再处理输入”的模型调用。

准确起点是 `CharacterState.narratedUntil`：上一次已经叙述并成功提交的时刻，不限定为上一次自主推进、上一次活动开始或上一次角色回复的时刻。

```text
输入先落库，或日程／共同节点到期
  → 合批／静默窗口结束或手动推进，且前台允许运行
  → 主叙事补齐 [narratedUntil, 本轮 at] 的过去生活
  → 更新本轮候选处境、活动和体力
  → 判断当前消息是否可见
  → 个人导演理解新经历与可见消息，决定反应和之后的意图
  → 必要时表达、发送
  → 整理记忆，随段 B 提交经历与新的 narratedUntil
```

例如：10:00 自主轮已叙述到 10:00；10:40 用户消息触发一轮，就补 10:00～10:40 的生活，再决定是否回复。11:10 另一条消息触发时，从 10:40 补到 11:10，不再从 10:00 重造同一段生活。角色在 10:40 选择不说话，也不影响这一轮成功提交生活和时间进度。

代码依据：`src/app.ts:102～114` 在个人导演调用之前完成主叙事；`src/recovery.ts:61～74` 以正式事务提交候选状态和已看标记。`tests/turn.test.ts` 已有顺序、未看消息隔离和沉默跳过表达的用例。

### 6.2 哪些入口需要补齐，哪些只保存或维护

| 入口 | 主叙事规则 |
| --- | --- |
| 普通消息合批后，角色清醒且没有已知接收阻断 | 先普通主叙事；本轮新消息正文不提供给普通主叙事，避免用收到的新问题倒造此前生活。更新处境后再判断实际可见性。 |
| 预约到期、自主周期、起床、待看或延后回复检查形成故事回合 | 同一轮先主叙事，再个人导演；多个原因合并时只补一次。 |
| 确认共同活动开始的准备轮 | 普通主叙事补到当前，个人导演确认进入。下一首节点已经从准备轮的截止继续，不重补此前生活。 |
| 正在共同活动中的手动／自动推进、冲突预约协调 | 同一轮共同主叙事同时补齐经过与推进公开场景，再共同个人导演；不额外增加一轮普通主叙事或私人生活。 |
| 普通模式已睡着，或已知洗澡等无法接收且没有其他到期故事原因 | 输入先保存，等待起床、活动结束检查或其他可运行故事回合；不会每来一条消息就额外叫模型。期间 `narratedUntil` 不被输入接收或暂存动作推进。 |
| 世界／学校更新、Embedding、记忆维护、状态查询和控制请求入库 | 不代表角色已经经历或感知新事件，不为这些技术任务调用主叙事，也不修改 `narratedUntil`。下一实际故事回合再补齐。 |

“先补齐”适用于真正开始处理角色故事的回合，不要求每次数据库接收消息都马上调用模型。这样兼容共同活动的 60 秒窗口，也保留睡眠和不可接收状态的自然性。

### 6.3 补齐内容与防止重复的边界

主叙事依据上次已确认的处境、意图、已知生活安排、环境事件及检索资料，补齐已经过去的过程和结果。计划不是自动已发生事实，未来安排不能写成已经参加；新重要自愿选择和未来行动意图仍由个人导演决定。

短间隔可以没有新经历，允许 `experiences=[]`，无需为了“补生活”每分钟编造一件事。较长空档则应提供有依据的主要生活过程、值得记住的经历和当前状态，不按分钟逐条补日志。主叙事叙述客观过程，个人导演决定由这些经历引起的情绪与主观反应；有依据的事件和感受再交给既有记忆整理。

共同活动里的经过延续已公开局面；静默段可按§3.5生成双方活动动作，并通过`【…】`全部公开。补齐时间本身不额外扩大这一授权，也不允许跳到未来或生成不符合实际经过时间的结果。

成功提交后才推进正式 `narratedUntil`。模型失败、发送中断或后处理未完成时，仍按现有冻结／恢复规则完成同一轮；不能先标成已经补齐而丢失经历，也不能在恢复时把同一段提交两次。

本轮建议是保留并明确这条现有机制，在共同活动改造验收中继续覆盖它。无需为了“每种活动都先唤主叙事”新增第二套流水线；自主触发时机另按第 7 节的统一空闲规则调整。

## 7. 自主周期改为统一的前台空闲周期

### 7.1 目的与统一公式

自主推进用来在长时间没有前台故事活动时唤醒角色，先补齐过去生活，再由私人生活个人导演决定接下来的意图，以及是否主动联系。它不需要按固定墙钟周期强行插入已经持续处理的对话或共同活动。

每个实际运行角色主叙事的前台故事回合成功完成时，只要角色仍清醒，统一设置：

```text
intervalMinutes = 本轮冻结的一次 150～210 分钟均匀抽样
nextAutonomousAt = 本轮 completedAt + intervalMinutes
```

不保留或恢复活动开始前的旧自主截止，不对旧截止反复加三小时，不按消息条数积累延期，不补跑已经被前台活动替代的自主机会。共同活动准备轮、每个共同推进轮和结束轮都采用这条相同规则，因此不再需要共同活动专用延期逻辑。

例子：10:00 故事回合完成，本次抽中 180 分钟，预计 13:00 自主唤醒；11:00 对话轮完成，又抽中 180 分钟，则改为 14:00。12:30 共同活动的一轮完成，则改为 15:30。只有之后持续没有新的前台故事活动，才在截止时执行自主生活。

实际生活仍由第 6 节的主叙事持续补齐；重排自主机会不会删除、暂停或漏掉这段时间的生活。

### 7.2 哪些情况重置间隔

下表是已按本方案实施的统一重置策略；实际角色主叙事前台轮首次冻结抽样，成功完成时重排，恢复复用已冻结间隔。

| 情况 | 是否重置 | 原因 |
| --- | --- | --- |
| 已合批的对话回合 | 是 | 角色故事已经唤醒并更新；无论角色回复、延后回复还是不发言。 |
| 预约、待看／延后回复检查形成的故事回合 | 是 | 已补齐处境并处理日程或消息；如果这一轮只有主叙事、没有个人导演，仍算已经更新生活。 |
| 共同活动开始准备轮、首节点、后续节点、结束轮 | 是 | 统一采用前台成功完成规则，不另存旧自主时间。 |
| 自主生活轮、起床故事轮 | 是 | 完成后安排下一段空闲间隔，沿用既有长度。 |
| 收到输入、保存推进命令，但尚未形成故事回合 | 否 | 只保存数据；待实际故事成功完成后重排。已有前台待办按下节规则优先。 |
| 睡眠或明确不可接收期间单纯暂存输入 | 否 | 没有运行主叙事；保持睡眠／待看规则。 |
| 世界／学校更新、后台记忆整理、Embedding、搜索的工具续调用、格式修补、状态查询 | 否 | 这些不单独构成一次角色前台故事活动；工具和修补归所属回合统一计算一次。 |
| 失败、暂停、重启、同轮恢复或重复后处理 | 不产生额外重置 | 只在该轮最终成功提交一次时生效。 |

这里“模型被唤醒”特指角色前台故事唤醒，不包括任意后台模型调用。否则周期性环境更新或记忆维护也会不断推迟自主生活，与用户设定的目的不符。后台任务不占共同轮数，也不重置自主间隔。

### 7.3 前台优先、睡眠与恢复

自主截止到达时，若已经存在待处理对话批次、共同活动节点或到期预约，先处理这些前台事项，不同时把 `autonomous` 加入该回合，也不为它另跑一次私人生活导演或主动联系抽样。前台回合成功提交时统一生成新截止。

共同活动持续等待用户表达时，前台共同活动仍在进行，不允许自主截止穿过静默窗口启动无关私人生活。调度器依据已有前台待办及活动状态统一判定可否自主唤醒；没有共同活动专用“结束后恢复旧截止”。暂时不可运行的自主候选从当前定时器候选中排除，等待有效前台截止或新的输入唤醒，避免旧过期时间造成立即空转。普通模式没有前台待办、只是在进行上课等私人生活时，仍按现有清醒自主规则处理。

睡眠优先：完成轮正式进入睡眠时 `nextAutonomousAt=null`，起床故事成功完成后再安排。共同模式跨过原计划睡眠时间的处理须与第 5 节一致，不能误按旧时间区间清空一个仍在清醒参与活动的角色。

间隔只抽样一次并写入冻结候选；在既有段 B 事务使用本轮实际 `completedAt` 计算截止，与生活状态一并提交。失败或恢复不重新抽样，不把后台成功、输入接收或发送确认当作这项提交。等待期间的输入不覆盖冻结候选，而是在下一前台轮完成时再次统一重排。

因此原规范中的“聊天不重置自主周期”“预约与自主同时到期仍消费自主周期”，将在实施时由本节规则替代；旧实现说明和历史测试当前仍描述原行为，本稿不将它们误改为已经实现。

## 8. 与现有数据及恢复流程的衔接

推荐最小扩展，不在本稿编写实施代码：

| 位置 | 建议新增或调整的信息 | 责任 |
| --- | --- | --- |
| `Scene.shared` | `activityId`、`completedSteps`、轻量活动走向；保留标题、进度、最近公开节点与程序计算的 `nextStepAt`，不保存原自主截止。 | 当前活动身份和已经提交的故事状态。 |
| `Runtime` | 活动绑定的输入／输出计时锚点、无输出轮完成锚点；待消费推进请求读取独立控制表，不另存一份请求数组。 | 输入即刻写入、发送即刻确认的调度信息。 |
| 输入／控制记录 | 普通消息仍入 messages，命令另存控制记录并绑定 `activityId`；具体选取的消息和控制请求 ID。 | 避免控制指令成为剧情或记忆。 |
| `TurnRecord`／冻结候选 | 活动 ID、选中的输入与请求 ID、本轮轮号、推进原因、收尾阶段；复用现有 `autonomousIntervalMinutes`，扩展到所有角色前台故事轮。 | 生成、发送、提交和恢复使用同一份决定。 |

| 模型合同 | 共同主叙事取消可写下一调度时间；共同模型获得轮号／收尾要求；个人导演末轮必须结束；限制活动内额外任务触发。 | 用结构化校验支持上限与收尾。 |
| 本地配置 | `sharedIdleSeconds=60`、`sharedMaxSteps=20`；普通叙事约10轮收尾、约7～8轮开始收束，程序wrap_up仍从第17轮开始。 | 时间与轮数可日后调整；此次不是字符／token预算。 |

表中是设计责任划分，最终字段名、默认值和旧行升级方式应在实施细化固定。升级前服务停止、备份并检查实际状态，不根据以前 memories/details 为零推断目前没有故事。没有旧活动则初始化新字段；有缺活动 ID／计数或未完成旧共同轮时，记录并检查能否从已提交 turns 重建，必要时向用户提出具体接续方案，不静默清空活动、伪发结束标志或从零重开 20 轮。

关键提交与恢复规则：

1. 普通输入和控制请求立即落库；回合只消费选择时固定的 ID 集合。
2. 发送确认记录真实活动锚点；角色状态、推进轮数、结束和统一自主间隔随既有段 B 一次提交。
3. 段 B 读取最新 Runtime，按被消费的请求 ID 删除，保留生成期间新到达的输入与命令；不能用旧候选覆盖整个最新 Runtime。
4. 结束时撤销该活动的节点与未消费控制请求。尚未处理的普通消息继续按普通 15 秒接收规则重新组织，不能一起删除或冒充已看；已处理消息不重复交付。
5. 重启先恢复未完成轮，之后最多运行一轮过期活动节点；不按离线时长补跑几十轮。若当前还有新消息，用最新锚点决定是否仍需等待。
6. 已尝试发送的候选与计数固定；未尝试稿可按既有恢复规则重生成同一轮号。结束标志续发不造成第二次结束或第二次延期。
7. 活动外命令、旧活动计时器和旧控制请求不能改变新活动；所有关联以活动 ID 判断。

## 9. 下一步实施范围与验收重点

实施细化和执行计划任务1～7已完成离线开发，入口见文件开头。涉及 `src/host/input.ts`、`scheduler.ts`、`runtime.ts`、`state.ts`，以及 `src/app.ts`、`recovery.ts`、`types.ts`、模型合同／提示词、配置、入口和对应测试。复用已有记忆与搜索模块，不新增供应商或模型档位变更；实际检查证据和后续真实语义待办见实施日志。

后续验收至少包含：

- 开始通知后首节点立即生成，随后采用 60 秒；普通私聊仍是 15 秒。
- 用户连续消息、分段角色输出、旁白／动作／表情均正确延后唯一截止；不被后台输出重置。
- 手动推进空闲立即选择，忙时不打断、请求持久化，多次命令合并，选择后到达的新命令保留。
- 手动与自动同到期只一轮；生成中输入不丢、不进入错误快照；无输出轮不会立即空转。
- 轮数只在正式提交增加；恢复不重复计数；第 17 轮开始收束，第 20 轮有公开收尾与结束标志，不存在第 21 轮。
- 角色可选择不发言；控制文字不进记忆；未来走向不被整理成已经发生的经历。
- 选轮时双方没有新输入，允许继续自动推进并演完活动，不触发固定无输入轮数提前结束；程序选择允许代写双方活动动作的提示，所有代写经公开旁白输出为`【…】`，不能只写内部进度或经历。
- 真实用户发言／动作优先于代写；普通私聊及实际输入回合不启用静默代写；静默分支允许双方活动动作，双方台词与心理、角色后续意图仍保留原职责边界。
- 用户 `【动作：…】` 在线下共同模式按动作理解，括号外文字按发言理解，输入顺序及动作主体保留；动作输入不触发推进控制，不默认角色配合。语义效果通过后续真实故事验收，不把 mock 传递测试当作语义保证。
- 已确认公开代写可进入共享活动记忆并被角色提起，不依赖用户阅读／在场标记；没有公开的代写候选不得作为共享经历，不据代写推断用户现实背景或活动外重大意愿。
- 真实输入与公开代写冲突时沿用自然澄清／剧情修正处理，后续输出和记忆更新有来源，保留已发送记录，不静默覆盖。
- 普通消息、预约、起床和共同节点先补齐 `[narratedUntil, at]` 再反应；沉默轮照常提交时间进度，不重复叙述过去；睡眠暂存与纯后台任务不推进该字段。
- 活动跨过计划入睡不被旧边界卡住；普通模式已睡着不因命令醒来；结束轮统一重排睡眠和自主时间。
- 对话、预约及共同活动等前台故事轮成功完成后统一重排 150～210 分钟自主间隔，沉默／只有主叙事也生效；不恢复活动前旧截止、不累计延期、不重复抽样。
- 前台与自主同到期时只处理前台，不消费自主原因或抽主动联系；等待合批／共同节点期间不被旧自主截止插入或空转。没有前台干扰时自主按期运行，后台模型及技术任务不重置间隔。
- 冲突预约在共同轮协调；不隐式覆盖活动、不开双故事并行；环境和维护在批次之间让位。
- 收尾允许静默授权内的双方活动动作及结果，保持既有公开事实与经过时间一致。字段与时序由程序测试保证，叙事自然性、代写与公开正文的语义一致性需真实故事验收。
