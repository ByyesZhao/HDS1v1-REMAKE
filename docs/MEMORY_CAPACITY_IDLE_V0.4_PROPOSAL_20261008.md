## 1. 当前实际设计

| 项目 | 当前实现 | 本稿改动 |
| --- | --- | --- |
| 短期 | 通常在真实新进展后保留7天详细记录；仅改写、重谈不重置7天 | 增加100条活跃目标，超量可提前退出详细层 |
| 普通长期 | 新短期同时保存简要预备长期，通常7天后可见；重要经历立即可见。长期通常保留90天 | 增加3000条活跃目标，低保留优先级内容可提前归档 |
| 唤醒 | 必须有本轮真实重谈来源；同一canonical记忆同一天最多一次。3个合格日期续期，累计30个日期进入常驻审核候选 | 沿用；不把检索命中、后台复读或压缩算成唤醒 |
| 常驻 | 后台可审核为常驻经历或多事件支持的稳定认识；不直接改作者角色背景 | 改为空闲后做增量审核，仍需原证据门槛 |
| 具体事实 | `details`一个key保留当前值，`detail_history`保留变化；每轮记忆模型负责实际变化 | 每轮更新照旧；空闲复核矛盾和冗余，不随经历容量过期 |
| 基础提取 | 回复发送完成后，`finishPostprocessing`调用`organizeMemory`；记忆、经历、状态、任务和轮完成在段B事务提交 | 不延后至15分钟，恢复也沿用原冻结轮和后处理结果 |
| 深度整理 | 当前每日04:30周期选择到期短期与30次候选，单个后台准备槽，每批20个候选 | 增加15分钟空闲触发和增量范围；每日入口仅补漏，不能越过新门禁 |
| 索引 | Embedding待办可在前台空闲后准备，不必等每日周期 | 不强制等15分钟；新事实无向量时仍可词法检索 |
| 人为上下文预算 | 默认关闭字符预算、分块预算及固定检索条数限制，近期原文窗口为30条 | 不恢复这些限制；100／3000是活跃数据层容量，不是单次模型输入配额 |

当前没有短期／长期总条数上限，也没有持久化的“衰减度”字段。到期主要通过查询日期退出日常可检索范围，原文仍留库；`discarded`、`merged`是其他已存在的状态，不能把容量归档混同于彻底舍弃。

源码核对入口：[每轮提取](../src/memory/organize.ts)、[段B提交](../src/recovery.ts)、[保留与唤醒](../src/memory/lifecycle.ts)、[日期筛选](../src/memory/store.ts)、[维护调度](../src/memory/maintenance.ts)、[配置默认](../src/settings.ts)。当前04:30和唤醒日期使用Asia/Shanghai；本文不顺便重做原记忆时区规则。

## 2. 采用哪种容量处理

| 方式 | 优点 | 问题 |
| --- | --- | --- |
| 达到容量直接物理删除 | 能减少正文占用 | 会断开来源、旧ID和关联关系；明确追问旧事时也无法恢复 |
| 转层／归档，增量合并同事件重复项 | 控制日常工作集，保留追溯及明确回忆入口 | 归档会继续占磁盘，不是数据库文件大小上限 |
| 完全依靠模型压缩后再接纳新增 | 有机会保留更多有效信息 | 压缩不一定减少条数，失败或没有空闲时会堵住新记忆 |

推荐第二种。程序负责活跃层容量；模型只对确属同事件的重复记录做合并，或改进摘要。不能把不同事件拼成“这周发生了一些事”以凑条数，也不能用截字数代替记忆整理。

100条是七天窗口内详细条目的初始目标，约相当于平均每天14条；它不是必须每天提取14条。3000条在90天内约相当于平均每天33条，属于较宽的起始值。二者都按事件记录计，不按消息数量计，也不限制单条正文长度。最终是否合适由真实新增量、提前转层次数和恢复需求判断，不能仅凭月数推定。

## 3. 容量计数和保护范围

### 3.1 短期100条

计数对象为当前有效、未merged／discarded、尚未自然到期且未容量退出的短期主记录。七天之外的详细归档、已合并次记录不计。不同短期行不能仅因关联同一long ID就假装只占一条；真正合并后才减少短期行数。

有真实新进展时仍可以更新同一事件，不机械地每轮新建。当前一场对话的多条消息不等于多条短期记忆。

### 3.2 普通长期3000条

计数对象为未merged／discarded、未自然到期或容量归档的普通长期canonical主记录，**包含仍未进入可见期的预备长期**。否则每轮建立的预备摘要会变成不计容量的隐藏积压。一个canonical身份只计一次，关联短期和别名不重复算长期。

已经通过审核晋升为durable的主身份及其learned投影属于常驻层，不占普通长期3000条；晋升须维持原30个有效日期等条件，不能为了腾容量将普通事件批量晋升。

### 3.3 不参与这一淘汰池

作者核心角色背景、`details`及其历史、常驻稳定认识、当前状态／任务／预约、学校学期与科研安排、原始聊天／经历／公开剧情记录，都不作为100／3000条经历容量的删除对象。学校计划不是可被普通记忆压力抹掉的事实。

仍服务于活跃短期的关联长期先保护，避免详细记录尚在而长期主身份已经退出。本次提前转入或真实恢复的长期保护至当前容量处理结束，不能刚接上简要摘要／完成恢复就立刻将同条挤出；归档其他合格候选，无法归一时按临时超量规则继续。常驻记录不自动淘汰，但空闲审核可以发现重复或依据不足的认识；次数高不等于永远正确。

### 3.4 目标上限，不是拒绝写入阈值

新增记忆必须先获得正式身份和来源，不因达到容量拒绝本轮段B或丢掉新事件。正常情况下，在写入后的短事务中按规则退出必要条目，将活跃数归一到目标；不调用模型、不等待网络。

旧库首次启用、特殊配置导致保护对象超过目标等情况，允许明确的临时超量：记录差额和容量待办，逐单元处理，前台继续。不能为了宣称绝不超量而删除受保护身份。默认100／3000下，活跃短期所需长期通常只占长期池的一小部分。

`null`可关闭对应容量；降低容量不删除正文，升高容量也不自动唤醒所有归档。若目的是限制SQLite文件大小，需要另定归档导出／清理规则，本稿不声称已做到磁盘容量封顶。

## 4. 哪些条目先退出

“衰减最高”和“唤醒最少”不是同一个量。一个从未被提及的新事件也可能重要；同一次长对话中的多轮重谈也不能冒充多次有效唤醒。

建议程序按如下排序选择退出候选，先移出排序靠前者：

1. 排除本层受保护身份；普通重要度先于`importance=high`。
2. **累计有效唤醒日期数升序**，使用`totalAwakenings`，不用续期后会清零的`windowAwakenings`。
3. 衰减比例降序。
4. 真实新进展／有效唤醒时刻更早者先退出；再按`happenedAt`、`createdAt`更早、ID稳定排序决胜。

短期的唤醒依据取其关联canonical长期的真实日期计数；长期取自身canonical计数。后台读过、检索命中、模型重写摘要和Embedding重建都不给保留加分。

衰减只作为可计算的排序值，不新增模型评分：

```text
lastMeaningfulAt = max(lastEventUpdateAt, 最近有效唤醒的firstEffectiveAt)
decayRatio = clamp((now - lastMeaningfulAt) / layerDays, 0, 1)
layerDays = 短期7天，普通长期90天
```

没有唤醒时使用真实事件更新时刻。这里的衰减不改变`expiresAt`，也不另外制造续期。按配置的当前Clock计算，单位用实际时长；不把后台处理时刻当作“刚经历／刚想起”。

这种次序优先保护重要度和真实反复提及，再用时间区分。若唤醒数、衰减等相同，确实优先退出更早的事件。剩余期限仍按原机制决定自然到期；容量提前退出是另一种明确原因。

## 5. 退出后如何保留和恢复

### 5.1 短期提前退出

例如7天内已有100条，新来第101条。基础提取已给每个事件生成`eventSummary`和`feelingSummary`，因此不需要先找另一模型压缩才能接纳：

1. 按排序选择应退出的详细短期条目，保留其详细原文、来源及事件时间。
2. 确认关联长期存在且有可用简要摘要；普通预备长期提前进入可见期，避免“详细记录退出了，摘要还要再等几天”的空档。
3. 这次提前转层不算唤醒。对尚未生效的普通预备长期，保留起点改为实际退出详细层的时刻，并同步原预备初始grant；90天从这个新起点计算。已有实际生效的长期、有效续期或durable不因这次操作重置期限。
4. 原七天截止和退出原因保留，空闲后可改进简要摘要；失败也不撤掉已有摘要。

不把关闭容量后再次暴露旧短期当作新经历；原详细记录只通过合适的归档查询访问，后续真实新进展需要按当前来源继续该事件。

### 5.2 长期容量归档

容量归档使该长期退出日常`current`检索，保留ID、内容、来源、唤醒日期、grants及索引。它不同于`discarded`：有过唤醒的经历也可以退出普通容量池，但不因此被永久抹掉。

程序需增加明确容量退出标记及原因，查询时同时检查日期和容量标记；不要伪造过去的`expiresAt`或挪用`merged`来表达归档。可选字段的具体类型在实施细化时固定；逻辑上至少要记录实际退出时刻和短期／长期容量原因。

### 5.3 明确回忆和重新激活

“还记得那次……”等符合现有权限的请求可查容量归档；普通查询不悄悄扩大为所有档案。单纯查到不恢复、不计唤醒。

只有本轮有合法真实重谈来源且模型明确awaken，才可清除长期容量归档标记并重新激活；canonical身份和每日去重沿用原规则。首次从容量归档重新激活采用原归档激活的90天窗口语义，需要扩展当前只检查日期过期的激活分支。既有更晚有效保留期限不缩短，同一次重谈不同时成为续期所需的另一份证据。

重新激活也占3000条目标，必要时归档另一条低优先记录；不能无限靠“恢复”突破容量。恢复长期不自动恢复旧短期全部详细内容到100条池。

所有容量变更和恢复提高`stateVersion`，正式结果及处理标记在同一事务；正文不变时不为了换可见层反复建Embedding。旧快照维护结果继续用readSet检查，不能把刚归档／恢复的记录按旧状态覆盖回来。

## 6. 空闲15分钟的程序口径

### 6.1 空闲起点

“对话结束”没有额外结束按钮，采用可恢复的程序静默判断：

```text
idleAnchor = 最近一次正常输入或【推进】到达时刻、
             最近一条已确认实际发出输出的时刻、
             最近一个非环境故事轮completedAt、
             最近一次角色实际参与／获知的新事件确认时刻、
             最近一次受保护活动开始／实际结束时刻
             上述时刻中的最晚值
idleReadyAt = idleAnchor + 15分钟
```

双方最后消息都计入，让模型的回复耗时不侵占空闲窗口。纯静默故事也从正式完成之后等15分钟，不能因为没有输出就视为从未被唤醒。计划开始时刻、尚未发送草稿、世界／学校仅写客观安排、索引或维护自身完成不重置这个窗口；学校通知被角色实际获知、真实事件进入生活故事时则刷新。

**等待期间发生新对话或新角色事件，立即失效旧空闲截止并刷新15分钟计时。** 新输入到达时先刷新，不必等模型选择回复；新输出／正式故事完成之后又以更晚时刻刷新。开始共同活动等受保护活动时，计时刷新且深度整理资格关闭；活动结束及最终故事完成后重新等完整15分钟，不累计活动开始前已等的那部分。平台重复投递或同轮恢复不冒充一份新交互。

该刷新规则同时作用于待准备、等待重试和已ready尚未应用的深度任务，不仅取消一次timer。一个后台请求已经在途时可继续计算，结果ready后仍须满足最新空闲截止；后台结果完成不把这个截止再向后推，否则会形成维护自身永远延期的循环。

共同活动未正式结束时，无论双方有没有输出、60秒下一节点是否到期，都不启动或正式应用深度整理。共同活动结束按最后公开输出、最终轮完成和结束时刻中的最晚者，再完整等待15分钟。

其他正在进行的明确活动，按`scene.activity`的实际起止和状态判断；活动开始前不阻挡，结束后重新等15分钟。`phoneAccess=true`表示可读消息，不等于活动已结束。“在寝室”这类场景文字和未来计划不自行变成活动门禁；结束未知时不猜一个截止，等后续正式状态／经历确认结束，不设0ms循环。

`expectedEndAt`可以作为重新检查的预计时点，不单独证明角色已经完成活动。实际结束由正式故事／活动状态提交确认；预计时点已过但仍未确认时，等待正常输入、已有故事截止或状态变更，不为了后台整理额外推进生活。

**睡眠例外建议：** 沿用V0.3睡眠期间可后台维护的安排，睡眠本身不作为必须等起床的活动门禁；仍须满足无新收发／无故事完成满15分钟，以及没有可执行前台轮。后台整理不生成角色经历、不推进生活时钟、不代表角色在梦中读消息。本例外只针对睡眠；若希望睡眠也等待结束，可在审核时取消此例外，届时04:30只登记待办，不能强行执行。

### 6.2 增量待办及一次定时器

每个成功故事段B只登记本轮触及的记忆／细节版本及来源线索，重置空闲截止；不在那里执行第二个深度整理模型。重复恢复登记幂等，空结果没有新待办时不为了“到15分钟了”空调模型。

达到截止后，在既有Host后台准备槽选快照和批次。每批最多20个候选，关联长期、learned投影和必要事实证据作为readSet依赖，不因20条把必要关联截掉；仍不加字符预算。一次背景请求最多一个，与索引共用已有槽。

截止、活动门禁、pending／ready及retryAt都纳入已有单个Host计时器。活动未结束或输入正在合批时，不将已过去的空闲截止反复作为now；等可确定的活动结束、前台截止、重试时刻或实际状态变更唤醒。

### 6.3 新消息和活动怎样让位

深度计算已经开始后收到消息：输入先落库，重置15分钟截止，前台照常闭合和运行；不为了新消息取消在途请求，避免浪费。旧请求可以将结果存为ready，但新空闲条件未满足前，不应用正式记忆，也不启动下一批。

真正应用时，每次最多一个维护单元，检查readSet和当前空闲／活动条件，事务结束后`setImmediate`让出并重扫前台。冲突只作废该单元，最新版本重新排待办；已经过时的结论不能覆盖本轮新认识。

旧轮恢复、实际消息／预约／起床／共同节点、合格通知轮、世界学校步骤及自主推进继续按现有优先级执行。后台不能因为“已经等了15分钟”取得前台优先权。可读性与空闲条件不是一回事，不可读时仍只使用已看过的消息和已正式提交经历。

### 6.4 每日04:30、到期和索引

保留04:30作为到期／漏办周期入口，并增加空闲增量入口。到期短期及30次候选也受新空闲门禁；日期过期时先由查询退出，预备长期按正常日期可见，不依赖压缩成功才接上。

每轮、到期、容量转层、晋升证据变化产生的待办按owner版本去重；不能每天重新审核全部3000条。周期cutoff固定，不能追着新消息扩大本批。离线后只补当前已到期和未处理版本，不补造每一天的故事／审核；重新上线先恢复前台，再等恢复后的空闲条件。

空闲锚点跨重启保留。若没有需恢复的前台、活动门禁也已解除，且持久化15分钟已过去，可处理待办，不强制因纯重启再等15分钟；恢复一个旧故事时，则按其实际completedAt刷新。

索引是派生数据，不承担“认定事实”责任，可继续在现有前台空闲点准备／提交，不必满15分钟；仍每次一个单元、前台优先。新短期或detail没有向量时可以立即词法使用。这个区别应在调度实现中按任务类型区分，不能把全部maintenance表一刀切延后。

失败沿用后台重试和ready保存，不把后台失败转为全局暂停；人工暂停不启动或应用，恢复后按持久化截止重新判断，stop沿用取消／关闭顺序。已有重试到期也不得绕过15分钟及活动条件。

## 7. 深度整理和固定信息审核具体做什么

### 7.1 记忆整理

基础每轮提取已负责事件、细节和感受，空闲整理检查增量，允许：

- 确属同一事件的重复短期／长期合并，完整保留事件范围、阶段感受和来源，不把共享词汇当同一事件。
- 改进预备／到期摘要；七天未满且未受容量压力的详细短期继续保留，不能每次空闲把所有短期提早压成长期。
- 整理已提前转层的摘要，处理到期及未唤醒、确无持续意义内容；后者仍沿用严格discard合同，与容量归档分开。
- 对达到30个有效日期且证据版本变化的候选做promote／retain判断。

当前consolidation的merge合同只支持至少两个长期主身份；将短期重复项合成一个详细主记录需要新增正式合同和应用规则，不能只改提示词让模型越过现有限制。

### 7.2 三类固定信息

| 信息 | 每轮处理 | 空闲审核边界 |
| --- | --- | --- |
| 作者核心背景／身份约束 | 按既有设定使用 | 可以发现冲突，不能自行重写作者文件或另造身份 |
| 手机、室友姓名、专业等具体事实 | 有合法来源的新事实或修订立即更新details和历史 | 核对本轮增量是否重复key、混淆对象或缺依据；不套90天、不要求30次 |
| 常驻经历／稳定认识 | 每轮可基于真实重谈增加候选证据 | 经历可常驻；稳定认识要不同事件支持，不能从单次情绪推成永久性格 |

固定信息审核不是再定时扫描整个人设，也不是新加一个可以随意改事实的导演。建议扩展现有`memory_consolidation`的增量审核职责，仍用独立Flash／high配置，不创建另一个模型槽；每轮`memory`也继续Flash／high，允许日后分别换Pro。

审核输入只带相关已提交版本、合法可见来源和必要核心约束，新增依赖都进入readSet。明确已有来源的事实修订须保持原sourceIds规则；后台总结不能伪造“本轮用户说过”。建议初版事实纠错只报告冲突／重复建议，不自动回滚已正式确认的details；后续新来源或用户明确修订仍由每轮链更新。

审核可以保留、合并同义稳定认识、发现结论超出证据并提出撤回建议。涉及核心身份或依据不清的长期认识，不静默改背景、不直接生成联系用户的任务。持久化审核结论和候选版本，避免无新证据重复调用；哪些修订可自动应用由后续实施合同逐项列明。

## 8. 需要修改的接口及数据范围

本方案不增加向量数据库、不新增通用语义评判服务；复用MemoryStore／Lifecycle、后台快照及单元机制。实施细化需固定以下变化：

| 范围 | 必需变化 |
| --- | --- |
| 配置 | 独立短期／长期活跃容量100／3000，允许null关闭；`idleMaintenanceMinutes=15`。不复用shortItemsLimit／longItemsLimit，后两者仍是检索选入限制 |
| 主记录 | 容量退出时刻／原因、短期提前转层依据；保留现有canonical、日期、来源及双版本 |
| 查询与恢复 | current排除容量退出，archive按原权限开放；容量归档真实重谈重新激活；短期退出与普通预备长期提前生效同事务 |
| 空闲状态 | 持久化最近有效交互／故事完成／活动结束锚点、增量待办版本及审核处理记录；不能仅使用进程内timer |
| 后台模型 | 增量候选与相关依赖、短期合并合同、稳定认识审核结果；不自动越权改核心或details |
| 调度 | 深度准备和正式单元应用均受空闲／活动门禁，纯索引保留现有路径；一后台槽、一计时器、前台优先 |
| 状态观测 | 活跃／预备／归档数量、容量目标／临时差额、提前转层／恢复次数、增量待办、空闲截止及阻挡原因；不记录私聊正文日志 |

旧库不能仅凭加载配置就大批物理删记录。建议首次启用先输出数量和拟归档清单，再按后台分批归一；全部正文可追溯，正式启用流程写入后续细化。增加JSON字段可兼容旧行，是否需要版本标记由正式迁移／合同变更决定，不凭文档版本V0.4直接把数据库schemaVersion改4。

## 9. 验收场景

1. 第101条短期进入后，弱条目退出详细层但对应摘要立即可查；未满7天不会产生几天无记忆的空档。
2. 普通长期第3001条含预备项，按canonical计数归一；details、作者核心、常驻及学校安排不减少。
3. 重要度、唤醒数、衰减相同时先退出更早者，最后ID排序确定；刚提取的重要一次性经历优先于普通琐事。
4. 同日多轮重谈／检索命中／压缩／索引重建不增加有效次数、不伪造“刚发生”；3次续期和30次候选沿原规则。
5. 归档可明确回忆，但仅检索不恢复；真实重谈恢复长期后再平衡容量，短期全文不随之回到活跃层。
6. 普通长期预备项提前生效同步保留起点与初始grant，实际有效续期不被短期转层重置；合并的来源、日期和情绪保留。
7. 用户10:00发最后消息，角色10:03发完、10:04故事完成，最早10:19深度准备；10:18再有消息，原截止失效并后延。
8. 共同活动中双方长期无输出，深度整理仍不启动；活动10:30结束且最终轮10:32完成，最早10:47。
   若原本10:19到期、10:18共同活动开始，则10:19不能启动；先前已等的14分钟不能抵扣活动结束后的15分钟。静默节点事件及新对话都刷新，已ready结果也等待新截止。
9. 明确个人活动未结束／结束未知不猜空闲；睡眠例外遵守本稿约定。纯未来计划／普通场景文字不永久挡住后台。
10. 已在途深度请求期间新消息到达，前台仍可发送；旧结果存ready，不能在新15分钟窗口前应用。单元之间真实让步。
11. 空闲前半段重启、ready恢复、暂停再恢复、04:30到期和retry到期均不绕过空闲门禁；没有可做事项时不0ms空转或空调模型。
12. 后台旧快照遇前台修改／容量归档／真实恢复，stateVersion冲突只作废对应单元，不覆盖新状态，其他单元仍可在合格窗口应用。
13. 三十次单事件不能变成用户永久性格；跨事件稳定认识也不能改作者核心背景。共同代写只能按已有公开经历合同记忆。
14. 索引准备不必等15分钟，新具体事实仍可当轮使用；原默认不限字符／token人为预算与检索相关性规则不变。
15. 旧库超量分批归一，新记忆及前台不被堵住；临时受保护超量可见，解除保护后继续处理，正文／来源没有物理删除。

## 10. 本稿推荐配置和审查重点

推荐初始值：短期活跃目标100、普通长期目标3000、基础提取每轮、深度整理空闲15分钟、后台准备并发1、每批候选20。7天／90天／3次续期／30次常驻候选及模型独立配置沿用；索引及时处理，当前上下文人为预算仍默认不限。

审核重点是容量计数包含预备长期、短期提前退出不会失忆、归档恢复不伪造唤醒、已有长期期限不被转层重置，以及15分钟门禁覆盖ready应用和活动静默轮。睡眠是否沿用后台维护例外、容量归档而非物理删除、100／3000是否作为初始活跃目标，可在本方案审核时调整；不需要为了这些选择先改生产代码。
