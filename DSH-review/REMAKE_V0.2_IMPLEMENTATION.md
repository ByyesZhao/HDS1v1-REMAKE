## 1. 文档范围

本文展开已落地的正常业务衔接：睡眠区间、待看消息与输入批次、候选冻结、发送和一次提交。

本文描述当前数值、字段和默认策略；共同活动开始/结束固定标志已实现。离线测试、Koishi Context 加载和少量供应商探针已有记录；QQ 实际发送、新图视觉描述和完整人物故事效果仍是接入验收项，不能由固定返回测试代替。

本次审阅后按用户新决定调整：表情包按角色每条非线下文字短段计数，长期目标为 5%，不再按“有意愿且匹配到素材的回合”计数；该口径同步覆盖生活与接口文档。主动联系的资格规则和 15% 目标不变。

### 1.1 全局约束

- 只做单角色一对一私聊，不需要群聊和合并转发。
- 一个插件、一个进程、一份故事状态即可。
- 程序内部用 TypeScript 对象传输，模型输出用 JSON。
- 故事时区初始为 `Asia/Shanghai`；持久化时间包含日期和偏移。
- 用户连续输入以最后一条消息后静默 15 秒为批次边界。
- 个人自主间隔均匀抽取 150～210 分钟；聊天不重置周期。
- 只叙述已经经过的时间；私人文字计划不生成活动定时任务。
- 清醒共同回合的已合批输入统一可见；睡眠期间暂停故事回合，普通私聊再判断手机接收条件。
- 共同活动以旁白在 QQ 发送 `【共同活动开始】`、`【共同活动结束】` 为明确标志。
- 保留独立表达模型和每轮逻辑记忆整理。
- 旧轮发送与后处理完成后再开始下一轮，新消息仍立即落库。

### 1.2 控制范围

按网络、电力稳定、单人使用的环境实施。不增加自动切换供应商、重试退避框架、熔断、分布式锁、消息中间件、健康检查、告警面板、备份体系、故障矩阵或多层输出审核。

原架构已经明确的输入保存、冻结稿续发、一次事务提交和控制格式修补继续保留，集中在 `storage.ts / recovery.ts / model/client.ts`。它们不再扩展为独立平台；恢复专题末尾列出的全面退出位置测试、版本冲突诊断、平台查询/幂等适配不进入本期任务。

字段类型、时间区间和消息可见性仍需确定：这些决定正常业务语义，不属于为少见意外增加的防御性编程。自由叙事不做质量打分或语义审查。

### 1.3 Review Focus：五项正常行为检查

| 场景 | 必须保持的行为 | 任务 |
| --- | --- | --- |
| 旧轮发送时用户连续输入 | 继续保存并合批，不插入旧轮，也不提前结束 15 秒等待 | T1、T3 |
| 洗澡期间收到消息 | 新正文不进入主叙事、个人导演、检索查询或整理输入 | T2、T4、T6 |
| 预约与自主周期同时到期 | 一轮处理；预约回复不抽主动概率，自主周期仍被消费 | T4、T7 |
| 本轮开始或结束共同活动 | 当前输入按入轮模式解释；切换不追溯改变可见性 | T5 |
| 已看消息选择稍后回复 | 已看状态保留；到期重新考虑，不直接发送旧草稿 | T4、T6 |

## 2. 已采用的实施选择

采用原架构和本配套实施说明，以下是当前工程实际选择。

| 项目 | 当前实现 |
| --- | --- |
| 工程形态 | 一个 Koishi 插件工程，目录沿用接口文档第 11 节 |
| 时间来源 | 一个可替换的 `Clock`；入轮取一次时间，发送确认及提交另取实际时间 |
| 调度 | 一个定时器指向最近有效截止时间；唤醒后重新计算，不为每条任务创建长期定时器 |
| 随机 | 一个 `Random`；生成期间抽取，冻结后不重新抽取 |
| 数据库 | 一个 SQLite 文件、一个薄存储入口；不同时保存正式 JSON 故事文件 |
| 模型调用 | 各导演是任务配置；同一供应商连接可供多个任务使用，不常驻独立代理 |
| 测试 | Vitest、可控时钟、固定模型返回；验收行为，不断言文学措辞 |
| 输入范围 | 首版处理文本和文本形式的动作；图片、语音理解不在原方案中，暂不新增模型链 |
| 表情素材 | 手动导入的本地素材；不自动收集用户图片 |
| 世界联网 | 可选，默认关闭；先完成虚构世界简报闭环 |

`runtime/koishi.yml` 保存 `botId / userId / databasePath / storyConfigPath`；私有 `config.local.json` 保存时区、背景文件引用、表达指导、初始场景、各任务模型、作息、历史预算、Embedding 和联网资料 URL。凭据从配置目录的 `key.txt` 载入环境变量，已有环境变量优先；素材维护命令接受导入目录，单张素材路径保存于 SQLite。只绑定目标私聊。

数据库使用 `DatabaseSync`，同库事务已离线验证；QQ 适配调用 `bot.sendPrivateMessage`，要求非空消息 ID 列表，实际 QQ 返回仍待联调。DeepSeek 固定 JSON 与 qwen 向量探针已通过，新图看图描述尚未在线验收。

## 3. 运行数据：补足业务上缺少的字段

以接口文档已有 TypeScript 类型为基础，下列是程序持有的增补，不要求模型重复输出。

### 3.1 消息、批次、回合是三个概念

`messages` 当前字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 程序生成的消息 ID |
| `platformMessageIds` | 平台返回的消息 ID 列表；输入通常一项 |
| `direction` | 用户输入为 `incoming`，已确认的角色输出为 `outgoing`；系统命令及 `error` 不进入故事消息 |
| `receivedAt` | 输入实际收到时间；输出以确认时间另存 |
| `content` | 原文或最终发送正文 |
| `batchId` | 输入所属批次；输出为 `null`；只作分组键，不建独立批次历史表 |
| `seenTurnId` | 输入首次让角色看到并正式提交的回合；未看为 `null`；输出为 `null`，不参与待看输入查询 |
| `turnId / outboxSeq` | 输出对应回合与发送项；输入留空 |

单例运行记录 `runtime` 放在 `state` 集合，保存：

- `openBatch: { id, readyAt } | null`：仍在接收消息的批次。
- `pendingBatchIds: string[]`：已结束合批但尚未首次由入口处理的批次，按顺序排列。
- `paused: boolean`：仅保留原文要求的插件暂停开关。
- 世界/学校下次更新时间和概率未命中次数。
- `lastError: string | null`：调用失败时保存错误，人工恢复时清空。

收到输入时，同一短事务保存消息和 `openBatch.readyAt = receivedAt + 15 秒`。截止后移入 `pendingBatchIds`，清空 `openBatch`。如果下一条到达时旧截止已过、定时器尚未执行，先封闭旧批再创建新批，不能把已经静默满 15 秒的两次表达重新粘在一起。

入口消费某个批次，只表示已判断它如何处理，**不表示已看**。暂存的批次从入口队列移走，其消息仍通过 `seenTurnId = null` 查询。查询待看输入时排除 `openBatch`，并按收到时间及插入顺序排序。这样不会每次唤醒都为同一批不可接收消息新建回合。

`TurnRecord.inputMessageIds` 保存本轮选取的已合批输入，包括最终可能不可见的消息。冻结结果额外保存 `visibleMessageIds`；只有后者交给个人导演、整理模块，并在段 B 标记已看。引用了输入 ID 不代表角色读到了正文。

普通入口一次取最早的新批；此前已由入口暂存的待看消息在可接收时一同交付，不额外吞并队列里其他尚未处理的新批。起床或待看检查可以一次交付所有已合批待看消息。仍开放的批次始终排除。入轮后到达的消息不会追加到已选输入。当前回合消费的队列项在段 B 移除；直接暂存而无需模型的路径在其短事务中移除。移除按选取的批次 ID 操作，不以旧快照覆盖期间新增的批次。

### 3.2 正式状态与运行元数据

正式状态包括角色状态、经历、记忆、有效约定、已看标记和概率计数。运行元数据包括输入缓冲、回合、发送项和后处理结果。

允许立即更新输入缓冲和发送进度；普通模型回合的正式效果只在段 B 写入。明确睡眠/不可接收区间内仅暂存输入，以及入睡边界清空自主周期，属于程序控制短事务，不强行调用三个模型。

### 3.3 冻结结果内容

`TurnRecord.frozenResult` 序列化以下材料即可，不建立另一套事件溯源账本：

```ts
interface TurnCandidate {
  visibleMessageIds: string[];
  reconsiderMessageIds: string[]; // 延后回复引用的已看消息
  narrative: NarrativeResult | SharedNarrativeResult | null;
  personal: PersonalResult | null;
  expression: ExpressionResult | null;
  experiences: Experience[]; // 程序分配 ID 后冻结的经历
  nextState: CharacterState;
  taskChanges: TaskChange[];
  completedTaskIds: string[];
  probability: {
    contactMisses: number;
    stickerMisses: number;
  };
  autonomousIntervalMinutes: number | null;
  environmentChanges: EnvironmentChange[];
  nextEnvironmentAt?: ISOTime; // 生成候选；提交时按实际完成时间重新计算
}
```

类型中的 `EnvironmentChange` 见第 10 节。经历条目、新任务和记忆条目的 ID 在写入相应工作区时分配并保存。`nextState.nextAutonomousAt` 在需要重排周期时由段 B 使用实际 `completedAt` 和保存的间隔最终填入。

`contactMisses / stickerMisses` 均表示连续未命中次数，越大越接近触发，不是倒数剩余次数。前者按合适主动联系机会计算，后者按每条非线下角色文字计算。`probability` 是输出全部确认后要应用的最终计数：未命中加一，命中且对应输出完成归零，无机会保持原值。表情包在同轮按文字顺序多次更新工作区计数，再冻结最终值；发送未完成前不能提前写入正式计数。

### 3.4 存储形态

实际使用内置 `node:sqlite`，文件库为 WAL + `synchronous=FULL`。`state` 为 `(key TEXT PRIMARY KEY, data TEXT NOT NULL)`，其他逻辑表为 `(id TEXT PRIMARY KEY, data TEXT NOT NULL)`。业务字段统一序列化进 JSON，没有独立的时间或状态列。`details` 当前值与 `detail_history` 分表，`memories` 用 JSON 内 `kind = short / long` 区分。薄存储层读取 JSON，由程序筛选排序。

已建 JSON 表达式索引：输入方向/已看标记/收到时间、消息批次、任务状态/到期时间、未完成回合、记忆类别/时间。细节语义 key 直接作为行主键，`outbox(turnId, seq)` 和 `post_jobs(turnId)` 有唯一索引。完成标记为 `turns.done`，`post_jobs` 只保存结果。已导入旧图库，不迁移旧聊天、记忆或人物状态。

## 4. 串行运行入口与调度规则

### 4.1 公共程序接口

共享类型位于 types.ts，公共入口由 InputBuffer、Scheduler、SerialHost、HdsiApp 的类方法提供。

```ts
interface Clock { now(): ISOTime }
interface Random { next(): number } // [0, 1)
type TriggerKind = TurnRecord['triggerKinds'][number];
interface TurnRequest {
  inputMessageIds: string[];
  taskIds: string[];
  triggerKinds: TriggerKind[];
  batchIds?: string[];
  environmentKind?: 'world' | 'school';
}

// InputBuffer / SerialHost：已通过目标私聊过滤的输入
acceptInput(message: IncomingMessage): Promise<void>;
// Scheduler：只选择有效原因，不调用模型
collectReady(now: ISOTime): Promise<TurnRequest | null>;
nextDeadline(now: ISOTime): Promise<ISOTime | null>;
// HdsiApp：SerialHost 串行调用，应用也检查未完成轮
runTurn(request: TurnRequest): Promise<void>;
// HdsiApp 方法，调用 recovery.ts 的阶段函数
resumeUnfinishedTurn(): Promise<void>;
```

上述为类方法签名示意。依赖由插件入口 index.ts 组装；app.ts 定义应用依赖与回合执行，recovery.ts 提供冻结、发送、后处理提交和未尝试稿丢弃函数。

时间比较和间隔计算使用毫秒时间戳，不按 ISO 字符串排序；持久化允许 Z 或显式时区偏移，日程生成与用户状态展示使用配置的故事时区。

### 4.2 每次唤醒的顺序

1. 更新已经到期的合批窗口。若插件暂停，只保存输入，不启动故事回合。
2. 若旧轮仍在执行，记住“有工作可做”即可；旧轮结束后重新扫描，不保存大量过时定时器事件。
3. 持久化状态未暂停时，启动先续办未完成旧轮；已暂停则等待 `hdsi.resume`。选择新轮时先处理入睡边界，再优先执行到期世界/学校更新，之后合并起床与故事触发。
4. 收集当前有效的输入、预约、消息检查、场景节点、自主周期。一个回合包含所有已到期的故事原因，不为每条任务单独调用主叙事。
5. 有世界/学校更新到期时，先作为同一串行入口下的独立环境回合提交，再重新收集当前有效原因处理故事回合；环境更新不直接触发个人导演。
6. 完成本轮后重新读取最新状态，设置唯一下一次定时器。

入睡时间与自主周期恰好同时到期时先执行入睡，自主周期终止。起床时合并到期预约及已合批待看输入；只产生一个起床回合和一段新的自主间隔。

睡眠期间过期的预约和消息检查保留原定时间，但从定时器候选中排除；起床再处理。当前共同场景的节点在睡眠期间同样不推进，醒来再叙述；睡眠不是程序擅自确认“活动结束”。环境更新仍可运行。

### 4.3 当前活动与消息检查

普通私聊明确处于不可接收活动的有效区间，直接暂存输入。有已知结束时间时维护一项 `check_messages/unread`，合并待看消息 ID，不为每条输入各建一个相同检查。

`expectedEndAt = null` 时不建活动定时器。到达已有检查时间，必须先更新叙事，再判断可见性；仍不可接收就改到新的预计结束时刻。如果叙事改为未知结束时间，取消该定时检查，消息保留为未看，等待其他已有触发点。

单纯结束普通吃饭等活动、没有待看消息或其他触发时，不必唤醒模型。以后第一次回合会补齐经过；需要精确推进的共同剧情使用 `scene_step`。

### 4.4 一轮的算法

1. 取 `at = clock.now()`，读取正式状态，保存 `TurnRecord`，固定本轮选取的消息 ID、任务 ID、触发原因和入轮模式。
2. 在工作区更新已到期的时间条件。普通主叙事仅用旧场景、计划和已知资料检索；共同主叙事还可用本轮场景输入。
3. 调用主叙事，叙述区间为 `[narratedUntil, at]`，合入当前场景和体力。无事件可输出空经历；程序将候选 `narratedUntil` 更新为 `at`。
4. 按**入轮模式**确定可见输入：共同场景直接可见；普通私聊按更新后的处境判断。生成 `visibleMessageIds` 后才装配个人导演的检索查询和上下文。
5. 选择个人合同：共同场景优先；其次是可见新输入、可处理的延后回复检查或到期预约；其余使用私人生活合同。单纯不可接收输入引起的场景更新可不运行个人导演。
6. 应用个人结果到工作区：情绪完整替换，文字计划按缺省规则处理，睡眠和任务按下文处理。存在自主触发仍要保存下一间隔，与个人合同无关。
7. 判断回复或主动联系是否真正需要表达。需要时调用表达模型；对每条非线下文字短段依次抽样，命中才检索表情素材。按第 8 节组装开始/结束标志、公开旁白、角色短段和表情包的有序输出。
8. 同一短事务冻结候选、完整 outbox 和 post job。无输出立即标记 `outputComplete`。
9. 依原规则发送；完成后整理一次记忆，再在同库事务内提交本轮所有正式效果、`done / completedAt` 并清空冻结稿。

有主叙事但没有个人结果的回合仍保存经历并调用一次整理，即使经历列表为空；不读取不可见消息。纯程序入睡边界不虚构经历、不调用整理模型，起床主叙事统一补齐睡眠过程。环境和没有叙事的睡眠控制回合直接使用空记忆结果。

## 5. 预约、延后回复与共同场景

### 5.1 任务结算顺序

到期任务 ID 本身只表示“本轮候选要处理”。任务真正交付后默认完成，但同一 ID 的明确改期或取消优先于默认完成：

1. 以原任务和 `update` 部分字段合并得到完整任务。
2. `cancel` 保存为 `cancelled`；`update` 保存为 `pending` 并使用新时间；同轮对同一任务只允许一个明确变更。
3. 已实际处理且未改期/取消的到期任务保存为 `completed`。
4. 尚未能交付的检查保持待处理，或按当前接收条件重排，不误记完成。

预约到期即交给个人导演判断，不要求先有用户消息。角色可以回应、取消或改期，回复不走主动概率。只有“双方确认的具体约定”创建 `appointment`；任务 ID 和已有约定一起提供给模型。

### 5.2 延后回复

`reply.later` 创建一项 `deferred_reply`，引用本轮可见新输入与本轮重新考虑的消息 ID，描述保存新的回复意图。检查再次延后时优先更新当前检查，避免同一组消息累积重复待办。

到期后这组消息作为 `reconsiderMessageIds` 传入，不能混入首次可见列表。普通私聊仍不可接收时按活动/睡眠边界等待；结束时间未知则暂不把这个过期检查作为定时器候选，其他正常触发重新判断即可。

首次已看消息和重新考虑消息在整理输入中标明用途：旧原文不是新发生的对话，不能仅因又出现一次就加强长期记忆。新回复及本轮新经历照常整理。

### 5.3 开始共同活动

从普通聊天进入共同场景的这一轮，主叙事仍使用普通合同，避免尚未决定参与就生成共同结果。个人导演给出 `sharedChange.start` 后，程序在工作区初始化：

- `mode` 使用指定的线上/线下模式，`title` 使用指定标题。
- `progress = '已确认开始，待首个公开节点'`，`lastPublicNode = ''`。
- `nextStepAt = 本轮 at`，并登记一项到期 `scene_step`。

本轮先由程序发送固定旁白 `【共同活动开始】`，再发送角色的确认发言或动作；完成后提交模式和首节点待办。表达模型使用即将进入的线上/线下模式组织本轮输出，但本轮用户输入的可见性仍按入轮模式确定。下一轮共同主叙事生成第一个公开剧情节点；若已有合批输入一同处理，无输入也能开始公开场景。时间不人为加十分钟。

开始标志正文由程序固定产生，不让模型改写或把它混进角色台词。即使角色选择不说话，已确认开始也要发送标志。仅对 `chat → shared_online/shared_offline` 的实际进入发送一次；活动内普通节点不重复发送。初版切换到另一个共同活动先结束当前活动，再开始下一活动，不隐式覆盖当前标题。

`start` 本身不能宣告用户已到场或替用户完成行动。只有对话确实确认现在开始才输出它；预约、意向和角色单方面邀请都不够。

### 5.4 推进与结束

`Scene.shared.nextStepAt` 是场景节点时间的语义来源，`scene_step` 是调度用记录。每次共同叙事更新后只维护一项有效节点任务；新时间为 `null` 则取消旧任务，非空则创建或更新它。普通推进结果的下一节点时间应晚于本轮 `at`，即时首次进入是程序创建的特例。

本轮有公开正文才更新 `lastPublicNode`；为 `null` 时沿用之前的公开节点。角色实际动作已经进入输出，下一轮主叙事读取已确认动作作为已发生行为，不再替角色决定一次。

个人导演选择结束时，先按本轮既有共同场景发送公开节点和角色反应，将线上文字命中的表情包插在对应文字之后，最后发送固定旁白 `【共同活动结束】`；再提交 `mode = chat`、`shared = null` 并取消未完成的场景节点。即使没有剧情或角色短段，结束标志仍发送。保留主叙事给出的实际地点和活动；下一轮普通私聊恢复手机接收条件。

两个标志都使用既有 `OutboxItem.kind = narration`，payload 分别为不带外层括号的 `共同活动开始`、`共同活动结束`，发送器统一包装为 `【】`。它们随模式候选一起冻结，逐项确认，不经表达模型，也不新增消息类型或模型调用。标志不是剧情节点，不写入 `lastPublicNode`；整理可读取已发送标志，但不能凭此虚构活动结果。

用户看到标志即知道场景边界。程序仍在段 B 一次提交正式模式，不能为发送标志另开一次故事状态提交；期间新输入照常保存，下一轮在旧轮提交后读取新模式。恢复跳过已确认标志，未知标志沿用原有自动重发规则，不另做特殊恢复。

线下模式不发贴图；线上动作只描述虚拟活动或远程可表达的动作，不凭 `kind = action` 自动建立现实接触。

## 6. 睡眠安排：采用可解释的小规则

以下是 host/state.ts 的当前睡眠安排规则，不增设睡眠导演或睡眠债模型。

### 6.1 产生一份具体区间

1. 初始化时提供一份明确的下一次睡眠区间；起床回合生成下一晚区间。睡眠结束前沿用这一份，不每条消息重新抽取。
2. 默认入睡在当晚 23:30～次日 00:30 均匀取整分钟，起床在次日 08:00～09:00 均匀取整分钟。窗口按“这一晚”跨日展开，不按当前日期截断。
3. 初次排当晚区间时，体力为“疲惫”将入睡窗口提前 30 分钟，“精疲力尽”提前 60 分钟；其他档位不偏移。不随每次回合重复扣减。
4. 个人导演给出具体睡眠/起床建议时，在下一次正式入睡前用于修订候选。不得安排起床早于入睡；已过去的入睡建议按当前时刻开始，不倒写过去已经睡着。
5. 对已确认的次日早间预约，默认预留 60 分钟起床准备；候选起床时间取原候选与“最早相关预约减 60 分钟”的较早者。仅考虑这段夜间之后、默认起床窗口结束前的预约。
6. 次日早课由个人导演读取校园安排后给出具体 `wakeAt` 偏好。程序不解析自然语言课表，也不把学校所有事件都当成必须参加的课程。

只有 `reason`、两个时间均为 `null` 时，维持已有区间；没有区间才按默认窗口安排。提示词应要求：如果“早点/晚点睡”确实希望改变本晚时间，就给出具体建议时间。理由仍供叙事使用，程序不做关键词判断。

所有选定时间随候选保存。入睡后不再通过未看消息修改睡眠计划；起床回合消费旧区间并安排下一晚，避免重复触发同一次起床。睡眠是否生效仍按原文的时间区间推导，不另建 `isSleeping` 字段。

### 6.2 与回合运行的衔接

串行回合不被入睡计时器中途打断。若生成或发送跨过入睡时间，先完成当前冻结回合，随后立即处理入睡边界，停止自主周期；下一轮不会继续运行个人导演。睡眠开始不直接增加体力，起床后的主叙事根据实际睡眠经历更新。

若按预约提前起床落到入睡之前，arrangeSleep 抛出错误，应用保留未完成回合并暂停。程序不会自动求解冲突，也不会自行再调用个人导演调整；须人工调整安排或偏好后恢复。

## 7. 模型任务与控制合同

`model/client.ts` 提供一个入口：

```ts
runModel<T>(task: ModelTask<T>, input: unknown): Promise<T>;
interface ModelTask<T> {
  name: string;
  schema: unknown;
  prompt: string;
  parse(value: unknown): T;
}
```

实际使用 OpenAI 兼容 Chat Completions HTTP，默认 JSON Object + 本地 Zod Schema 校验；任务层不依赖 SDK。各任务按名分别选择连接。系统提示含固定职责规则与 JSON Schema，当前没有额外 few-shot 示例；动态输入独立序列化为用户消息。

正式配置与样例的十项任务均为 `deepseek-flash`。`narrative/narrative_shared/personal_chat/personal_life/personal_shared/expression/world/school` 使用 `reasoningEffort: low`，`memory/stickerDescriptionModel` 使用 `high`。任一任务可独立改为 `deepseek-v4-pro`；强度允许 none/low/high/max，省略为 high，请求传为 reasoning_effort。修补和本地查询续调用沿用同一任务连接。Embedding 独立配置，无思考强度。

### 7.1 只校验真正影响控制的内容

- 必需字段、分支、有限枚举和数据类型。
- 有日期和时区的时间、开始结束关系；经历时间落在本轮区间内。
- 任务修改引用实际提供的 ID；控制字段缺失不会由默认值伪造。
- 延后回复时间晚于本轮 `at`；普通后续场景节点时间晚于 `at`。
- `reply.now / contact.willing=true` 有意图与草稿；情绪列表允许空。

不校验情绪名称是否“标准”，不分析散文里的每个承诺，不增加语义审核模型。稳定细节冲突按记忆方案处理，不在每层再建一套事实核查。

原始调用后最多修补 **2 次**。同一任务接收原输出、字段路径和具体错误，重新返回完整任务 JSON；程序不保证有效散文逐字不变。每次任务运行另外最多允许一次 lookupDetails 本地查询及同任务续调用，不占修补次数。默认最多三次生成/修补请求，加一次查询续调用。普通 complete 的 HTTP 异常直接上抛；查询续调用位于解析 try 内，其异常进入同一有限修补路径。没有独立网络重试器；最终失败尽力发 error 并暂停。

### 7.2 提示输入的可见性

| 任务 | 本轮新普通私聊正文 | 本轮共同场景输入 | 个人草稿 |
| --- | --- | --- | --- |
| 普通主叙事 | 不提供，也不用它构造检索查询 | 不适用 | 只读已提交旧计划，不读本轮未产生草稿 |
| 共同主叙事 | 按入轮模式区分 | 提供已合批选取输入 | 不读本轮随后生成的草稿 |
| 个人导演 | 只提供通过门禁的部分 | 提供 | 自己产生 |
| 表达 | 提供与表达有关的已看部分 | 提供有关部分 | 提供已确定要发送的草稿 |
| 记忆整理 | 只提供本轮首次可见部分，复查原文另标用途 | 提供 | 不当作已发事实；未发送意图不进入事实来源 |
| 世界/学校 | 不提供 | 不提供 | 不提供 |

## 8. 输出、素材与概率

### 8.1 输出列表

固定顺序为：开始标志（仅实际开始轮）→ 本轮公开剧情旁白（有则一项）→ 表达 `parts` 原顺序，每条文字之后紧接它命中的表情包 → 结束标志（仅实际结束轮）。例如 `文字1 → 表情包1 → 文字2 → 文字3 → 表情包3`。同轮可以有多个表情包，没有命中就省略，不为标志或表情包拆出新回合。

`output/qq.ts` 的边界为：

```ts
sendItem(item: OutboxItem): Promise<{ platformMessageIds: string[] }>;
countVisibleCharacters(content: string): number;
delayMs(next: { content: string }): number;
```

文本计数按可见字素，组合表情算一个字符，去掉空白后计数。提示词要求动作 content 为裸正文，且不将动作包装塞进 text；当前解析器不独立检查此语义。`delayMs` 对实际 content 计数，发送器再按 kind 添加包装。等待四舍五入到毫秒，1/13/25 字分别为 3000/6500/10000，超过 25 字仍为 10000。

首个角色短段直接发送；开始/结束标志、公开剧情旁白和素材无字数等待。标志不占用“首个角色短段”的位置。`notBefore` 依据上一项真实确认时间计算并保存，不以模型生成时间预测全部发送时刻。空白段不建输出项。

### 8.2 表情包按角色文字逐条抽样

功能启用后，每条非空 `SpeechPart.kind = text` 是一次机会，排除线下共同活动。用户输入、`action`、公开旁白、开始/结束标志、系统消息和表情包不参与；相同 outbox 项的重发也不重复计数。三条文字就依次抽样三次，不设每轮一个的上限。

先抽样，命中才检索，不以严肃情境、是否有 `stickerIntent` 或素材匹配分数作前置门槛。查询以对应文字为主，可附加个人导演的 `stickerIntent`；没有意图字段就直接使用文字。素材导入保存 `id / path / description / embedding / embeddingModel`；用同一 Embedding 模型编码描述和查询，在薄模块内按余弦相似度取最高项，不设匹配阈值、不建向量数据库或“无匹配”分支。

启用前导入至少一项可用素材；未导入则暂不启用表情包功能，计数保持原值，不形成补发欠账。这是部署准备，不在每条消息上判断“素材够不够合适”。素材少时仍从现有库选最相关项，可能重复或不够贴切；通过补充素材改善，不再增加拦截规则。

抽样和素材选择在发送前按文字顺序完成并冻结：未命中将工作区 `stickerMisses` 加一；命中则插入素材项、将工作区次数归零，再计算下一条文字。整组输出确认后段 B 提交最终值。例：初始 2，三条结果为未中/命中/未中，工作区依次变为 3/0/1，最终提交 1；恢复复用清单和最终计数，不重抽。

`stickerMisses` 是当前单角色故事的一份持久化标量，初始为 0，跨轮延续，不在回合结束时归零。上一轮提交 1，下一轮就从 1 开始；经过多久、跨日、睡眠或模式切换均不清零。不计机会的项目保持原值；暂停功能也不清零，恢复使用原值，不补算停用期间文字。只有命中且对应素材实际发送成功才按前述提交规则归零。`contactMisses` 也是独立的跨轮计数，表情包命中不重置主动联系次数，反之亦然。

线下排除使用该条文字的**输出模式**：通常沿用入轮模式；有 `sharedChange.start` 时，开始标志后的角色文字使用指定的新模式；有 `sharedChange.end` 时，结束标志前仍使用原共同模式。因此开始线下活动轮和结束线下活动轮的角色文字均排除；下一轮普通私聊才恢复计数，沿用之前的 `stickerMisses`。本方案结束标志是本轮最后一项，不在它后面追加普通私聊文字。输入可见性按入轮模式，输出是否面对面按上述输出模式，两者用途不同。主动联系形成的文字与普通回复文字采用相同表情包规则。

更换 Embedding 模型、端点或维度时运行一次显式重建索引命令，不做后台双索引迁移。首版保留静态素材文件，不设计素材云服务。

部署补充（2026-10-07）：既有 67 条素材已经导入，aliases / embeddingInput / embeddingBaseUrl / legacyFingerprint 为可选来源字段。导入先核对源模型、端点、维度和指纹，再复制图片并保留 ID；仅维数相同不能直接复用。重建优先使用原 embeddingInput（描述与标签），清除旧指纹。当前为 qwen3.7-text-embedding，请求显式指定 1024 维；所需资料和图片在新项目内，运行不读取旧工程路径。

### 8.3 概率初始参数

沿用 `p(n) = min(1, p0 + step × n)`，`n` 是相应机会的连续未命中次数。表情包的一次机会是一条非线下角色文字，主动联系的一次机会仍按生活文档的资格与意愿定义。选择 `p0 = 目标频率 / 2` 后，按期望等待机会数求解 `step`：

| 项目 | 目标长期频率 | `p0` | `step` |
| --- | --- | --- | --- |
| 表情包（每条非线下角色文字） | 0.05 | 0.025 | 0.00177786838251657 |
| 主动联系（每次合适联系机会） | 0.15 | 0.075 | 0.0183782066846511 |

计算依据：设 `S(0)=1`、`S(k)=∏_{i=0}^{k-1}(1-p(i))`，一次命中前的期望机会数 `E=Σ_{k≥0}S(k)`，长期命中率为 `1/E`。以上数值已用该公式数值计算至显示精度；这是理论机会频率，不是实测每天的发送比例。

命中条件使用 `random.next() < p(n)`，未命中次数加一，对应输出成功后归零，正式计数统一在段 B 提交。表情包不检查主观意愿或匹配阈值；主动联系仍只在自主触发且采用私人生活合同的合适机会中抽样，无资格或无意愿不计联系次数。

表情包 5% 指长期“表情包数 / 非线下角色文字短段数”，不是“带表情包的回合比例”，分母也不含表情包本身。多段回复会产生更多抽样，这是逐条规则的预期结果。上表表情参数已按 5% 重新求解，主动联系参数保持不变。

每条文字的即时概率是 `p(n)`，不是固定 5%。一轮三条文字至少命中一次的概率取决于入轮计数；从 `n` 开始为 `1 - (1-p(n)) × (1-p(n+1)) × (1-p(n+2))`。`1 - 0.95³ ≈ 14.26%` 只适用于每条独立固定 5% 的另一种算法，不能作为本方案的逐轮验收值。

两条曲线分别在连续未命中次数达到 549、51 时封顶为 100%；这是线性曲线的尾部，通常会在封顶之前命中，不是固定每 549 条文字发素材或每 51 次机会才联系。如果希望更短硬保底，需要重新校准曲线，不能直接加大步长却保留原平均频率声明。

T7 用固定随机种子做一次离线机会抽样验证长期频率；封顶用直接设置计数的确定性测试验证，不等待随机模拟出现极长未命中序列。封顶不是常态发送间隔，但 `p(n) = 1` 时必命中仍是可验证的规则；不建立线上统计平台。

## 9. 记忆检索与整理

### 9.1 一个可落地的初始检索方案

角色记忆存储在 SQLite，由程序加载记录后匹配关键词，未使用 FTS 或向量检索。查询提取中文双字片段（单个汉字也保留）、英文词和数字，并去重。稳定细节 key / aliases 的直接匹配优先于正文模糊匹配。

单用户规模先在薄存储层读取候选文本、由程序计算匹配度即可，不强制依赖某个 SQLite FTS 扩展。以后真有性能需要再替换内部查询，调用方不变。

检索分两次：主叙事按旧计划、当前场景、相关安排检索；个人导演在门禁后按新经历、可见输入和当前场景检索。不能提前用未看消息的“手机型号”召回手机资料给主叙事，以免通过检索泄漏内容。

### 9.2 默认上下文数量

以下是 memory/context.ts 固定的当前筛选数量；仅 historyBudget 已开放配置：

| 内容 | 选取规则 |
| --- | --- |
| 核心背景、当前状态、本轮新经历、可见新输入、到期约定 | 完整提供，不因历史预算截断控制信息 |
| 最近对话 | 最近 30 条角色已看输入及实际角色输出；按时间排列，排除系统消息 |
| 短期摘要 | 最近 7 天，按时间取最近 12 条，排除与已选原文完全重复的来源 |
| 稳定细节 | 相关匹配前 12 项；相同 key 只取当前值 |
| 长期记忆 | 有查询词匹配才参与排序，取前 8 项 |
| 旧值历史 | 仅在“以前/变化过程”等相关查询时按 key 读取 |

实际长期排序为：相关度 × 重要权重 × (1 + 0.1 × min(提及次数, 5)) / (1 + 距最近加强天数 / 90)。普通权重 1，高重要权重 1.5；相关度是命中去重查询词的比例。不相关项不参与排序。

历史预算默认 8000，可由 historyBudget 设置；计数对象是整个历史上下文序列化 JSON 的去空白可见字素，包含字段名和 ID。超限按顺序移除低排名长期记忆、较旧短期摘要、较旧对话、旧值历史、低排名稳定细节。本轮输入、状态、经历及背景不在该历史对象中，不受此预算裁切。

### 9.3 稳定细节的主题查找

`details` 用稳定的语义 key，例如 `character.phone.model`、`roommate.linqing.hometown`，别名放自然中文。整理时把检索到的既有 key 提供给模型，更新使用同一 key，不通过换措辞创建第二部“当前手机”。

模型任务可先返回 {"lookupDetails":"主题"}，客户端本地检索后将 lookupResult 传回同一任务；一次 runModel 最多执行一次补查。预取已覆盖时直接生成。查询只读取本地当前值和相关历史，不是新的模型或通用代理系统。

该查找能力解决“模型写到某个预取未覆盖的具体属性”的正常需求；关键词召回仍可能不足，不能宣称一定消除所有事实不一致。

### 9.4 整理输入和提交

给本轮经历分配来源 ID；角色输出来源使用已确认 outbox 对应消息 ID。整理输入明确区分“已发生经历”“实际可见对话”“安排/意图”，不得将未来计划、未发表草稿、未命中主动联系文本转成事实。

短期摘要保留 `sourceIds`；长期创建保存初始提及次数 1 和当前加强时间，加强操作只针对既有 ID。只有实际重谈或新经历支持时加强，检索命中不自动加强。

真实变化或明确设定修订才更新旧细节，是整理提示词的语义要求；程序只校验结构及来源 ID，不独立判定事实真伪。合法值变化直接写入当前值和历史，同值变更整条跳过（也不单独更新 aliases）。短期超过七天只退出默认检索，不自动删除记录。

## 10. 世界与学校：增量输出合同

实际增量变更合同如下；模型不提供程序分配的 ID 或 status：

```ts
type EnvironmentChange =
  | { action: 'create'; event: Omit<EnvironmentEvent, 'id' | 'status'>; id?: string }
  | { action: 'update'; id: string; event: Partial<Omit<EnvironmentEvent, 'id' | 'status'>> }
  | { action: 'cancel'; id: string };
interface EnvironmentResult { changes: EnvironmentChange[] }
```

事件存储额外有程序字段 `status: active | cancelled`。更新合并旧记录，取消后不再作为有效安排注入，已有经历引用仍保留。环境更新不修改角色状态、消息已看、情绪或体力。

默认世界每天 06:00、学校每天 06:10 和 16:00，均可通过非空时点列表配置。首次故事初始化将两个更新设为立即到期；提交按实际完成时间选择下一个日程时点，不逐天补跑历史。学校模型按旧事件 ID 增量变化，学校事件不自动生成 appointment 或作息任务。

环境回合复用 `turns / frozenResult` 和段 B 提交边界，无 QQ 输出、不调用表达或个人记忆整理；`post_jobs.result` 可保存合法空 `MemoryResult` 后提交环境变更。它不推进角色 `narratedUntil`，事件何时被角色感知由后续主叙事决定。

联网默认关闭（webSources=[]）。开启时，从配置 URL 列表逐个抓取 HTML，移除脚本、样式、标签，合并空白并截取前 12000 字符，作为世界和学校共用资料。模型输出 basis/sourceUrls，程序检查 URL 属于本次材料及 web_reference 非空来源，不独立核验新闻正文，也不主动搜索其他网页。

## 11. 最小恢复与日常管理

实现直接遵守[恢复专题第 2～4 节](REMAKE_V0.2_RECOVERY.md)，不重新发明状态机。按 `done → outputComplete → 发送尝试/冻结结果` 判断续办阶段。

存储模块只需提供真正的 `transaction(fn)` 和必要读写操作；事务中不运行模型、不发 QQ、不等待分段。选择 SQLite 连接后验证其事务语义和正常重启读写，持久化配置沿用已确认的最低要求，不增加断电设备测试和文件系统故障模拟。

已实现三项管理命令，只绑定当前目标私聊：

- `hdsi.status`：展示暂停状态、当前阶段和下一调度时间，不进入故事记忆。
- `hdsi.pause`：阻止启动新轮；已有回合完成后停住，输入继续保存。
- `hdsi.resume`：解除暂停，按已保存阶段继续，再处理队列。

格式修补耗尽及模型、平台、后处理异常会保存 paused=true 和 lastError，并尽力发出系统 error，当前阶段不自动重试，输入仍保存。暂停跨重启保留，须 hdsi.resume 解除；意外退出但 paused=false 时，启动会先续办旧轮。未知发送项只在恢复入口启动后重发。

续办入口在启动扫描或 `hdsi.resume` 时，先把遗留 `sending` 保存为 `retry`，再按序续发；调用平台前仍先保存为 `sending`。当前调用明确失败或无法确认时立即保存 `retry` 并暂停，不退回 `pending`。

不增加重置故事、跳过记忆提交、强行标记已发等高影响管理操作。
