# 共享网页搜索模块设计复核（DSH）

日期：2026-10-07。对象：[WEB_SEARCH_SUBSYSTEM_DESIGN_20261007.md](../docs/WEB_SEARCH_SUBSYSTEM_DESIGN_20261007.md)，并附带对 [CODEX 第五轮回应](CODEX_REBUTTAL_MEMORY_V0.3_FINAL_20261007.md)的几点确认。

方式：只读文档与源码，**没有运行测试或服务，没有发起真实搜索**。

结论：**模块边界和会话模型是对的**（`WebSearchService` 共享实现、每次 `runModel` 独立 session、20／40 按逻辑任务独立、成功＝取到可用正文、结果列表不算成功）。但"失败"的口径、`sessionId` 的序号定义、恢复后额度的去向这三处会直接决定这个模块好不好用，另有验收覆盖与全局上限两处需要补。搜索本身不必等记忆 V0.3 完成，可以先做适配器与离线验收。

## 1. 先确认的两点（对我上一轮的回应）

1. **容量兜底：接受用户决定，不再提自动裁剪。** 用户已明确选择"超出接口容量就报错、保留未完成轮，不删历史重发"。我撤回 REVIEW5 §2 的建议，也同意你的判断——"连续几个月后几万字符就超限"我确实没有实测支持，不该据此恢复默认预算。
2. **"自相矛盾"这个分类我说错了。** `src/index.ts:77` 的 `.slice(0, 12000)` 是当前 V0.2 源码，两份 V0.3 文档是尚未编码的设计，二者不构成文档与自身矛盾，只是"待实施改动"。采纳你写的实施步骤（移交共享搜索模块、移除固定截断）。同样同意把网页配置从记忆 `ContextLimits` 里撤出、改由 `WebSearchConfig` 承接。

## 2. 需要定清的三处额度语义

### 2.1 "搜索接口失败或无候选也计一次失败"会与 40 次额度互相消耗

设计 §3.2 的规则是：`failures` 包含"搜索接口失败**或无候选**"；开始操作前检查 `successReads < 20 && failures < 40`；§3.1 又说"失败后只要成功次数未达 20 且失败次数未达 40，可以继续尝试"。

问题在"无候选"这一项：**空结果不是故障，是正常返回**。一个阶段若连续几次用不同关键词都没搜到东西（很常见：学校导演查一个不存在的活动），每次都会消耗失败额度，到 40 次后整个 session 停止——而此时成功额度一次都没用过。也就是说 40 次"失败"里混进了两类完全不同的东西：真的取不到材料（故障），和世界本来就没有这个信息（正常）。

建议二选一：

- **A（推荐）**：把"搜索接口报错"与"返回空候选"分开。接口报错计 `failures`；空候选不计，但**同一个 session 内相同或高度相似的查询不重复执行**（按 query 去重），这样既不会无限重试，也不会让正常空结果吃掉故障额度。
- **B**：保留现口径，但把 `maxFailures=40` 的语义明确写成"含空结果"，并在验收里加一条"连续空结果会提前结束该阶段搜索"的用例，让这个后果变成有意设计。

两条都可实现，但**不定的话实现者会按字面写**，而后果是"查不到东西的阶段以后就再也不能查了"，这不太像用户想要的。

### 2.2 `sessionId` 里的"同名调用序号"会与格式修补打架

§3.1 说 session 绑定"故事阶段用 `turnId` ＋ `taskName` ＋ **同名调用序号**"，同段又说"格式修补始终复用同一个 session，不重置计数"。

这两句只有在"序号 = 该轮该任务的第几次 `runModel`"时才自洽；如果实现者把序号理解成 `transport.complete` 的调用次数，那么两次格式修补就会各生成一个新 session，额度被重置（或反过来被算成新任务）。建议直接写成：

> 序号按 `runModel` 调用计；同一 `runModel` 内的首次请求、工具续调用与格式修补共用同一个 sessionId。

这一条与记忆 V0.3 的 `ModelRunOptions`/`ModelClient` 改造是同一处代码，顺手写清成本很低。

### 2.3 恢复后"剩余配额"的消耗方式没有定义

§3.1 要求"持久化已确认的计数、材料和阶段归属，恢复可复用已保存材料及剩余配额"。但没写恢复后怎么算：

- 已保存的 `successReads`／`failures` 继续累加（推荐，防止"重启刷额度"）；
- 已保存的**材料**在恢复后被再次交给模型时，**不再计入成功次数**（否则一次崩溃就会额外消耗额度）；
- 重新发起相同的搜索请求时，命中已保存材料则直接返回，不重新读页。

建议把这三句写进设计，并在验收里加一条"重启后不重置也不重复消耗额度"。

## 3. 需要补的两处

### 3.1 全阶段搜索缺少"单轮总量"这一层

§1 明确"各逻辑模型任务独立计算 20／40，世界和个人分别计数，不共享一池额度"——这是用户的选择，我不反对。但要指出它的量级后果：**当前有 11 个逻辑任务**（原十项 + `memory_consolidation`），若一轮里多个阶段都大量搜索，理论上单轮可达 11 × 20 = 220 次页面读取，每次都带正文回到同一轮的不同模型调用。

§4 说"前台搜索是该阶段主动申请的等待；用户已允许更久等待"，方向可以，但文档没有把这个最坏情形写出来，也没有任何**跨阶段的可选总量上限**（哪怕默认关闭）。建议：

- 在设计里显式写一句量级（例如"最坏情形单轮约 220 次读取，用户已接受按阶段独立计数、无全局熔断"），让这个后果是**被知道的**；
- 提供一个可选配置 `maxTotalReadsPerTurn`（默认 `null`＝不限），在需要控制单轮延迟或费用时可用。

### 3.2 验收项 2 与 6 覆盖不足

- **验收 2** 只举了"18 成功＋3 失败可继续""任一达 20／40 停止"。建议补一条**混合边界**用例：15 成功＋45 失败（失败先到上限）、25 成功＋10 失败（成功先到上限）、以及 19 成功＋39 失败后**最后一次**操作的结果。现有例子都落在"还能继续"的一侧，没有覆盖"谁先到"。
- **验收 6** 现在是"实际上下文错误不触发自动删历史重试"。这只是证明了一个否定行为，**没有测出正常使用中容量错误会不会发生**。既然用户选择了"报错即暂停"，那么"多久发生一次"就是这个设计最重要的未知量。建议加一条实测项：用几个月规模的候选（可离线构造）跑正常轮次，记录注入字符数的分布与触及所选模型容量的比例；若比例明显不为零，就需要回到用户面前重新确认（而不是现在改设计）。

## 4. 小项

1. **表达的搜索边界可以再紧一句。** §4 写表达"可核对知识或措辞，继续只表达已决定的回复意图，不藉搜索增加安排、经历或改变行动"——意图、行动、经历都守住了，但**没有禁止"引入草稿里没有的新事实"**。表达模型拿到网页材料后，完全可能把一个新事实写进最终文字（而它不在草稿里）。建议补半句："不得在最终文字中引入草稿与已提供事实之外的新信息。"
2. **`requestedPages` 默认 1 与 20 次额度需要一句衔接。** 默认每次搜索只读 1 页，却允许 20 次成功读取，实际就是"允许多轮不同关键词的搜索"。建议在 §3.2 明说，免得实现者把默认值调大来"用满额度"。
3. **环境白名单的更新时机。** §5 说"URL 白名单要随本 session 实际读到并提供的材料更新，不能在模型开始搜索前冻结为空集合"。现有 `environmentTask` 的校验要求 `sourceUrls` 全部落在传入白名单内，因此白名单必须在**解析最终 JSON 之前**更新完毕。建议把这句衔接写清（模型返回最终 JSON 前，session 已把本次读到的 URL 注入白名单）。
4. **`webRead` 与"背景压缩只基于快照"的关系。** §4 说后台压缩"在固定业务快照上补充公开知识，网页材料另外保存为本 job 外部依据"。但 `webRead` 是模型按需申请读 URL 的——若它读的是快照里没出现过的 URL，等于绕过了"只基于快照"的边界。建议明确：后台阶段的 `webRead` 也允许，但材料只能作为外部依据登记，不影响 stateVersion 校验与来源门禁（这一条 §6 已有"不能偷偷放宽 sourceIds 门禁"，把 `webRead` 一并写进去即可）。
5. **`WebMaterial` 建议加 `truncated` 或长度字段。** §5 说检索／正文整理会删除导航、脚本，且"不按 12000 字符硬截正文"。既然正文长度不定，来源登记与验收都需要一个"这份材料有多长"的可观测字段，否则验收 6 的"尾部默认保留"无法判定。

---

## 5. 结论

搜索模块值得单独做，`WebSearchSession` 按 `runModel` 隔离、适配器可替换、离线先行验收这三点都同意，也不必等记忆 V0.3 全部完成。**开工前建议先定第 2 节三处（空结果是否计失败、序号口径、恢复后额度如何消耗）**，补第 3 节两处（单轮总量量级与可选上限、验收 2／6 的覆盖），第 4 节五项可随实施处理。

**边界**：本次未运行任何测试、构建或服务，未发起真实搜索或模型请求；第 2.2、2.3 节关于 `runModel`／`ModelClient` 的判断来自对 `src/model/client.ts` 现有实现的静态阅读。
