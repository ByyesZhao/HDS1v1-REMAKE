## 2. 开始标志前的控制：采用 A，明确普通内容与命令不同

细化 §3 已规定未确认的冻结 start 不能提前作为活动入口，§4.1 已规定活动外命令 cancelled。因此当前设计实际上已经选择 A，只是 §3 第3项“输入按普通15秒路由”容易被读成控制文字也入 messages。

建议替换为：

> 开始标志尚未确认时，普通内容仍按15秒接收；全文精确的推进命令仍按活动外控制处理，保存 cancelled 记录并返回“当前没有共同活动”，不写 messages，也不在准备轮段 B 转成交给首节点的请求。开始标志确认后收到的推进才绑定活动。

“被邀请／同意开始”与“开始标志已经确认”不是同一程序边界。保持这个边界，无需从未公开的 start 候选绑定控制，更不需要在候选取消或重生成时迁移请求。补任务2测试 `advance_before_start_confirmation_is_inactive`，与任务5的已确认标志过渡测试配对即可。

## 3. 环境更新仍有自己的截止，不被共同等待排除

DSH 1.2 把细化 §5.2 的“排除被抑制截止”扩大到了环境。这段实际只列出三类：被抑制的自主截止、共同中的旧 sleepAt/wakeAt、等待共同节点的复议任务；没有排除 nextWorldAt/nextSchoolAt。

细化同节第2项明确“无可运行前台时，到期世界／学校更新”，方案 §5.2 也明确可利用60秒窗口运行环境工作。当前 `src/host/scheduler.ts` 的 nextDeadline 末尾本就纳入 nextWorldAt/nextSchoolAt；待实施变更是 collectReady 的选择排序，不是删除环境计时器。

例如本轮最后输出22:31:30确认，共同下一步22:32:30，世界更新22:31:40到期：

1. 无手动推进／到期预约时，定时器选22:31:40。
2. 到时共同节点尚未可运行，选择 world。
3. 环境轮不改变共同轮号、sharedClock、nextStepAt、自主截止或 narratedUntil。
4. 环境调用已开始后若手动推进到达，仍按现有串行门禁等它完成，再选择前台；不额外引入中断或并行环境执行器。

建议在细化 §5.2 明写：

> 环境截止持续参与 nextDeadline。共同等待不等于环境等待；每次串行空闲判定，无可运行前台就可处理到期环境。若连续存在手动／预约等可运行前台，环境让位到首次出现可用空档；不把“活动结束”设为环境唯一入口。

不承诺“最多推迟20×60秒”。20限制成功共同故事轮数，不限制模型、搜索、发送、后处理的墙钟耗时；暂停／失败更不能保证这个时长。活动结束后若仍有可运行普通前台，前台优先规则也继续生效。可以说明可能延迟，不为此增加环境强插配额。

任务3单列 `environment_deadline_remains_in_shared_wait`：当前时刻22:31:35，nextDeadline应为22:31:40；在该时刻 collectReady 得 environmentKind=world，不带共同选轮元数据。任务5补 `environment_commit_preserves_shared_clock`，检查环境提交前后计数、锚点、共同截止、自主截止与 narratedUntil 均相同。

## 4. 代写防止设定漂移，但不加一两个动作的硬限制

自我放大的问题值得约束，而且方案 §3.5 已有“不仅凭连续代写就认定用户现实习惯改变”，此前接受的回应也明确不形成用户新长期意愿。这些内容在细化提示词中还可以更直接。

建议补充：

> 代写只延续已确认活动，不能把本轮表现或此前代写归纳成用户新增的稳定性格、能力、偏好或关系设定。沿用用户真实提供的背景和已知习惯；可描述本次活动的具体行动与客观结果，不据此声称用户“一向擅长／总是喜欢／已经形成新关系”。

例如 `【你在这次操作中避开攻击，抵达补给点。】` 在授权内；仅据此新增“你一直是技术高手、喜欢冒险”这样的稳定设定不成立。虚拟角色可以对本次公开表现形成自己的感受，不等于改写用户固定属性。

不采用“一轮最多一两个动作”。它不是用户提出的节奏要求，也不能证明设定不漂移：一个动作仍能夹带能力或偏好判断。每轮合理进展已经受实际时间、已公开事实、活动范围和20轮收尾约束，无需新增动作数量配额。

也不采用一概“不得替用户完成关键抉择”。用户已明确允许活动内行动选择及结果，此前回应 §8 已限定不能把“重大选择”解释成撤销全部行动代写。继续禁止用户台词／心理、活动外承诺及重大关系决定；活动内路线、游戏操作等选择仍可公开代写。合理提前完成及final收尾也保留，不能禁止把已经具备条件的结果推进到结束。

任务4提示词测试加入稳定设定边界断言，不加动作计数校验或语义审核模型。仍需真实多轮故事验收，提示词存在不代表已经实测无漂移。

## 5. outline：收束阶段只减不增，开展阶段仍可建立线索

DSH 的小标题指向收束阶段，但建议写成“非final轮只允许减少或保留”，字面上覆盖第2～16轮，过于宽泛。首轮建立的走向不是要求把之后可能出现的全部线索预先穷举；正常开展仍需要合理更新。

建议采用以下明确范围：

- 首节点 outline=null 时建立走向，包括 maxSteps 较小、首节点已处于 wrap_up/final 的情况，不对它做“旧集合包含”判断。
- opening/ongoing：保留与已确认活动一致的目标，允许必要的新线索；不得每轮换成另一场活动。
- 已有 outline 的 wrap_up：openThreads只允许保留或删除旧条目，不新增；保留项沿用原文本，进展写到progress/publicNarration。可以对字符串集合做包含校验，避免额外引入线索ID系统。
- final：仍返回现有必填outline，openThreads为空，不新增走向项；goal/endingCondition保留为本次活动说明。尚未解决、准备以后继续的内容在公开收尾和个人导演的后续意图中说明，不把清空列表谎称成任务已经完成。
- goal/endingCondition建立后原则上沿用。确需因真实新输入或明确场景变化调整时有叙事依据，不能只凭静默代写不断改变目标；这项语义要求留在提示词，不用字符串相等冒充含义审核。

这是对既有“收束阶段减少新支线”做有限加强，活动目标提前完成仍允许end，晚到的用户新要求可以协调留到之后，不绕过20轮上限。

若采纳程序包含校验，任务4给 narrativeTask 和 runNarrative 增加末尾可选 `previousOutline?: SharedOutline | null` 参数；app从本轮正式状态传入原outline，普通调用不传。既有 sharedMeta 参数顺序不改，个人合同无需为了该校验新增参数。

任务4补：开展阶段可以增加必要条目；wrap_up保留／删除通过、新增拒绝；final非空openThreads拒绝；首节点旧outline=null可建立，maxSteps=1的首节点final返回空列表。格式错误仍使用既有两次修补，不另开故事轮。
