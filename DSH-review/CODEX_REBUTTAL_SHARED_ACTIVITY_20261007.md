## 2. 静默窗口与节点消费的具体口径

### 2.1 60 秒从最后一项可见输出算，是明确选择

用户已选“双方最近消息后 60 秒”，方案 §3.2 已明确旁白、角色文字／动作和表情都属于本轮输出，并取最后一个确认时间；不是只取最后一段 text，也不是从模型起调时刻开始。

仍采用 `max(最近用户输入, 最近可见输出确认, 最近无输出轮完成) + 60 秒`。当用户输入比角色最后输出更晚时，应从用户这条输入开始重新等，不宜把 DSH 建议的简句解释成“永远只从角色输出算”。

DSH 对等待观感的提醒可以作为例子；“4～5 段就要 25～40 秒”不是固定保证：`src/output/qq.ts:17～21` 仅对已有前一段发言的后续 text/action 加延迟，旁白和表情不采用同样延迟。生成、网络和分段数量也不固定，不能以“20～40 分钟”作为活动完成时间承诺。共同活动限制是 20 个成功提交的轮次。

### 2.2 消费手动请求并替代旧自动节点

共同模式的手动、自动及预约协调统一通过一次“选择共同回合”入口。选择时固定活动 ID、本轮输入与控制请求 ID，并把该轮覆盖的当前自动节点关联到冻结回合：它在旧轮执行或恢复期间不能另行启动。

有输出时按最后确认项更新锚点；无输出时按完成时间更新。段 B 成功提交后，按最新 Runtime 计算／维护唯一下一节点，旧窗口已被替代。失败时仍续办同一冻结回合，不把旧节点变成第二个待办。

不得笼统删除活动的全部待办。回合选择之后收到的新输入会影响最新锚点，新推进指令保留给下一轮；本轮只消费已选的控制请求。活动已结束则取消该活动残余节点和指令，普通未处理消息继续交给普通模式。

后续实施需把 `Scene.shared.nextStepAt → 唯一 scene_step` 的创建／更新集中到一处，输入、输出确认及正式提交只能经这个规则维护节点，不保留模型直接创建节点的路径。

## 3. 推进命令不进入普通消息表

控制身份在收到时就能判断：绑定目标私聊、全文为 `【推进】`、关联当时已正式开始的活动。不需要等到调度器空闲才判断“这是不是命令”；等待的是命令执行及消费。

规定控制记录不写入 `messages`，也不参加普通合批、未读集合、近期原文、检索查询或记忆来源。活动外命令是系统控制提示，不应通过角色对话流水线产生。

运行状态持久化待执行请求，独立控制审计可采用简单 `control_requests` 记录，保存 ID、活动 ID、接收时间、平台消息 ID 及 pending/consumed/cancelled 状态，具体类型和存储实现留给实施细化固定。这样不需要给所有 messages 查询新增过滤条件。

已选请求随 TurnRecord 固定，最终消费与段 B 同事务；活动结束取消剩余请求，不留“未读控制消息”。方案原来的“可单独审计”应在细化中改成明确分流，而不是可选做法。

## 4. 无对话时允许活动继续演完：用户已经决定

用户本轮补充：

> 在双方都没有输出对话的情况下，允许共同活动期间“无人回应就必然把整场活动演完”，并且允许主叙事编造我的行为，但是都要用【】输出出来

按这条决定，采用 DSH 的 A：没有用户新消息、角色也没有新台词时，仍可以每 60 秒公开推进，完成活动并最晚在第 20 轮收尾；不引入固定 3 轮或其他 N 轮无输入强制提前结束。角色仍允许沉默，也仍允许活动完成后提前自然结束。

用户后续授权覆盖此前“不替用户编造行为／关键动作”的限制：双方无新对话的推进段，主叙事可生成用户在本次活动里的动作、行动选择和相应结果，不需要等用户逐步确认。必须把这些行为写入 `publicNarration`，由既有旁白 outbox 统一包装成 `【…】`；不能只写内部 experiences／progress，也不当作真实 incoming 用户消息或角色台词。

待处理的真实发言和动作仍优先，生成后新到达的输入按串行规则下一轮处理。授权判断以选取时已发生对话为依据，不预测稍后个人导演是否说话；个人导演仍决定虚拟角色自身的自愿反应。代写用户行为不包括新增用户台词或心理，不据此修改用户现实背景。

因此 DSH 提出的产品取舍现已确定，并且用户允许的范围比原方案更宽。方案 §3.5、§4.2、§6.3 和验收项已经同步，不再保留与该授权冲突的“所有共同回合一律不能代写用户行为”表述。当前代码的合同／提示词仍是旧实现，后续实施需同步新增静默授权及公开输出要求。

## 5. 睡眠采用 A，但需要固定进入条件及完整调用链

当前 `src/host/state.ts:6～8` 的 `isSleeping` 只有时间区间，没有独立“实际睡着”字段。DSH 对 `app.ts` 睡眠早退的提醒成立；只改提示词或 Scheduler 不足以修复。

推荐采用 A，不新增实际睡眠标记，固定以下状态约束：

1. 从普通模式确认进入共同活动之前，角色必须通过普通睡眠／可参与判定；不能拿一个 start 候选或推进指令把原本已睡着的角色唤醒。
2. 已成功确认进入并具有合法活动身份的共同模式，代表角色仍在清醒参与；保存的 `sleepAt` 是可协调计划，不因时钟跨过它直接阻断共同轮。
3. 角色想睡觉或确实不再参与时，先在共同结束轮自然收尾，再提交普通模式与调整后的睡眠安排；不保留“活动还在进行，同时实际睡着”的混合状态。
4. 结束提交后，对新的普通模式状态按完成时刻统一判定睡眠，再决定自主截止为 null 还是 `completedAt + interval`。结束后的旧活动 ID 不能继续豁免睡眠。

统一判定需要覆盖：Scheduler 的收集与截止候选、`canRead`、`generateTurn` 的睡眠早退和 waking 分支、段 B 的自主时间处理，以及恢复时的同一路径。尤其不能只让睡眠早退失效，却在计划 `wakeAt` 到期时把仍在活动的角色误判成刚起床并重排一夜作息。

这是一项共同活动状态约束和共享判定规则，不是增加一个独立的共同活动自主延期机制；自主重排仍全部遵守方案 §7。

DSH 所称“A 天然避开实际已睡着”的说法略过了前提：直接用 `mode !== chat` 豁免任何旧状态并不可靠。对合法新活动，上述进入／退出约束足够；对已有旧活动或不一致状态，需要先做下一节的升级检查，不能默认绕过睡眠。
