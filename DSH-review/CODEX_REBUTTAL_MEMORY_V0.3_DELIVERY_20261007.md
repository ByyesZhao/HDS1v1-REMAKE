## 1. 总体结论

DSH 对核心生命周期、事务恢复、来源门禁和维护让位的肯定基本合理；部分问题也确实需要修正。但报告混入了几处源码误读，不能把所有条目当成已确认缺陷。

建议优先处理真实规则偏差：归档不应提前暴露预备长期、合并应保留事件时间范围、记录中不应混入模型操作字段。维护应用异常退避和搜索 URL 边界处理也是有价值的小改进，但不应据此引入大量极端情况防御机制。

不需要重新裁定预备长期是否提前可见：记忆细化 §3 已明确“在 retainedFrom 前不提供”。执行计划的 current 验收范围不是允许 archive 绕过该规则的例外。

## 3. 记忆检索与来源问题

### 3.1 §2.1：部分接受，限定影响范围

`src/memory/retrieval.ts:73` 只按条目的 id 保护，而调用方传 visibleSourceIds。对于记忆／细节候选，确实缺少 sourceIds 交集判断。

但“永远不相等”不准确：recent 数组包含消息本身，其 id 就是消息 ID。当前输入、核心背景和状态也在模型业务输入中独立提供，不会被这个历史预算函数删除。默认预算 null，因此当前默认部署不走裁剪。

后续可把保护条件改为“条目 id 命中，或 sourceIds 与受保护来源相交”，补可选预算验收；不重新启用任何人为预算。

### 3.2 §2.2：不接受“结构化补查死锁”，接受触发规则覆盖偏窄

`makeRetrievalRequest` 从该阶段可见话题建立 base.permissions；`lookup` 检查这个已建立的权限，而不是检查结构化请求 query 是否含触发词。上面的离线复现已直接否定“查询必须恰好含正则词”的结论。

当前程序判断使用正则，确实可能漏掉“我们暑假一起去了哪里”等其他追忆表达。这是召回入口覆盖有限，不是结构化 scope 字段不可达。可以以后补常见追忆／历史事实表达和可见性回归。

不建议按报告的“查询词必须出现在可见文本中”直接开放 archive：词面重合不能证明追忆意图，还会拒绝正常改写。保持“程序依据本阶段可见信息建立权限”的既定规则即可，不需要用户重选权限政策。

### 3.3 §2.3：不接受重复计数解释，另确认可选限制下漏计

`ranked` 仅含 direct 与融合结果；always 在前面的候选循环被排除，最后另加入 learned。默认不限时 `ranked.length + always.length - selected` 没有重复计算 always。

`hdsi.status` 展示的是 MemoryIndex.stats，不展示这里的 excludedByLimits。报告关于状态输出的说法也不成立。

真实的小问题是 `stable=always.sort(...)` 共用数组，显式字符限制中的 pop 同时缩短 always，导致被删除的常驻项未计入 excludedByLimits。可保存裁剪前数量修正指标。不要直接用 candidates-selected 替代：那会把因不相关而排除的候选也误算成被预算排除。

### 3.4 §7.2：接受，应按既有细化修正

`src/memory/store.ts:62-65` 的 archive 条件同时绕过 expiresAt 与 retainedFrom，已复现提前返回。

正确规则是：archive 可找回已经生效而后到期的长期；**任何范围均不提前提供尚未生效的预备长期**。普通事件前七天仍可通过详细短期召回，重要事件本来就立即生效。修正不削减用户信息，也不需要新业务裁定。

建议验收覆盖创建后一天、恰好七天生效、到期归档追问及 high 立即生效；同时覆盖默认 build 和结构化 lookup，避免只测 current。

### 3.5 §7.3：不能仅凭同 canonicalMemoryId 自动删除稳定认识

两条 learned 行指向同一主事件，不代表两条认识语义相同。例如同一组经历可以支持不同的稳定结论。stable_understanding 还具有多事件来源，不能套用“单事件常驻经历只留一份”的投影规则。

当前合并确实可能保留相同结论的重复项，可以记录这一限制，后续由维护识别重复认识；不能仅按 canonicalMemoryId 去重而丢掉不同结论。DSH 的观察可以接受，“同一认识必然重复”的推断需要更多证据。

### 3.6 §7.4：区分真实缺口与低优先级观察

| 条目 | 判断及建议 |
| --- | --- |
| 合并仅保留最早 happenedAt，未合并 lastEventUpdateAt | 接受。细化 §4.3 要求保留事件时间范围，而当前类型也没有明确结束时刻字段。后续应固定起止表示并保留更新时刻；更新时刻不能直接冒充事件结束时刻 |
| DTO 控制字段混入 owner | 接受。create／update 的展开会保存 action、clientRef 等，并随检索再次提供。后续显式选择持久化字段，查询投影也不应回传旧操作意图 |
| promote 不立刻归零 windowAwakenings | 接受小偏差。当前 durable 后续 refresh 会归零，不影响 expiresAt=null，但转换时应直接归零使状态一致 |
| revision 额外增长 | 部分接受。部分改动会增加不必要重建，但本次没有发现漏索引；统一依据实际索引文本变化判断更准确 |
| 同日再次唤醒也增长 stateVersion | 不能一概当成空操作：同日可能补充新来源或修正最早时刻，维护 readSet 应看到这些变化。只有完全没有变化时才适合优化 |
| 空 refine、未使用字段／测试辅助查询、unconfigured 待办 | 可维护性或重复工作观察，低优先级，不需要为本次审核扩展大规模重构 |
| durable 的预窗口守卫 | 报告自己也承认当前正常生命周期不可达；不是当前业务缺陷，不列为实施前置 |

## 4. 维护调度问题

### 4.1 §5.1：接受失败后即时重试风险，不接受事务内吞错修法

当前 applyOneReady 失败会回滚事务，ready 留存，nextDeadline 返回 now；持续失败时可能反复立即唤醒。人工注入应用持久化异常已复现这一条件。正常合同和版本检查已经挡住报告举的多数业务状态错误，因此不能表述成正常路径必现。

建议做小范围失败退避以保护聊天响应；但**不能在 applyUnit 内捕获异常后继续提交同一事务并标 stale**。如果异常前已经改了部分正文／计数／投影，这种修法会提交部分应用结果。

正确边界：整个单元事务先回滚；事务外记录 lastError 与延后重试。调度必须让 startOne、applyOneReady、nextDeadline 对这个等待状态理解一致，避免另一处仍把它当 now。失败不等于版本冲突，不冒充 stale，也不静默丢弃该单元。可沿用后台五分钟重试的现有约定，无需增加用户决策。

### 4.2 §5.2：当前单宿主语义下没有第二个旧轮恢复缺口

恢复后 pump 本来就 continue 并重新检查 unfinishedTurn。系统串行运行，旧轮完成后才创建新轮；新轮若失败，既有异常路径暂停并保留该轮，resume 重新开启恢复。

报告没有给出在这些约束成立时又出现第二个未完成轮的可达路径。单纯 wake 也不会重置 recover，所以“下一次 wake 会恢复”的描述不准确。无需扩大自动恢复循环或改变暂停语义。

### 4.3 §5.4：两处误读，一处需限定测试证据

- 总模型配置确实是 modelRoles 十项加独立 stickerDescriptionModel 一项。文档“总数十一项”本身正确，并没有声称数组长十一；可以补括号提高可读性。
- 当前细化 §7.2 第 2 步已经是 paused/stopped，第 3 步才是旧故事，与代码一致，不需要二选一。
- 在途后台不造成 0ms 唤醒的测试有实际断言，不是空断言。它没有覆盖应用异常路径，这一点接受；后续异常退避修正须另补回归，不能把专项断言推成覆盖所有可能错误。

### 4.4 §5.5：不接受三个源码误读

- requested 由 wake 的 active.then 分支读取，用于最后一次扫描与收尾之间到达的唤醒，不是死字段。维护每提交一个单元后 setImmediate 并从循环顶端重查输入，细化要求的让位粒度已经落地，现有实际 I/O 测试通过。
- this.active 是已经串上 catch().finally() 的 Promise；wake 在这个 Promise 上注册 then，执行时 finalizer 已经完成。报告所说 then 先于置空 finally 的顺序不成立。
- work() 查询明确限制 pending/computing/ready，过滤在 SQL 中执行，不把 done 全部加载后排序。长期任务保留策略可以另议，但报告的全表加载理由不成立。

24.8 天上限是 Node 定时器最大支持范围，分段重新安排合理；不能取消而把超长延迟交给 Node。撤回的旧签名空转判断无需进一步修改。

## 5. 搜索与模型工具问题

### 5.1 §6.1：接受；配置入口也不能撤回

候选 URL 归一化在搜索错误捕获范围外，非法结果会打断阶段且未登记失败，已复现。真实适配器应产出规范 HTTP(S) URL；共享服务也应在候选接收边界处理非法结果，保留合法候选并按约定确认失败，避免恢复反复处理同一个坏结果。

DSH 对 z.url() 的更正反而不正确：当前安装实现默认只检查 URL 可解析；只有明确指定 protocol 才应用协议限制。ftp 和 file 均实际通过，而 settings.webSources 使用的正是默认 z.url()。因此配置来源也需要与 HTTP(S) 阅读合同一致的校验。

接入真实 provider 前值得处理这两个入口；不等于 provider 一接入必然出错。

### 5.2 §6.2：不接受“合法工具请求消耗修补”，需澄清非法分支

合法且当时可用的 webSearch／webRead 经单独分支执行，不进入格式修补；现有工具循环测试也验证这一点。

会进入修补的是参数不合法，或工具 schema 已撤下后模型仍输出该工具。执行计划任务 3 明确写的是“合法工具请求不消费修补次数”；设计文档没有加“合法”二字，值得对齐措辞。

当前允许两次修补机会；在没有先前错误时，连续第三个违规响应才抛 ModelFormatError。DSH 所说“两次不合作即暂停”不准确。

不建议直接采用“所有非法／已超限工具请求都不占修补，只回反馈”的改法：额度耗尽后，这会使持续违规的模型无限续调用；把这些请求算成网页失败又可能让失败计数超过 40。保留已有有限修补规则，不新增第三套调用预算；修补错误提示可以继续明确要求输出业务 JSON。前台格式错误暂停仍沿用原项目语义。

### 5.3 §6.3：接受需要明确措辞，不接受与重放规则冲突

应区分三件事：

1. 同一已完成 operationId 重放：不请求 provider、不增加成功或失败。
2. 直接读取本 session 已持有 URL：返回旧材料、不增加计数。
3. 发起新的搜索 operation：可继续取得未读候选；若没有任何新材料，也没有已计页面失败，记一次未取得资料的失败。

第 3 项不是第 1 项的重放，现有测试已经明确。保留当前计数更符合“失败指没有取得可用资料的尝试”，也使重复无效搜索有明确终止。建议文档写明 no_candidates 在此包含“无未读候选”，或以后区分原因名称；不把它误称网络失败，不新增成功扣额。

### 5.4 §3：配置来源实际优先，审查前半句错误；改顺序属于可选政策

代码把 initialSources 排在搜索结果前，requestedPages=1 也会先读配置来源，已复现。报告前半句“单页不会读取配置来源”与源码及其后半句矛盾。

当前规范允许来源 URL 优先为候选，故现行为不直接违反规范。不过无关配置来源可能占掉此次搜索所需的一页，值得优化。

如果调整，我建议**搜索结果优先；没有足够可用的新结果时再尝试配置来源兜底**。这是本轮唯一值得向用户确认的可选行为变化，不是修复归档／事务问题的前置条件。若不调整，应在文档明确配置来源排序。

### 5.5 §6.4～6.6：接受记录边界，避免扩张范围

| 条目 | 判断 |
| --- | --- |
| 子结果与完成标记分事务 | 属实。已确认材料／计数／步骤同事务，最后完成标记另事务；重开可按确认步骤恢复。后续文档应准确描述这一边界，不把已验收的逐页恢复改成整操作最后一次提交 |
| 新操作未缓存搜索候选列表 | “可复用”是许可而非必须；不违反规则。公共正文仍复用，查询不进入公共缓存 |
| repair 提示一直保留 | 属实，可在后续成功接受合法工具等响应后清理旧修补提示，但不能重置累计 repairCount 或丢失尚未处理的反馈；低优先级 |
| 本轮 selfReadSources 未限 runId | 当前同轮只有一个 personal 阶段槽位，且登记限 personal_life。恢复／重生成复用它，按 turnId 汇集有依据。没有证明混入其他阶段；不应随意丢掉本轮已实际提供的阅读来源 |
