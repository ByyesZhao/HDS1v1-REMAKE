# 记忆容量与空闲整理 V0.4：对 DSH 第十五轮的回复及容量补充

日期：2026-10-08。状态：方案审核回复，未实施。

审核对象：[DSH REVIEW15](DSH_REVIEW15_MEMORY_CAPACITY_IDLE_V0.4_20261008.md)、[原方案](../docs/MEMORY_CAPACITY_IDLE_V0.4_PROPOSAL_20261008.md)。现状核对依据：本地源码，当前记忆实现仍沿用 V0.3。本轮不修改代码、配置或正式库，不启动服务或调用模型。

结论：DSH 关于完善实施口径的建议大部分成立；短期唤醒排序、夜间批次推算和后台让位关系需要修正。可以继续细化，但不能直接按其全部建议编码。本次同时纳入用户最新要求：**普通长期活跃目标从3000改为1000；归档也应有限，超量清理旧弱记忆。** 原方案中的3000及“所有退出原文一直留库”不再作为后续实施依据。

## 1. 逐项处理结论

| DSH 条目 | 处理 | 后续文档要固定的规则 |
| --- | --- | --- |
| 1.1 短期自身／关联长期唤醒数 | 不采用“短期自身计数”；补充原因 | 当前真实唤醒只记录在canonical长期；短期使用关联计数，不因此延长7天 |
| 1.2 提前转层的grant方向 | 采纳明确示例 | day 3容量退出，未生效预备长期day 3立即可见，初始期限从day 3计算 |
| 1.3 总量与可见量 | 采纳统计澄清，纠正标题 | 1000包含预备项；可见普通长期是其子集，不另设一个1000可见配额 |
| 1.4 睡眠与连续批处理 | 采纳用途说明，修正调用量与调度推论 | 15分钟是资格门槛，不是固定调用周期；新后台准备／应用仍让位于环境前台 |
| 1.5 完整排序 | 采纳 | 写出完整比较键，不能只给衰减公式 |
| 1.6 锚点写入点 | 采纳，补充现有提交边界 | 环境步骤不刷新；普通活动已有段B状态提交边界，需要新增持久化识别数据 |
| 2.1 短期refine合同 | 采纳对象区分，不认定简要摘要路径缺失 | 现有refine改关联长期摘要；短期详细正文不是该合同的修改目标 |
| 2.2 索引优先顺序 | 采纳明确调度，采用合格任务FIFO | 索引不等15分钟；两类都合格时沿用创建时刻／ID顺序，避免深度任务饥饿 |
| 2.3 保护占用 | 采纳观测说明，纠正容量解释 | 保护对象已包含在1000中，不能再扣一次；仍可检索的受保护长期不是损失的容量 |

## 2. 三处需要纠正的判断

### 2.1 短期自身的唤醒字段当前不能承担排序

[MemoryStore.makeOwner](../src/memory/store.ts)为各类owner初始化`totalAwakenings=0`，但[MemoryLifecycle.awaken／refresh](../src/memory/lifecycle.ts)只接受canonical长期身份，并把真实有效日期数写到长期主记录。当前没有给短期自身累计唤醒日期的业务路径。

因此直接改为“短期自身`totalAwakenings`”会使现有短期几乎全按0排序，失去用户希望的“反复提及优先保留”作用。若要使自身计数有效，必须新增另一套短期唤醒认定；本方案没有这种必要。

保留原选择：短期按关联canonical长期的累计有效日期数排序，用来表示这个事件是否被反复提及。长期保护则是另一层候选排除规则，不能混同。

这不会造成短期无限占位：即使长期很热，短期仍在最后一次真实新进展后7天退出；只重谈、长期续期、检索命中都不延长短期。长期很热而新一阶段详情并不热，确实可能让该阶段详情在剩余7天内较少被容量提前挤出，这是有意的保守选择。全部短期仍受100条目标和自然到期约束。

### 2.2 预备项会减少可见数，不会使可见普通长期超过上限

DSH §1.3标题写“可见层可能远超3000”，正文公式却说明它少于总量。正确关系按新目标写为：

```text
普通长期占用 = 尚未可见的预备长期 + 当前可见普通长期
正常归一后普通长期占用 <= 1000
当前可见普通长期 <= 普通长期占用
```

自然到期、容量归档、merged／discarded不属于这个普通活跃池；durable属于独立常驻层。检索还可以包含details、短期、learned等，不能拿全部检索记录总数检查“普通长期1000”。

不增加独立的“可见长期目标”。保留占用、预备、可见、归档四个统计口径即可。普通池已满时预备项会占一部分位置；受保护的长期如果已经可见，本来就是可见容量的一部分，不能再从1000中减掉。

### 2.3 空闲15分钟不是“每15分钟调用一次”

首次满足资格后，只要没有新的有效交互／故事完成、没有受保护活动或可执行前台轮，就可以逐批继续处理尚未完成的增量。维护完成不刷新空闲锚点；没待办时不调用模型。

因此无法用“睡8小时÷15分钟≈30批”估算调用量。实际调用量取决于未处理版本、每批候选量、调用耗时、冲突和重试。睡眠可作为集中处理的机会，但不需要安排一个整夜定期调用任务，也不承诺一定整理完。

世界／学校链和后台准备使用不同执行槽，已经在途的后台请求可以与06:00环境链并行；但[Host.pump](../src/host/runtime.ts)先处理到期前台，随后才申请新后台准备或应用单元。不能把“不同槽”写成“无需让位／完全没有资源竞争”。费用和批次数记录实际运行数据，不用静态推算代替验收。

## 3. 同意补入实施细化的精确口径

### 3.1 排序和提前转层

活跃层容量退出按以下顺序，排在前面的先退出：

```text
先排除本层受保护身份
再比较：
  importanceRank(normal=0, high=1) 升序
  effectiveAwakeningDates 升序
  decayRatio 降序
  lastMeaningfulAt 升序
  happenedAt 升序
  createdAt 升序
  id 升序

短期effectiveAwakeningDates来自关联canonical长期
长期effectiveAwakeningDates来自自身canonical
lastMeaningfulAt使用真实事件更新／有效唤醒时刻
不使用后台处理、索引或归档时刻给旧事保鲜
```

衰减沿用原方案的7／90天计算式。短期缺少有效关联计数时按0处理；正式迁移应报告缺失关联，不能凭空补唤醒。

短期day 3提前退出、原截止day 7：如果关联普通长期尚未生效，将`retainedFrom`和初始grant锚点改为day 3，`expiresAt=day 3+90天`。这与“短期出现新进展、预备可见时点随7天窗口后移”是两个业务操作，不能复用后移分支。已经生效的长期、真实续期和durable不因转层重置期限。

“空闲后改进简要摘要”指关联长期的`eventSummary／feelingSummary`等；[现有refine](../src/memory/maintenance.ts)能够处理这个目标。它不改短期详细正文。真正合并短期详细记录仍须新增正式合同，不能仅在提示词里允许。

### 3.2 空闲状态的提交入口

实施细化应固定持久化空闲状态及以下写入点，不借用环境步骤或维护job的`completedAt`：

| 事件 | 正式写入点 | 是否刷新 |
| --- | --- | --- |
| 新用户消息／【推进】 | [InputCollector.acceptInput](../src/host/input.ts)接纳新输入的事务 | 是；重复投递不产生新时间 |
| 一条输出确认发送成功 | [sendFrozen](../src/recovery.ts)提交confirmedAt与实际消息记录 | 是；未发送草稿或失败尝试不算 |
| 非环境故事正式完成 | [finishPostprocessing](../src/recovery.ts)段B写入done／completedAt | 是；包括没有输出的正式生活故事 |
| 共同活动开始／实际结束 | 活动正式状态／结束提交，与最终轮完成统一取最晚时刻 | 是；未正式结束持续关闭深度资格 |
| 普通明确活动开始／实际结束 | 段B比较已提交character活动状态与nextState，并持久化相应锚点 | 是；expectedEndAt仅用于重新检查 |
| 学校提醒／其他事件实际被角色获知 | 正式生活故事／经历提交 | 是；不直接用客观通知计划生成时间 |
| 环境步骤完成、索引／维护完成 | 各自现有步骤／job提交 | 否 |

普通`scene.activity`已有段B提交边界，缺的是用于空闲判断的持久化识别信息，不能说当前完全没有提交点。具体字段和活动连续／切换判断在实施细化固定；不把描述措辞变化误判为一场活动结束。

睡眠后台例外仍为建议：睡眠不阻挡维护，但其他资格照常检查；不生成睡眠经历、不推进生活时钟。新的输入、输出和实际事件即时刷新计时；准备、重试与ready应用都重新检查。

### 3.3 索引与深度整理的公平调度

保留[现有work排序](../src/memory/maintenance.ts)的`createdAt → jobId`，但先按任务类型、retry和空闲／活动门禁过滤合格任务：

- 未满15分钟时，索引可以合格，深度任务不能合格。
- 两类均合格时，按上述顺序处理，不能让持续新增的索引永远挡住旧深度任务。
- 有合格ready单元时先逐单元应用并让步，再考虑准备。
- **未满足深度门禁的ready结果不能阻挡合格索引**；当前startOne的全局ready检查需要随新门禁改为检查合格ready，而非原样保留。
- 每次只准备一个后台请求；每个提交单元后重扫前台。前台到期优先，已有后台请求无需因新消息取消。

默认归一后，100条活跃短期至多关联100个不同长期身份；这些身份已计入1000。本次转层／恢复的临时保护另计，只持续当前容量处理；旧库尚未归一时不能直接套这个数量推论。保护不是给长期池增加一个额外的100条配额。

## 4. 用户最新要求：100／1000／500与最终清理

### 4.1 选择和适用范围

仅把普通长期从3000降为1000，仍永久保留全部旧正文，不能解决用户新提出的累积问题。三种做法中，建议采用第二种：

| 做法 | 结果 |
| --- | --- |
| 活跃退出立即永久删除 | 规模最简单，但失去近期明确回忆与恢复机会 |
| 活跃1000＋有限归档500，再按时间／保留优先级清理 | 保留有限的找回机会，同时旧弱记忆最终退出；推荐 |
| 无限归档，仅限制日常检索 | 仍持续增加记忆数据，不符合用户最新要求 |

本次建议的完整口径：

| 层 | 目标与期限 | 超量／到期后的处理 |
| --- | --- | --- |
| 活跃短期详情 | 100条，真实新进展后7天 | 压力下先接上关联长期摘要；原7天到期后清理短期记忆详情 |
| 普通长期活跃池 | **1000条**，包含预备项；原90天／3个有效日期续期机制 | 低保留优先级项退出到有限归档；自然到期也归入同一归档池 |
| 普通长期归档池 | **建议500个canonical主身份** | 超出时删除最弱候选，不再建立第二层无限归档 |
| 常驻、details、作者背景 | 不参加上述普通经历容量 | 仍按证据／冲突审核，不因为容量直接删除 |

1000是用户明确的新目标。500按用户给出的值作为建议初始归档上限。以下归档时限、短期详情清理及清理排序是本次补充方案，待审核后折入实施细化；不是当前程序已经具有的行为。

### 4.2 自然到期也计归档，归档也有时间出口

归档池包含自然90天到期和容量提前退出的普通长期，按canonical去重；不能只数新加容量标记的条目，却让日期过期记录另堆一份无限历史。查询和数量统计依据同一归档判定。

建议增加**归档最长保留90天**，从本次实际进入归档的时刻计算。自然到期的进入时刻取实际`expiresAt`；容量提前退出则取容量退出时刻。旧库启用晚、进程离线久，不能用维护执行时刻给本已很旧的记忆再加90天。容量退出后又自然到期，也不能把归档起点后移。

这样，一条没有足够有效唤醒续期的普通记忆，在正常7天转层／90天保留结束后，最多再有90天归档机会；旧弱内容即使没有凑满500条，也会最终清理。若期间真实重谈并正式重新激活，则沿用原身份进入活跃池；以后再次真实退出时才产生新归档窗口。单纯查档、维护重写、索引重建不重置窗口。

不增加“少于几次就提前删除所有活跃记忆”的额外阈值：低唤醒已体现在原续期门槛和容量排序中；新增重要经历仍有合理保留期。未晋升常驻的记录，历史唤醒较多也不获得永久归档豁免。

### 4.3 归档满501条，谁被清理

先清理已经超过归档90天期限的合格条目；仍超500时，再按以下顺序删除：

```text
排除正在服务活跃短期、常驻投影或未完成正式故事的必要身份
累计有效唤醒日期数升序
lastMeaningfulAt升序（更久没有真实新进展／有效唤醒者先删）
importanceRank(normal=0, high=1)升序
happenedAt升序 → createdAt升序 → id升序
```

归档清理把“唤醒少、时间旧”放在前面，区别于活跃池先保护high的重要度排序。相同唤醒数优先删除更旧事件，不能因为刚刚才被归档而把旧事排成新事。清理期限已到时，高重要度也不能自动获得无限保留；常驻证据及仍被正式引用的身份按保护规则另行处理。

这是程序规则，不需要模型判断“是不是值得遗忘”。需要压缩／晋升审核的记录仍走原深度任务，但不能让整理失败变成永久禁止清理的理由。

### 4.4 清理的是记忆数据，不只改成不可见

正式清理一个普通长期身份时，同事务删除或解除属于该身份的记忆正文、无效别名关系、对应向量、唤醒／grants及已失效的派生任务数据。不能只加deleted标记却继续保存所有正文和向量。同一job还有其他有效单元时，只作废相关单元，不整批丢弃其他结果；涉及已清理owner的正文快照也要退出持久化留存。清理完成的任务不能永久保留完整记忆正文；长期观测保留时间、数量、原因等简要结果即可。

关联短期详情不能另建无限档案：容量提前退出后暂保留至原7天截止，届时确认简要长期已正式保存，就可清理短期详情及其向量。改进摘要失败不影响已有合格基础摘要；短期详细合并／清理与过时维护结果的处理顺序需在执行计划固定，避免删除后还要求旧快照覆盖。若摘要缺失或正式引用尚未解除，记录有原因的清理待办，不无声破坏引用。

merged次记录和discarded记录也不能因为“不计活跃／归档”就无限留正文。实施细化应统一清理退出记录的正文／向量；仍被引用的旧ID只保留必要的轻量重定向，不能断开尚存主身份。已经清理的ID不能被旧后台结果重新写回；owner不存在视为该单元过时，不能回建旧记忆。

常驻learned的必要证据主身份保留；details和其当前事实不随普通经历删除。原始消息、已公开剧情／experiences、作者设定及学校计划本轮不制定删除政策。它们是来源／业务记录，容量100／1000／500不等于整个SQLite文件大小封顶；若以后要限制这些原始记录，可以另定日志保留方案。

因此，永久清理后该事件不能再通过记忆归档直接恢复；真实的新经历或用户重新叙述，可按当轮合法来源建立新记忆。不能为了“永不遗忘”自动扫描全部原始聊天并重建刚删掉的档案。

### 4.5 何时执行清理

合并、摘要改善、稳定认识审核仍受用户确认的空闲15分钟门禁。**容量计数、归档期限检查和少量确定性清理是程序维护**，不额外调用LLM；正常新增时可以在短事务处理必要条目，旧库大量超量则分批让位于前台，不能要求模型先成功整理才能腾出位置。

归档期限和短期详情清理截止纳入已有Host计时器／待办，不能只在新增记忆时检查；即使后续没有新消息，已到期旧记录也会获得清理机会。仍逐单元处理并检查前台优先级，不另建持续轮询或大量同步删除循环。

不在未完成故事引用尚未解除时删其必要身份；已有后台快照不构成永久保护，仍按版本／存在性检查处理过时结果。初次启用先输出数量、拟清理范围和原因，再按正式升级流程执行。本轮仅写方案，不实际删除任何历史数据。

100／1000／500是归一后的容量目标，首次升级或必要引用未解除时可以有明确的短暂超量和待办。不得把暂缓当成无限保留出口；保护解除后继续归一，观测展示实际差额和最老待办。纯规则清理不必等待一次15分钟空闲，避免持续聊天时归档不断增长。

## 5. 下一轮细化应合并的内容与验收

实施细化和执行计划需一起固定：

1. 活跃短期100、普通长期1000（含预备）、普通长期归档500；归档90天为本次建议值，配置和统计分开命名。
2. 短期用关联canonical的真实唤醒计数，活跃退出与归档清理分别给出完整排序；衰减不改变保留期限。
