本次只读核对现有源码和方案，新增本文；没有修改方案、程序、配置或数据库，没有运行测试、服务或在线模型验证。本文中的具体补充均为设计建议，尚未实施，也不表示用户已经批准所有 V0.3 参数。

## 1. 总体结论

审查总体合理，指出了进入实施细化前需要明确的规则。应采纳合同、有效期筛选、维护调度、字段归属和迁移方面的建议。

但“现有轮次派生 ID 与跨轮更新存在机制性冲突”的论证不成立；真正缺少的是更新／合并合同和稳定 ID 的使用约定。另有一处事实过时：空别名保留旧别名已经在上轮实现。

合并计数取 max、每任务查询向量限一次、仅用非空来源认定真实唤醒等建议，需要收窄或补充适用范围，不能直接作为已经确定的规则照搬。

## 3. 关于 3.1：创建 ID 的含义与稳定身份

### 3.1 当前 ID 可以跨轮稳定使用

现有 `src/memory/organize.ts:24–32` 在**创建**时分配：

```ts
const id = `${turnId}:short:${i}`;
const id = `${turnId}:long:${i}`;
```

它编码创建操作的来源，不要求以后内容永远只来自创建轮次。更新新增来源、保留 createdTurnId／updatedAt／sourceIds 即可。ID 不必描述当前内容的全部来历。

`src/storage.ts:57–58` 的 save 是按传入 id 的 UPSERT；现有加强路径已经证明同一行可以跨轮更新：

```ts
const old = d.storage.read('memories', c.id)!;
d.storage.save('memories', c.id, {
  ...old, mentions: old.mentions + 1, reinforcedAt: at,
});
```

因此，“名字含创建轮次，所以跨轮没有稳定行身份”不成立。

### 3.2 数组位置变化不会自动改变被更新条目的 ID

真正需要扩展的是 `MemoryResult`：当前短期只有创建列表，长期只有 create／reinforce，没有内容 update／merge。

例如第 N 轮创建 `turnN:short:0`，第 N+1 轮新增更新操作应为：

```text
action: update
id: turnN:short:0
本轮新增内容与来源: ...
```

即使它位于本轮结果数组第 5 项，程序仍按 `change.id` 更新原行，绝不能再次用 `<turnN+1>:short:5` 推导更新 ID。revision 和索引引用自然跟随同一 ownerId。

若实现者误把 update 当 create，确实会生成重复记录；错误原因是操作分派，而不是原 ID 格式。同轮重复修改同一 ID 应像任务变更一样由合同拒绝、走格式修补，不让数组位置决定身份。

### 3.3 建议的身份规则

- 创建后 ID 永久不变；保留现有轮次派生 ID 即可，也允许未来新建记录改用 UUID，但不是必须迁移的前提。
- create 的程序 ID 映射稳定保存，或使用原确定性派生规则，恢复不得重新分配。
- update／reinforce 必须引用模型输入中允许操作的已有 ID；merge 必须明确被合并 ID 和保留的主 ID。
- createdTurnId／sourceIds／更新时间分别表达创建与后续来源，不能从 ID 字符串推断全部 provenance。
- 内容或索引输入变化才增加内容 revision；单纯计数、续期、归档状态变化不必重算同样文本的向量，状态由检索筛选判断。

这足以支撑 ownerId + revision 的派生索引，不必重写旧记录主键。

## 4. 关于 4.1：空别名问题已在上轮修复

当前 `src/memory/organize.ts:44`：

```ts
aliases: change.aliases.length ? change.aliases : old?.aliases ?? []
```

其含义已经是：非空替换、空数组沿用旧别名、首次创建没有旧别名则空数组。`tests/review-fixes.test.ts` 分别覆盖空与非空两种值变化。

因此，原审查“当前整体替换，空数组会抹掉旧别名”的源码判断应撤回或注明针对旧快照。**V0.3 草案未重述别名策略**这个文档意见可以采纳：明确继承现有行为，不无限合并过时属性别名。

同值变更仍整条跳过，包括 aliases 更新；如果以后要允许只改别名，需要独立定义该行为，不能在本次回应中默默改掉。

## 5. 合并规则确实需要补，但不能只取较大计数

DSH 建议 content 重写、sourceIds 并集、时间保留、计数取较大者。这适合作为讨论起点，不能一套规则覆盖全部字段。

### 5.1 内容和感受不是“新值覆盖旧值”

同一事件的不同阶段可以有不同感受，例如考试后担心、获知结果后释然。合并应保留这种发展，而不是选择一个覆盖另一个；不相容的人物、事件或时间无法确认是同一经历时保留两条。

sourceIds 去重并集；事件开始／结束保留真实时间范围；短期到期锚点只取最近真实事件更新，不取模型重写时刻。正文压缩、合并本身都不产生新经历或唤醒。

### 5.2 max 不等于有效唤醒日期去重

两个同事件记录各有 2 次计数：

```text
A：10-20、10-22
B：10-21、10-22
```

按同日最多一次，合并后的有效日期是三天；相加得到 4，取 max 得到 2，两者都不准确。更极端的无重叠日期也会被 max 丢掉。

如果目标是精确执行三次续期与三十次候选，应保留轻量的唤醒日期记录，例如记忆 ID、本地日期、首次有效时刻、来源和 turn ID。首版可以是专门表或紧凑数据字段，实施细化选择一种即可；合并时按日期去重，而不是仅凭总数和最后一天猜测历史。

若用户接受保守近似，也可明确采用 max，但必须写明会少计，不能声称它是精确迁移。这是规则选择，不是数据库优化。

### 5.3 期限与主 ID 的建议

合并保留明确主 ID，其他 ID 保留合并去向以便旧引用追溯，失效副本不再独立检索或计数。选择和映射由程序保存，不由数组下标临时决定。

合并不能使用维护当前时刻自动刷新九十天。保留原记录合法期限／续期依据，不缩短已经获得的较晚期限；去重唤醒合并后是否达到额外续期条件，应根据保存的实际唤醒时刻和窗口规则重算，而不是把合并动作当第三次唤醒。常驻记录无九十天期限，合并也不能降回普通活跃记录。

以上比“时间取最早、计数取较大”更需要实施前逐项定清楚。

## 6. 可采纳的合同、检索与维护补充

### 6.1 硬校验与语义判定分开

同意在新的 reinforce 合同加入非空 sourceIds、合法当前来源 ID、允许引用记忆 ID；同轮／同日本地日期去重由段 B 事务完成。

但非空合法来源仍不能在程序侧证明“真实重谈”。检索材料的复述也可能给出一个合法 outgoing ID。避免自我制造唤醒仍需要提示要求和验收样本，不能把来源校验写成已经实现的语义审核。

原审查第 1 节把“outgoing 不能单独作为依据”当作原方案已明确的硬规则，表述偏强。草案禁止的是**仅因检索提供资料而在回复中复述并计数**，并未全面禁止实际输出作为来源。若要新增“唤醒必须含首次可见输入或新经历来源，outgoing 只能补充”的更严格合同，可以单独提出；它不是草案已批准内容，也不能顺带限制新事实使用实际角色输出作来源。

### 6.2 归档入口

同意明确谁决定归档查找。建议查询接口显式区分 current／archive 与当前事实／历史值；程序根据实际可见用户话题中的明确回忆请求开启 archive，查找续调用也可以提出 archive 请求，但必须以该请求上下文为准，不让模型仅因有兴趣就查全历史。

“以前／旧”等词不能单独使所有档案开放：查以前手机型号需要 detail_history，不一定需要归档经历；随口说“以前吃过”也未必是找回某段旧记忆。首版可用明确回忆请求规则加模型的既有补查接口，不增加一个独立分类模型；实施细化应列正反例并固定判定入口。

current／archive／历史值三种范围的筛选同时作用于词法和向量，不能让词法旁路绕过到期或版本判断。

### 6.3 字段归属与维护槽

模型提出内容、已有对象引用、来源、更新／合并／压缩／唤醒意图。ID 映射、内容 revision、短期到期时间、retainedFrom、expiresAt、计数及本地去重日期由程序按来源和规则维护。事件真实发生时间需要与创建／处理时刻分开，不把所有回忆事件都改成当前时间。

维护增加独立截止时间和工作类型，不能把它伪装成 world／school 或普通角色故事轮。maintenance job 与 post job 分开，分别恢复，索引任务仍是派生待办。

暂停门禁可以沿用现有 pump／collectReady 的暂停判断；真正需要的是让所有新维护入口服从同一门禁，以及 paused 状态不因到期维护时间不断立即唤醒。不是再引入一套暂停状态。

04:30 调度、停止后补办和旧轮先恢复需要写入运行时／恢复文档，DSH 对这一点的要求可以采纳。大量到期内容连续处理会影响新故事响应，实施细化还应明确批次推进与调度让步规则，避免“每批20条”被误解为整次启动最多20条或无界阻塞整个聊天队列。

## 7. 缓存、迁移与文档建议

### 7.1 向量与缓存

入库向量和查询向量都归一化，点积才对应余弦相似度；不能仅归一化库向量就把点积当作可标定的余弦值。

“每任务最多一次查询向量”宜限定为**一次逻辑检索**：同一查询跨记忆类别共用向量，同一查询的重试／格式修补不重复计算。已有 lookupDetails 补查允许新的查询，不应被这个次数限制封死；不同可见信息阶段的主叙事与个人导演也不能强行共用一个查询。

建议只做进程内、有数量与寿命上限的查询向量缓存，按模型／端点／维度／输入模板／文本标识。缓存的是向量，不是包含旧事实或过期记录的整个检索结果；是否过期和哪个 revision 有效仍每次查库。

### 7.2 迁移

建议旧记录内容 revision 从 1 开始；旧短期按 createdAt + 七天补到期字段，没有资料时不编造更晚事件更新时间。旧长期首次迁移九十天观察期为一次性规则，重建向量不得再延期。

旧 mentions 复制为 legacyMentions 后冻结，新计数从零开始，不继续把旧字段作为唤醒计数或第二套加强依据；旧来源、时间和 ID 保留。以上是对草案迁移段落的合理补全。

### 7.3 文档

实施时同步 MEMORY、INTERFACES、IMPLEMENTATION、RECOVERY、LIFE 中的调度说明、README、审核入口和实施日志；当前 V0.2 说明暂不改成尚未交付的 V0.3 行为。

图上可直接写“累计三十次 → 常驻候选 → 判断类型”，消除略读误解。原图出边已有“审核内容类型”，正文又明确候选，因此属于表达改进，不是自动晋升的另一套规则。

三次续期为草案主方案；每次续期当前只是一句可讨论注记，不是实施者可擅自选择的并列运行方案。用户未改变规则时不得选走备选。

## 8. 请 DSH 复核的核心分歧

1. 是否同意撤回“轮次派生创建 ID 天然不稳定”的机制冲突，改成“必须增加按已有 ID 更新／合并的合同与恢复规则”？
2. 是否确认工作区已经实现空别名保留，并把该项改为 V0.3 继承说明？
3. 是否同意计数 max 是会少计的近似；若坚持精确日期去重，应保存可合并的唤醒日期依据？
4. 是否同意来源 ID 的硬校验不等于真实唤醒语义校验，且“outgoing 完全不能单独作依据”不是原草案已确定规则？
5. 是否同意向量查询次数限制不能封死合法 lookup 补查，缓存不应跳过有效期／当前版本过滤？

待这些判断确认后，可在用户认可的基础上修订方案并形成实施细化。当前总体方向可保留，尚不需要依据本审查修改程序。
