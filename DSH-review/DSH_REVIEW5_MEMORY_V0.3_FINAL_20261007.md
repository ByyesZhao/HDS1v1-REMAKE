## 1. 自相矛盾：联网材料的 12000 截断

- 细化 §6.3 把 `webMaterialCharactersLimit` 默认设为 `null`，并注明"不再默认截取前 12000 字符"；§10 验收第 9 条要求"联网资料超过 12000 字符默认不截掉后半段"。
- 执行计划任务7 的验收项也写"联网资料 >12000 字符默认保留尾部"。

但**现有代码是硬编码截断**：`src/index.ts:77` 的 `getWebMaterials` 里 `.slice(0, 12000)`。文档只说了默认值，没有把"修改这处硬编码、改为按配置决定是否截断"写进任何任务的文件列表或步骤。

`src/index.ts` 虽然在任务7 的 Files 里，但任务7 的验收项写的是"默认保留尾部"——如果实现者只改配置不改那一行，这条验收必然失败，而且失败原因不容易定位。建议在任务7 的实现步骤里明确写出这一行，或直接写"删除该 slice，改由配置控制"。

## 2. 未定参数：取消预算之后，用什么兜住请求体积

这是本次修订最需要用户拍板的一点。用户的原话是"取消人为预算，默认不限"，但**空值预算与"不限"不是同一个意思**，文档两处读法不同：

- §6.3 line 198："实际调用仍受供应商所选模型的上下文／输出／Embedding容量限制……超出真实接口容量时按现有调用失败路径明确记录，**不偷偷删当前来源或截短记忆后强行重发**。"
- 执行计划 Global Constraints："**实际技术容量按所选接口**，不把字符预算当token容量。"

按字面执行，行为是：候选不限 → 选中的全部正文完整注入 → 一旦超过模型上下文 → **调用失败 → 故事暂停**。对一个"运行几个月"的生活模拟，这不是罕见情况：短期 7 天 × 每天数条事件 + 长期 90 天 + 细节，无限额时单轮很容易堆到几万字符。

现有 V0.2 的 8000 预算实际上兼任了"技术容量兜底"这个角色，现在它被移除了，但**没有替代物**。

建议在细化里补一条明确规则（措辞可以是"技术容量兜底不是人为预算"）：

> 当选中内容的合计长度超过所选模型的上下文容量估计时，按相关性从低到高移除**完整条目**（不截半条正文），并记录本次移除数量；本轮来源、核心背景、当前状态和控制信息不参与这种移除。该兜底只在触及容量时生效，不构成每轮固定预算。

这样既保留用户"平时不人为截断"的意图，又不会让"记得越多越容易调用失败"。若用户确实希望连这层也去掉，那应当明确写成"接受调用失败并暂停"，让验收 8 的样本测试覆盖这一点。

## 3. 结构性问题：取消候选配额后，RRF 要在多大的集合上做

细化 §6.2 现在是：确定 key／别名优先；其余走 RRF（常数 60）；`candidateItemsPerRoute` 默认 `null`、`detailItemsLimit／shortItemsLimit／longItemsLimit` 默认 `null`。

也就是**词法与向量两路都可以给出全部命中，然后在全量上做排名融合，再把全部结果交给模型**。两个后果：

1. **成本**：`10,000 条候选` 的基准测试（验收 8）在默认不限下就是常态规模，每轮都要对两路全量排序并合并。行数还在逐月增长。
2. **质量**：词法路是"包含查询词"就命中（现有 `queryTerms` 是二元组），没有分数下限。一条"今天吃什么"可能词法命中上百条历史，全部进入上下文，反而把真正相关的挤淡。

§6.3 已经留了可配置开关，但没说**默认路线上"相关性筛选"到底怎么算**。建议明确一句：词法路在进入融合前按命中词数／覆盖度做一次基础筛选（或用可配置的最低命中数），向量路则沿用"未标定前不开启 semantic-only"的既有约定；两者都不引入固定条数上限。这样"默认不限"仍然成立，但不是"全库注入"。

## 4. 小项

1. **`webMaterialCharactersLimit` 与 `ContextLimits`：** 前者出现在 Global Constraints 与 §6.3 表中，但执行计划"文件与类型约定"的类型表里没有它（表里只有 `ContextLimits` 六个字段）。建议补进 `ContextLimits` 或单列一个配置项，别留成"文档提到但类型里没有"。
2. **`longItemsLimit` 的归属：** 细化 §6.3 表注写"long 包含按需常驻经历"，但 §5.3 已把常驻经历放进 `learned_background`、由 `RetrievedContext.learned` 单独承载。请明确 `longItemsLimit` 是否也约束 `learned`，否则实现者会两处各截一次或都以为对方在截。
3. **首轮索引的 `stateVersion`：** 短期创建时同时写出预备长期并"提前登记索引任务"，但预备长期在 `retainedFrom` 前不提供给检索（§3 表格）。应用索引单元时核对 `stateVersion`，而这期间短期若被新进展更新（§3 第三行场景），预备窗口会调整——建议明确"应用索引只校验 `revision` + 配置签名，不校验 `stateVersion`"（§2.2 已有这个意思，但 §7.4 又要求"事务应用前核对当前版本"，两处需要一句衔接）。
4. **首次建议的 `initialState`：** 现有 V0.2 初始化会写 `nextMathWorldAt/nextSchoolAt`（`src/index.ts:42` 一带），新增 `nextMaintenanceAt` 要一起初始化到"下一个 04:30"；任务1 的测试项已覆盖"无到期任务时下一 04:30"，建议在任务7 的装配步骤里也点一句，避免只在迁移路径上设置。
5. **`ContextLimits.recentMessagesLimit`=30 未列入验收：** 执行计划验收 3 提了"近期原文窗口保留现有范围"，但没有测试项断言"当旧配额全部关闭时，原文仍恰好 30 条"。建议并入任务4 的"默认不限测试"。
6. **验收 8 的通过判据：** "完整提供"需要一个可判定的形式（例如"构造 N=100 条相关候选，断言返回 100 条且未截断正文"），否则只能靠读代码分支，与 §10 开头"必须证明可见行为，而不仅检查源码是否有分支"自相矛盾。
