方式：只读文档与源码，**没有运行测试或服务，没有修改任何文件或配置**。行号以当前工作区 `src/` 为准。

结论：**方案方向正确，可以进入实施细化；但有 5 处口径需要先定，其中 1 处需要用户表态。** 方案把"模型驱动节奏"改为"程序驱动节奏"、把自主周期从固定墙钟改为前台空闲周期，这两个方向与用户意图一致，也与现有"串行 + 冻结 + 段 B 一次提交"的结构相容，没有引入第二套执行系统。第 3 节确认了它判断准确的部分。

## 1. 建议先定的五处

### 1.1 `idleAnchor` 的起点需要写明是刻意的

方案 §3.2：

```text
idleAnchor = max(最近用户输入接收时间,
                 最近一轮最后一个剧情／角色输出项的发送确认时间,
                 最近一次无可见输出的共同轮完成时间)
autoAdvanceAt = idleAnchor + 60 秒
```

"最后一个输出项"是**最后一个 outbox 项的 `confirmedAt`**。现有发送节奏是每段之间按字数等待 3～10 秒（`output/qq.ts:6`），一轮 4～5 段就要 25～40 秒，于是：

- 用户 22:31:00 发言，模型 22:31:40 发完最后一段 → `autoAdvanceAt = 22:32:40`；
- 即**用户真正拥有的静默时间是从"看完最后一句"起算的 60 秒**，而不是从自己发言起算。

这符合"双方最近消息后 60 秒"的字面要求，但方案没有说明它是刻意选择还是实现巧合。§3.3 只覆盖了"输入在旧轮发完前已等满 60 秒"的情形。建议补一句明确写法，例如"窗口自角色最后一次可见输出确认起算；用户的输入会把它重新推后"，避免实施者改成"从本轮开始算"或"从最后一段文字起算"。

### 1.2 手动推进与自动到期的"已消费"语义没有写死

常见序列：用户发一条消息（`autoAdvanceAt = T+60`），紧接着按 `【推进】`。方案 §3.1 说手动请求"合并为一个请求""不等待 60 秒"，但**没有说消费手动请求的这一轮是否同时取消那个自动节点**。

若不取消，同一批输入会在 60 秒后再次触发一轮：一条消息吃掉两轮、白烧一次 20 轮额度，用户会看到重复推进。

建议补一句："消费手动请求的轮次在发送确认后重置 `autoAdvanceAt`；该轮已覆盖的自动节点不另行触发。"

### 1.3 `【推进】` 的落库位置要定死，否则会出现"未读的控制指令"

§3.1 说"原始控制请求可单独留作运行审计"，§8 的表格又说输入记录要"普通消息与推进命令分类"。但按 §3.1 第 1 步，命令是**立即持久化并唤醒调度器**的，而"它是否被当作指令消费"要等调度器空闲（可能旧轮还在跑）才能判定；同时 §3.1 又说"旧活动结束时取消它尚未消费的请求"。所以存在中间状态：命令已入库、尚未消费、活动可能已经结束。

这里有一个具体风险：现有记忆检索的近期原文条件是 `direction === 'outgoing' || seenTurnId !== null`（`memory/retrieval.ts:55`）。如果控制命令作为 incoming 写入 `messages` 且永不置 `seenTurnId`，它会一直留在未读集合里被反复交付——这正是方案自己担心要避免的"控制指令成为剧情或记忆"。

建议直接规定：**被判为控制指令的记录不写入 `messages` 表**，只写运行审计；或者明确它写入时即带分类标记，且所有交付路径（含未读集合）都排除该标记。前者更简单。

### 1.4 长时间无人回应时活动是否照样演完，需要用户表态

§4.2 规定第 17～19 轮收束、第 20 轮终结，§4.1 又说"活动可提前结束，20 是上限"。但方案没有回答：**用户在第 3 轮就不说话了，活动会怎样？**

按 60 秒自动推进的节奏（每轮生成 + 分段发送约 1 分钟），20 轮大约 20～40 分钟就会烧完，所以不会永久挂着；代价是"用户离开后，她会自己把整场活动演完"。这是本次唯一需要用户选择的产品行为：

- **A**：维持现设计——无人也按 60 秒推进到第 20 轮自然收尾；
- **B**：补一条提前收尾——连续 N 轮（例如 3 轮）没有用户输入时，进入收束并在下一轮结束。

两者都自洽，但观感差别很大，建议明确选一个并写进方案。

### 1.5 跨过 `sleepAt` 的判据要和 `isSleeping` 对齐到同一处

§5.1 说"尚未实际入睡的预计睡眠时间是可协调安排……必须调整共同模式下的判定顺序，而不能只在提示词说'预约优先'"，第 168 行又要求"从计划睡眠到真实睡眠的控制，以及最终自主时间计算，要由同一个提交顺序处理"。方向对，但**没有给出判据**：现在 `isSleeping` 只有时间区间（`host/state.ts:7`），系统里不存在"她其实已经睡着了"这个状态。

可行且改动可控的两种收法：

- **A（推荐）**：共同活动进行期间，`sleepAt` 只作为提示词里的"计划"，不参与门禁；判据只需要"当前是否有进行中的活动"，活动结束轮的段 B 提交再按当时状态安排睡眠。
- **B**：新增"实际入睡"标记，由主叙事在场景里确立、随段 B 提交，`isSleeping` 改读该标记。改动面更大，且要么信任模型、要么再加校验。

同时提醒一处相关现存行为：`app.ts` 开头的 `isSleeping` 判断会直接返回一个"纯睡眠候选"（`app.ts:79-87`），因此**只要 `sleepAt` 到了、活动又在跑，那一轮完全不会运行主叙事与个人导演**——这正是方案要修的"卡住活动"。改的时候要一并防止反向问题：她**实际上已经睡着**时，不该因为活动在跑就继续玩下去。A 方案天然避开这一点（活动结束即重新安排睡眠），B 方案需要额外校验。

## 2. 三处引用与表述不精确（不影响结论）

1. §1 表格第 19 行把"15 秒截止"指到 `src/host/input.ts:12`，实际在 `input.ts:21`（`:12` 是 `acceptInput` 的方法签名）。
2. 同表"预约前是否必须先跑一轮自主生活"指到 `scheduler.ts:35`，实际判据在 `scheduler.ts:27-28`；`:35` 是 `triggerKinds` 的构造。
3. §7.2 表格写"若这一轮只有主叙事、没有个人导演，仍算已经更新生活"，但 `app.ts:144` 的 `autonomousIntervalMinutes` 目前只在 `autonomous` 或 `waking` 时非空——这是**待实施变更**而非现状。建议像同表第 26 行那样显式标注"本方案将改"，以免被读成已实现。

## 3. 已核对成立、建议保留的设计

- **"先补齐生活"确实已经实现**：`app.ts:102-114` 先运行主叙事、再判断可见性、再交给个人导演；`recovery.ts:61-74` 在段 B 提交候选状态与已看标记。§6 把它写成"保留并明确"而不是新做，判断准确。
- **取消模型可写的 `nextStepAt` 是可控收敛**：现只有 `app.ts:111`、`contracts.ts:16,57`、`prompts.ts:8` 在用；`Scene.shared.nextStepAt` 作为程序计算结果保留即可。顺带可以删掉 `contracts.ts:57` 的"必须晚于 at"校验——那条校验的存在本身就是为了约束模型，程序接管后不再需要。
- **统一自主周期的公式与现有实现相容**：`recovery.ts:69` 已经是"`completedAt` + 冻结的分钟数"，方案只是把触发条件从"仅 autonomous/waking"扩展到"所有前台故事轮"，冻结候选复用机制不需要改。
- **20 轮上限有程序校验**（`stepNumber/maxSteps/remainingSteps` + 拒收第 21 轮）符合"不靠模型自觉"的原则；把收束阶段也写进合同而不是留给模型自由发挥，方向正确。
- **§8 的七条恢复规则**（按活动 ID 关联、段 B 读最新 Runtime、结束时撤销节点与未消费请求、重启最多运行一轮过期节点、结束标志续发不二次结束）与现有"串行 + 冻结 + 一次提交"结构一致，没有引入第二套执行系统。
- **§5.2 的排序**（先执行条件、再安排优先顺序）比"预约 > 睡觉 > 消息"的单表更准确，尤其是把"计划睡眠"和"已睡着"分开这一点，正是当前实现真正缺的东西。

## 4. 实施细化时建议一并写清的两点

1. **旧活动行的升级口径**：§8 末尾提到"已有活动旧行缺计数时，迁移需明确起算口径"，但没有给默认动作。当前生产库尚未建立首个故事（记忆迁移时 `memories=0 / details=0`），所以现实风险很低；仍建议写明"若检测到进行中的旧活动：结束它还是从第 1 轮接续"，以及是否需要服务停止。
2. **`scene_step` 的唯一性与来源**：§8 说"每活动至多一个有效任务，时间来自程序节奏控制"，这与现有 `app.ts` 中"每轮维护一项 `scene_step`"的处理一致（`app.ts:168-171`）。实施时建议把"程序计算 `nextStepAt` → 写 `scene_step`"这条链写成一处逻辑，避免保留两条都能创建节点任务的路径。
